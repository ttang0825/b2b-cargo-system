지금까지 작업한 내용으로 PR을 만들고, merge될 때까지 지켜봐줘.

## 1. 올리기 전에

- 변경 파일이 의도한 것만 있는지 확인할 것 (`next-env.d.ts`·`tsconfig.json`은 빌드가
  다시 만드는 파일이라 섞여 들어갔으면 `git checkout --`로 되돌릴 것)
- 검증이 아직이면 먼저 할 것: `npx tsc --noEmit` 통과 +
  `npm run build` 프리렌더 실패가 **기준선(47개)과 항목 단위로 동일**한지
- 커밋 메시지는 **무엇을 왜 바꿨는지**를 적을 것. 특히 지시서와 다르게 판단한 것,
  나중에 되돌리면 안 되는 것은 이유까지 남길 것
- 브랜치는 `claude/claude-md-reference-work-jtqcgh`,
  push는 `git push -u origin <branch>` (네트워크 실패면 2·4·8·16초 간격으로 최대 4회 재시도)
- 브랜치가 main에서 새로 시작된 상태라 `non-fast-forward`가 나면, **원격 브랜치 내용이
  이미 main에 들어가 있는지 트리 비교로 확인한 뒤에만** `--force-with-lease`를 쓸 것

## 2. PR 본문에 반드시 넣을 것

- 🔴 **DB 마이그레이션이 있으면 맨 위에** — 실행할 SQL과 "Preview에서 테스트하기 전에
  Supabase SQL Editor에서 먼저 실행해달라"는 안내 (Preview는 운영과 같은 Supabase를 봄)
- 무엇을 왜 바꿨는지, 설계상 되돌리면 안 되는 지점
- ⚠️ **지시서와 다르게 판단한 것**은 빠짐없이 이유와 함께
- 검증 결과 (tsc / 빌드 기준선 비교 / 자동검증 항목)
- **확인 부탁드립니다** — 사용자가 Preview에서 눈으로 봐야 하는 것 목록
- 코드 밖 사용자 작업이 필요하면 그것도 (예: 솔라피 발신번호 등록)

## 3. 만든 뒤

1. `subscribe_pr_activity`로 구독
2. CI 상태 확인 후 **PR 번호·Preview URL·CI 결과**를 사용자에게 보고
3. `send_later`로 1시간 뒤 자체 점검 예약

## 4. 지켜보는 동안

- **리뷰 코멘트가 오면**: 확실하고 범위 안이면 고쳐서 push하고 PR에 답변,
  애매하거나 구조가 걸리면 먼저 물어볼 것. 고친 뒤 Preview 재배포되면 알려줄 것
- **CI가 깨지면**: 원인을 찾아 고쳐서 push하거나, 못 고칠 이유를 PR에 답변할 것
- 배포 알림 봇 댓글은 대응 불필요
