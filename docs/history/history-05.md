화면 캡처라 글자 선명도 때문에 PNG 가 맞고, WebP 전환은 별도 판단이다 — **안 했다.**

**═══ ⑤ 🔴 이 환경에서 재면 안 되는 것 — FCP·LCP ═══**
프록시가 폰트 CDN(`fonts.googleapis.com`·`cdn.jsdelivr.net`)을 막아 **그 대기 시간이 그대로
섞여 들어간다.** 실제로 FCP 13,240ms · LCP 17,600ms 가 나왔는데 **우리 페이지의 값이 아니다.**
🔴 **이 숫자를 근거로 성능을 판단하지 말 것.** 이 환경에서 믿을 수 있는 것은 **전송 바이트**와
**요소 타이밍**(카드 노출 ↔ 이미지 도착 간격)이다.

**═══ ⑥ ⚠️ 재현에 세 번 실패하고서야 조건을 찾았다 — 다음에 같은 일을 하면 이 조건을 쓸 것 ═══**
🔴 **`waitUntil: "load"` 로 기다린 뒤 스크롤하면 재현되지 않는다** — 히어로가 이미 다 받아져

🔴 **rAF 로 스크롤 속도를 재도 안 된다** — CPU 스로틀에 눌려 1.5초짜리 스크롤이 15초가 되고,

**═══ ⑦ 🔴 리뷰③ — 덜덜거림의 진짜 원인: 브라우저가 `scrollLeft` 를 정수로 반올림한다 ═══**

실측이 답을 바로 줬다.
```

    10    → 10                          0    → 20.000
    10.25 → 10                          0.25 → 20.000
    10.5  → 11                          0.5  → **19.000**   ← 소수가 없다
    10.75 → 11                          1    → 19.000
```
22px/s 는 한 프레임에 **0.37px** 인데 화면은 정수로만 움직이니 **어떤 프레임은 0px, 어떤
프레임은 1px** 씩 가서 덜덜거린 것이다.
🔴 **속도를 올려도 낫지 않는다** — 프레임당 이동이 정수로 딱 떨어지지 않는 한 같은
현상이고 프레임 간격 자체도 일정하지 않다. **속도만 바꾸는 것으로 이 지적에 답하지 말 것.**
🔴 **고친 방법 — 정수부와 소수부를 나눠 싣는다.**
```
  정수 픽셀 → 바깥 상자의 scrollLeft   네이티브 스크롤 그대로 (터치·관성이 공짜다)
  소수 픽셀 → 안쪽 줄의 transform      0~1px, GPU 합성이라 소수까지 그려진다
```
🔴 **둘 중 하나만 쓰지 말 것** — `transform` 만 쓰면 손으로 넘기는 것을 직접 구현해야 하고
(64차 덜덜거림의 원인), `scrollLeft` 만 쓰면 위 반올림에 걸린다.
🔴 **그래서 DOM 이 한 겹 늘었다** — `.landing-vehicle-grid`(스크롤되는 바깥 상자) 안에
**`.landing-vehicle-track`**(실제로 미끄러지는 줄). 🔴 **안쪽 줄은 데스크탑에서
`display: contents`** 라 상자를 만들지 않아 카드 24장이 바깥 6열(1150px 이하는 4열)
그리드에 그대로 들어간다 — **지우면 그리드가 카드 하나짜리가 된다.**
🔴 **`useReveal` 은 바깥에 걸려 있다** — 같은 요소에 두면 두 transform 이 서로 덮어쓴다.
⚠️ 바깥이 모바일에서 `display:block` 이라 **인라인 `gap: 12` 이 무시된다** — 줄이 자기 gap 을
직접 갖는다.
⚠️ **중간에 한 번 더 막혔다** — 처음에는 `el.scrollLeft` 를 읽어서 더했는데 반올림 때문에
**1px 에서 멈췄다.** 위치를 코드가 소수까지 누적하도록 고쳐서 풀었고, 그 뒤에도 화면은
정수로만 움직여서 위 transform 분담이 필요했다. **두 단계였다.**
