### ① 🔴 표를 갈랐다 — 이 차수에서 가장 되돌리기 쉬운 결정이다

`push_subscriptions`(직원용, 38차)에 `customer_account_id` 컬럼 하나만 더하면 끝날
일처럼 보인다. **그렇게 하지 않았고, 다음 세션이 「정리」로 합칠 위험이 가장 큰 자리다.**

사유는 **롤**이다. 화주포털 계정과 직원 계정이 **둘 다 `authenticated`** 다(19차).
그래서 이 표들은 **RLS on + 정책 0개**로만 지켜진다 — 정책을 하나라도 만드는 순간
양쪽이 함께 열린다. 한 표에 두 종류를 담아 두면 언젠가 누가 「조회 편하게」 정책을
하나 열 때 **화주와 직원 기기가 한꺼번에 샌다.** 표가 둘이면 그 사고가 한쪽에서 끝난다.

🔴 **합치지 말 것.** 마이그레이션 단언이 `staff_id` 컬럼의 **부재**까지 확인한다.

### ② 🔴 `company_id` 를 구독 표에 복사해 두지 않았다

발송은 **회사 단위**(그 화주의 모든 담당자 기기)라 회사 id 를 이 표에 넣어 두면
조인 없이 끝난다. **그런데도 안 넣었다** — 담당자 계정이 다른 화주로 옮겨지면
복사해 둔 값이 낡아 **남의 회사 소식이 그 폰으로 간다.**

발송할 때마다 `customer_accounts` 를 조인해 회사를 정한다(조인 한 번).
⚠️ **그래서 이 표만 보고는 「어느 화주인가」를 알 수 없다 — 그것이 의도다.**
마이그레이션 단언이 `company_id` 컬럼이 **없는지**를 확인한다.

### ③ 🔴 서버에서는 `await`, 브라우저에서는 아니다 — 방향이 반대다

38차 B장이 실제로 겪은 자리다. **서버리스 함수는 응답을 돌려준 뒤 얼어붙어서** 떠 있는
약속이 끝나지 않는다 — 정산확정(`app/api/admin/invoices/confirm/route.ts`)처럼
**서버 안에서** fire-and-forget 으로 두면 **푸시가 아예 안 나간다.**

반대로 견적·배차는 **브라우저가** 서버 API 를 부르는 구조(원칙 53번)라 `await` 하면
담당자의 상태 변경이 알림을 기다리며 멈춘다. **거기서는 `void fetch(...)` 가 맞다.**

```
  견적 상세 · 배차 상세 · 배차 목록   브라우저 → /api/admin/notify-portal-push   await 금지
  정산확정                           서버 라우트 안에서 notifyPortalPush()        await 필수
```

🔴 **한쪽 규칙을 다른 쪽에 옮기지 말 것.** `lib/notifyPortalPush.ts`(브라우저용)와
`lib/portalPushNotify.ts`(서버 발송 정의처)의 **이름이 비슷해서** 헷갈리기 쉽다 —
**`notify-` 로 시작하는 쪽이 브라우저**다.

### ④ 🔴 부르는 곳이 넷이라 매핑을 화면에 적지 않았다

배차 상태를 바꾸는 자리가 **넷**이다(원칙 53번이 문서화한 그대로) — 배차 상세의
**확정 버튼 · 상태 드롭다운 · 상차/하차 체크박스**, 그리고 **배차 목록의 드롭다운**.
상태 → 사건 매핑을 화면마다 적으면 **「목록에서 바꾸면 알림이 오고 상세에서 바꾸면
안 오는」** 상태가 된다. `lib/notifyPortalPush.ts` 의
`notifyPortalPushForDispatchStatus()` **한 곳**이다.

🔴 **수동 재발송 버튼(배차 상세 「문자 발송」 섹션의 셋)에서는 부르지 않는다** —
거기는 담당자가 **문자**를 다시 보내는 자리라, 며칠 뒤 눌러도 「배차가 확정되었습니다」
푸시가 또 간다. ⚠️ **`fetchDispatchSmsPreview()` 안에 넣으면 딱 그 사고가 난다**

넣으려다 호출부를 세어 보고 그만뒀다).

🔴 **바뀌지 않았으면 안 보낸다** — 같은 값을 다시 고르는 일이 흔하고, 그때마다 화주

🔴 **그래서 지시서 2-1 의 「15초 폴링 결과가 늘어난 순간」으로는 가장 급한 발주요청을
못 잡는다.** 폴링이 아니라 **배지 건수(`counts`)가 늘어난 순간**에 얹었다 — 폴링 둘 ·
Realtime 하나 · `notifyBadgeRefresh` 세 경로가 전부 그 한 곳으로 모인다.
🟢 **새 되풀이 타이머 0개**(포털도 0개).

**② 관리자 경로 셋 중 둘이 없는 경로였다** — `/admin/inquiries` → 실제
`/admin/public-quotes` · `/admin/customer-requests` → 실제 `/admin/portal-requests`.
🔴 **지시서에서 옮겨 적지 말고 `app/admin/` 을 볼 것.**

**③ 발송 방식 — 지시서에 없던 선택지가 실측으로 생겼다.** 지시서는 (가) `web-push`
패키지 / (나) 직접 서명 + **페이로드 없는 푸시** 중 고르라고 했는데, 재 보니
**암호화까지 Node `crypto` 만으로 된다**(`hkdfSync`·`createECDH`·`aes-128-gcm` 이 다
있다). 그래서 **(나+) 직접 서명 + 암호화 페이로드**가 됐고 사용자가 확정했다.
🟢 의존성 0 + 알림 문구 정확 — 페이로드가 없으면 서비스워커가 깨어나 API 를 다시
불러야 하고 **어느 종류가 왔는지도 모른다.**
🟢 **RFC 8291 §5 시험 벡터와 바이트 단위로 일치**하는 것을 확인하고 옮겼다.
🔴 **이 구현을 고치면 그 시험을 다시 돌릴 것** — 암호가 틀리면 브라우저가 알림을
**조용히 버려서** 「안 온다」로만 나타난다(예외도 안 난다).

**④ 알림음 파일을 안 넣었다 — 완료조건 11번이 해당 없음이 됐다.** `public/` 에 음원을
두는 대신 **WebAudio 로 합성**했다. ① 이 저장소는 public 이고 바이너리를 늘리지 않는다
② 파일을 두면 코드가 **문자열로만** 가리켜 `grep` 참조가 0건이 되고, 그러면 §9
「지우면 안 되는 파일」 목록에 한 줄을 더해야 한다(함정 18번의 그 자리).
🟢 **소리가 셋이 된 뒤에도 그대로다** — 음 높이와 길이만 바꾸면 되므로 파일이 필요 없다.
🔴 **「종류를 늘리려면 음원을 받아야 한다」로 가지 말 것.**

### ② 실제로 돌려 보고 잡은 결함 둘 — 둘 다 눈으로는 안 잡힌다

**🔴 `AudioContext.resume()` 은 사용자 제스처가 없으면 거절하지 않고 「영영 안 끝난다」**
(실측 2026-09-16 · Chromium). 그냥 `await` 하면 함수가 돌아오지 않아 **호출할 때마다
끝나지 않는 약속이 하나씩 쌓인다.** 화면은 멀쩡해 보인다.

```js
await Promise.race([
  audioCtx.resume().catch(() => undefined),
  new Promise((r) => setTimeout(r, 300)),
]);
if (audioCtx.state !== "running") return false;
```

🔴 **이 경주를 빼지 말 것.**

**🔴 서버리스 함수는 응답을 돌려준 뒤 얼어붙는다.** 지시서 금지 10번의 「`await` 로 묶지
말 것」(fire-and-forget)을 그대로 따르면 **푸시가 아예 안 나간다.**
⚠️ **지시서가 본보기로 든 PR #154 는 브라우저에서 서버 API 를 부르는 경우라 사정이
다르다** — 그쪽은 브라우저가 계속 살아 있다. 여기는 **이미 서버 안**이다.
그래서 **3초 상한을 걸고 기다리되 절대 던지지 않는다**(`SEND_BUDGET_MS`).
🔴 **접수는 어떤 경우에도 성공한다** — VAPID 미등록 · DB 안 닿음 · **응답 없는 DB**
세 경우로 증명했다(상한 3001ms 실측).

### ④ 지킨 것 — 되돌리면 안 되는 것들

- 🔴 **`push_subscriptions` 는 RLS on + 정책 0개다.** **화주포털 계정과 직원 계정이
  둘 다 `authenticated` 롤**이라(19차) 정책을 하나라도 만들면 **화주가 직원 기기의
  구독 정보를 읽는다.** 마이그레이션 단언이 이것을 지킨다
- 🔴 **`endpoint` 유니크** — 같은 기기가 두 번 등록되면 알림이 두 번 온다. `on conflict`
  로 쓰고 **애플리케이션 사전조회로 대신하지 말 것**(§7 — 동시 요청은 그것으로 못 막는다)
- 🔴 **`staff_id` FK 는 cascade** — 퇴사자 기기로 알림이 계속 가면 안 된다.
  ⚠️ `support_access_logs`(원칙 32번)와 **반대로** 잡은 것이다 — 그쪽은 **이력**이라
  남겨야 하지만 이것은 **살아 있는 발송 대상 목록**이다
- 🔴 **어느 직원인지는 쿠키 세션으로만 정한다**(원칙 30번) — 클라이언트가 `staff_id` 를
  같이 보내면 콘솔에서 남의 id 로 바꿔 **그 사람 기기 목록에 내 기기를 끼워 넣을 수 있다**
- 🔴 **role 을 가르지 않는다**(사용자 확정: 직원 전원 같은 알림) — `role === "admin"` 을
  넣으면 **staff 가 알림을 못 받는다**
- 🔴 **서비스워커 캐시 목록은 한 글자도 안 건드렸다** · 구역은 `/admin`(**끝 슬래시 없음**,
  PR #127) · 🔴 **`public/customer/sw.js` 는 0줄**이다
- 🔴 **404·410 이면 구독 행을 지우고**, 그 밖의 오류는 `failed_at` 만 찍는다 — 일시적
  장애로 구독을 버리면 담당자가 다시 눌러야 한다
- 🔴 **아이폰은 홈 화면에 추가한 뒤에만 된다**(iOS 16.4+) — 설치 전이면 단추 대신 안내를
  그린다. ⚠️ **앱을 지우면 구독이 사라진다** — 다시 설치하면 다시 눌러야 하고 **버그가 아니다**
- 🔴 **거절당하면 다시 묻지 않는다**(브라우저가 영구 차단해서 창이 아예 안 뜬다)
- 🔴 **VAPID 가 아직 없는 배포본에서는 단추를 안 그리고 발송도 조용히 건너뛴다** —
  코드가 환경변수보다 먼저 배포되는 구간이 **반드시** 생긴다
- 🔴 **판별자는 문자열이다**(`kind: "ok" | "gone" | "error"`) — 이 저장소는 `strict: false`
  라 참/거짓으로는 타입이 안 좁혀진다(32차가 기록한 자리를 37차에 이어 또 밟았다)

### ⑤ 실사용 리뷰 — 알림음 볼륨·소리 (PR #160 코멘트)

사용자 코멘트 둘 — *「알림배너가 윈도우창 아래에 알림배너로는 못뜨나?」* ·
*「알림 소리의 스타일과 볼륨을 조절할 수 있나?」*

**① 윈도우 배너는 이미 B장이 하는 것**이라 **코드 변경 0**이다. 확정은
**「지금대로 둘 다」** — 관리자 화면을 보고 있어도 화면 배너와 윈도우 배너가 함께 뜬다.
🔴 **「화면을 보고 있으면 푸시를 건너뛰자」로 바꾸지 말 것**(사용자가 고른 것이다).

**② 볼륨 3단계 + 소리 3종**을 종 모양 **옆 `▾`** 에 달았다.

```
  볼륨   작게 0.07   [보통 0.18]   크게 0.38
  소리   [두 음 880·1318.5]   단음 1046.5   세 음 659.3·880·1174.7
```

- 🔴 **기본값(보통 · 두 음)은 A장이 넣은 그 소리 그대로다** — 아무것도 안 고른
  담당자의 소리가 **말없이 달라지면 안 된다.** 음 높이·길이·게인을 바꾸지 말 것
- 🔴 **고르면 그 자리에서 들려준다.** 그 클릭이 곧 사용자 제스처라 **자동재생 정책이
  그때 풀린다** — 안 그러면 첫 접수가 올 때까지 소리가 나는지 알 수가 없다
- 🔴 **고른 값을 인자로 넘긴다**(`playAlertChime({volume, tone})`) — 저장을 읽게 두면
  `localStorage` 가 막힌 브라우저에서 옛 소리가 나 「눌러도 안 바뀐다」로 보인다
- 🔴 **기억하는 곳은 브라우저(`localStorage`)다.** `staff_accounts` 컬럼으로 옮기지
  말 것 — 수신 설정 화면을 안 만들기로 한 **38차 0-3 과 어긋나고**, DB 변경이 0 이던
  A장이 DB 변경을 갖게 된다. 볼륨·소리는 **그 사람이 앉은 자리의 취향**이다
- 🔴 **끄기(🔔)와 펼침(▾)은 다른 단추다** — 합치면 소리를 끄려다 창이 열린다
- 🔴 **모바일은 펼침 창을 쓰지 않는다**(이미 펼쳐진 메뉴 안이라 창이 창 위에 겹친다)
- 🔴 **저장된 값이 목록에 없으면 기본값으로 떨어진다**(조용히 안 깨진다)
- 🔴 **웹 푸시로 뜨는 윈도우·폰 알림 소리는 OS 가 정하므로 조절 대상이 아니다.**
  「푸시 소리도 여기서 고르게 하자」로 넓히지 말 것 — **만들 수 없는 것을 있는 것처럼
  그리게 된다.** 창 안에 그 안내를 한 줄 적어 뒀다
- 🔴 색은 `var(--brand-yellow)` 다 — 리터럴로 다시 적지 말 것(PR #145) ·
  🔴 `var(--pv2-yellow)` 는 `.portal-v2` 스코프 안이라 **관리자에서는 옐로가 안 나온다**

### ⑥ 화주포털 A장 — 사용자 요청으로 범위가 넓어졌다

🔴 **38차 지시서는 「화주포털은 한 줄도 건드리지 않는다」였다.** merge 직전에 사용자가
*「이 알림기능을 화주포털에도 적용할 수 있나?」* 로 물었고 **「A장만 먼저」**로 확정했다
(2026-09-16). 🔴 **지시서의 그 금지를 근거로 포털 알림을 되돌리지 말 것.**

**배선이 쉬웠던 이유 — 필요한 것이 이미 다 있었다.**

```
                관리자                          화주포털
  신호   15초 폴링 둘 + Realtime 하나      Realtime 5개 표 (이미 돌고 있었다)
  건수   counts 3종                        counts 4종 (배지가 쓰던 것)
  워커   /admin                            /customer  (PWA, 이미 있었다)
```

🟢 **새 폴링 0 · 새 구독 0.** 배지가 쓰던 `counts` 가 **늘어난 순간**만 얹었다.

```
  견적 업데이트 N건       → /customer/quotes
  배차·운송 업데이트 N건   → /customer/dispatches
  정산 업데이트 N건       → /customer/invoices
  새 공지사항 N건         → /customer/announcements
```

- 🔴 **「새 견적」이 아니라 「견적 업데이트」다.** 포털의 신호는
  `updated_at > 마지막으로 본 시각` 이라 **새로 생긴 것과 고쳐진 것을 가리지 않는다** —
  담당자가 기존 견적의 메모 한 줄만 고쳐도 뜨는 자리라 「새」로 쓰면 **거짓말이 된다.**
  공지만 `created_at` 기준이라 **「새 공지사항」이 맞다**
- 🔴 **`/customer/request`(발주 요청)를 넣지 말 것** — 담당자 조치의 결과는 전부
  「견적 확인」에 뜬다(27차 리뷰 3라운드 확정, 그래서 **배지도 안 단다**). 눌러도 볼 것이 없다
- 🔴 **`displayCounts` 가 아니라 `counts` 를 본다.** 앞엣것은 지금 보고 있는 화면의
  배지를 0으로 눌러 둔 값이라, 그것으로 재면 **견적 화면을 열어둔 사이에 도착한 견적을
  영영 못 알린다.** 배지는 눌러 두는 게 맞고(보고 있으니까) **배너는 떠야 한다** —
  목록이 스스로 다시 그려지지는 않는다
- 🔴 **종 모양은 `accountLinks` 안이다** — 사이드바와 바텀시트가 그 함수를 **같이** 쓴다.
  따로 그리면 한쪽만 고쳐진다
- 🔴 **`placement="up-left"` 신설** — 포털 사이드바 **발치**라 아래로 열면 화면 밖으로
  나간다. 🔴 **`right: auto` 를 빼지 말 것** — 기본 규칙의 `right: 0` 이 남으면 `left: 0`
  과 같이 걸려 창이 **사이드바 폭으로 짜부라진다**
- 🔴 **`counts` 타입을 `Record<string, number>` → `PortalAlertCounts` 로 조였다**
  (`strict: false` 라 느슨하면 정의처와 키가 어긋나도 `tsc` 가 못 잡는다).
  **이 PR 에서 `main` 기준 지워진 유일한 한 줄이 그것이다**
- 🟢 **`TopNav` 는 `/customer` 에서 `null`** 이라 배너가 두 번 뜨거나 소리가 두 번 나지 않는다

**코드를 나눈 방식 — 한 벌을 둘로 복사하지 않았다.**

```
  lib/alertCore.ts        소리 · 늘어난 것 고르기 · 탭 제목      ← 양쪽이 같이 쓴다
    ├ lib/adminIntakeAlert.ts   관리자 말·경로 (새 발주요청 …)
    └ lib/portalAlert.ts        포털 말·경로   (견적 업데이트 …)
```

- 🔴 **코어에는 라벨도 경로도 없다** — 한쪽 말을 넣는 순간 반대편이 남의 말을 쓰게 된다
- 🔴 **코어에 CSS·JSX 0건** — 그래서 `.portal-v2` 스코프와 관리자 화면이 서로를 안
  끌고 온다(원칙 57번 · `lib/arrivalType.ts` 와 같은 자리)
- 🔴 **소리 저장 칸은 관리자와 한 벌이다**(브라우저당 한 번만 고르면 된다)
- `AdminIntakeToast` → **`AlertToast`** · `AdminIntakeSoundMenu` → **`AlertSoundMenu`**.
  배너가 라벨을 **만들지 않고 받는다** — 🔴 `새 {label}` 처럼 **조립하지 말 것**
- 🔴 **`.aintake-*` 를 그대로 쓴다.** `.pv2-*` 사본을 만들지 말 것 — 그 토큰은
  `.portal-v2` 안에만 있어 **관리자에서는 통째로 안 걸린다**(PR #145 실측)

### ① 범위가 작업 중에 두 번 줄었다 — 그것이 이 차수의 전부다

지시서 초안(그리고 설계 v4 5장 매핑표)은 **차주 3칸 + 운송료 + 수수료 + 화물번호**를

> *"잠시만, 지금 작업은 좀더 심플하게 가자. 배차 접수중일때 24시 배차망에서 배차가
> 되면, 배차된 차주의 차주명, 전화번호, 차량번호만 복사해서 붙여넣으면 이 정보만

수수료 칸은 **수금방식이 선착불이어야** 그려진다. 넓히려면 그때 지시를 받는다.

그리고 붙여넣을 글의 모양도 줄었다.

> *"「(차주명) (차량번호) (연락처)」 앞으로 이정도 정보만 붙여 넣겠다."*
> 🔴 **원문에는 실제 차주 이름·차량번호·연락처가 들어 있었다 — 이 저장소는 public 이라
> 여기에도 옮겨 적지 않았다.** 모양만 남긴 것이고, 잃은 것은 없다(⑦ 참고)

🔴 **그래서 목록 행 40열 탭 파서를 통째로 버리고 「한 줄 · 토큰 셋」 파서로 다시 썼다.**
설계 v4 의 「라벨로 가른다」가 **성립하지 않는 입력**이 된 것이다(라벨 줄이 없다).
🔴 **40열 탭 파서를 되살리지 말 것** — 아래 ③ 이 그 이유다.

### ② 왜 「접수중의 외부 배정 분기」 안인가 — 다른 자리가 없다

🔴 **차주 이름·연락처·차량번호 입력칸은 `dispatch_status === "접수중"` 의
`assignment_type === "external"` 분기 안에만 있다.** 배차확정 이후에는 세 값이
**읽기 전용**이라 채울 자리 자체가 없다.

```
                          접수중    배차확정 이후
   차주 3칸 입력            ✅        ❌ 읽기 전용
   배차확정 버튼            ✅        ❌
   차주 기본운임 계산기      ❌        ✅          ← 렌더 조건이 정확히 반대다
```

🔴 **「차주 기본운임 계산기 옆에 두자」가 성립하지 않는 이유가 이것이다** — 그 계산기는
`!== "접수중"` 일 때만 그려진다. 착수 전에 사용자에게 자리를 물었을 때 **내가 계산기만
근거로 들어 질문이 한쪽으로 기울었고**, 그 사실을 사용자에게 알린 뒤 다시 물어 확정했다.
🔴 **「어디에 둘까」를 묻기 전에 그 칸의 렌더 조건부터 읽을 것.**

### ③ 라벨이 없으니 순서가 아니라 「모양」으로 가른다

붙여넣는 글에 라벨이 없다. 사람이 손으로 옮겨 적는 값이라 **순서도 믿을 수 없다.**
그래서 토큰마다 정규식으로 무엇인지 판정한다(`lib/wecarry24Paste.ts`, 의존성 0).

```
  연락처    숫자만 남겨 10~11자리이고 0으로 시작
            🔴 대표번호(1661-2403 같은 8자리)는 안 걸린다 — 그래서 자릿수를 넓히지 말 것
  차량번호  /^[가-힣]{0,2}\d{2,3}[가-힣]\d{4}$/
            신형 `12가3456` · 영업용 `12바3456` · 지역 있는 `서울12가3456` · `경기12자3456`
  이름      위 둘이 아닌 첫 토큰
```

🟢 `010-1234-5678 홍길동 서울12가3456` 처럼 순서를 바꿔 적어도 같은 결과가 나온다.
🔴 **구분자는 `/\s+/` 다** — 탭·줄바꿈·공백을 똑같이 본다(창에서 드래그하면 탭이 섞인다).
🔴 **토큰이 8개를 넘으면 거절한다** — 목록 행을 통째로 붙여넣으면 값이 40개라
**전화번호가 여럿**이고, 잘못 집으면 **엉뚱한 사람에게 배차 문자가 나간다.**
그래서 막고 「이름 차량번호 연락처 세 가지만」이라고 안내한다.

### ④ 채우기만 하고 저장하지 않는다

🔴 **저장은 기존 「배차확정」 버튼이 한다.** 새 저장 경로를 만들면 그 버튼이 하는 검사
(선착불 지급조건 확인 등)와 낙관적 잠금을 **우회하게 된다.** 그래서 채운 뒤 그 자리에
**「아직 저장되지 않았습니다 — … 배차확정을 눌러 주세요」**를 적는다(원칙 33번 — 오류·

- 🔴 **읽지 못한 토큰을 조용히 버리지 않는다**(원칙 55번) — `unknownTokens` 로 돌려 화면에 나열한다

- 🔴 **서버에 보내지도 저장하지도 않는다** — 브라우저에서 갈라 입력칸에 넣고 버린다.

### ③ 🟢 v4 7장 「착수 전 확인」 실측 — 넷

**ⓐ 지시서는 이 값을 전제로 쓴다.** 코드로 잴 수 없는 것(붙여넣은 텍스트의 실제 모양)은 샘플

**ⓐ-1 `dispatches.external_order_no` 가 정말 없는가 → 🔴 없다.**

```bash

```

코드·마이그레이션 양쪽에 한 줄도 없다. v3 조사 시점 그대로이고 **신설이 맞다**(24시콜 화물번호가
연결 열쇠이므로 unique).

**ⓐ-2 `brokerage_fee` 를 채우는 자리와 부가세 토글의 관계 → 🔴 그 칸에는 토글이 없다.**

자리는 배차 상세(`app/admin/dispatches/[id]/page.tsx`)의 **「정산 정보」 카드 → 「선착불 정산 정보」
블록** 안이고, **`settlementValue.collection_method === "driver_direct"` 일 때만 그려진다.**

라벨이 **「주선수수료(부가세 포함가, 원)」**로 못박혀 있고, 아래 캡션이 `toSupplyAmount()`(÷1.1)로
공급가액·부가세를 보여줄 뿐이다. `VatBasisSelect`(부가세 구분 토글)는 **화주 청구금액**과
**차주 지급운임** 두 칸에만 붙는다.

```
  화주 청구금액(원)            + VatBasisSelect   ← customer_charge_vat_included
  차주 지급운임(원)            + VatBasisSelect   ← driver_vat_included
  전체 운송료(원)              (선착불 블록)
  차주 직접수금액(공급가액, 원) (선착불 블록)
  주선수수료(부가세 포함가, 원) 🔴 토글 없음 — 포함가 고정
```

🔴 **그래서 ⓐ 가 24시콜 「합계」를 `customer_charge` 에 넣을 때는 `customer_charge_vat_included` 를
함께 정해야 한다** — 기본값이 `false`(부가세 별도)다. 이것이 v3 §5 대조 블록의 **미결 「부가세
기준」과 같은 자리**이고, 🔴 **v12 가 라벨을 「공급가액 (부가세 별도)」로 통일했다고 해서 이 미결이
닫힌 것은 아니다**(라벨과 `brokerage_fee` 기입 기준은 다른 축이다).

🔴 **선착불이 아니면 그 블록 자체가 안 그려진다** — 24시콜 건은 **수금방식이 먼저 선착불이어야**
`brokerage_fee` 칸이 화면에 나타난다. ⓐ 가 값을 채우려면 수금방식부터 세워야 한다는 뜻이다.
⚠️ 화면 주석의 실측 — **DB 에 5,000(포함가)과 4,545(공급가액)가 섞여 들어가 있다**(35차가 라벨을

**ⓐ-3 붙여넣기 칸을 넣을 자리 → 🔴 저장 경로가 셋이라는 것이 핵심이다.**

v4 가 *「줄 번호가 아니라 계산 흐름으로 찾을 것」*이라 한 자리다. 흐름으로 보면 카드 순서는
**배정방식·배차확정 → 상차지·하차지 담당자 → 정산 정보 → 클레임 → 현장 추가비 → POD → 문자 발송**
이고, 24시콜 한 건의 값이 **서로 다른 세 state 와 세 저장 버튼**으로 흩어진다:

```

  화주 청구금액 · 부가세 구분 · 전체 운송료 · 주선수수료
      → editForm      → 저장은 **handleSave()**(맨 아래 「변경사항 저장」)

      → payoutCalcForm → 저장은 **handlePayoutCalcSave()**(접이식 안의 전용 버튼)
```

🔴 **붙여넣기 칸 하나가 두 카드에 걸쳐 값을 채운다.** 자리는 **배정방식 카드 위**가 자연스럽다
(맨 위에서 붙여넣고 아래로 내려가며 눈으로 확인). 🔴 **「한 번 붙여넣으면 저장까지 끝난다」로
설계하지 말 것** — 저장 버튼이 셋이라 어느 하나만 누르면 나머지가 조용히 안 들어간다. ⓐ 지시서가
**이 셋을 명시적으로 다뤄야 한다.**
🔴 **줄 번호로 찾지 말 것** — 35차가 이 화면을 크게 고쳤고 지금 **2,525줄**이다.

**⑥-3 🟢 부가세 기준 미결이 닫혔다 — v3 부터 열려 있던 것이다**

캡처의 두 값이 서로를 증명한다:

```
  합계 80,000 × 1.1 = 88,000
  88,000 − 산재보험료 차주분 350 = 87,650   ← 화면의 「송금할운임(부가세포함)」과 정확히 일치
```

🔴 **부가세가 가산됐으므로 합계 80,000 이 공급가액이다.** 따라서 그 안의 **운송료 65,000 과
수수료 15,000 도 둘 다 부가세 별도**다.
🔴 **그런데 35차는 `brokerage_fee` 를 「부가세 포함가 기입」으로 확정했다**(사용자 6·9번).
그대로 15,000 을 넣으면 포함가로 읽혀 공급가액이 13,636 이 되고 **마진이 10% 적게 잡힌다** —
ⓐ 는 **15,000 × 1.1 = 16,500** 을 넣거나 그 칸의 기준을 바꿔야 한다. **ⓐ 지시서가 정할 것.**

**⑥-4 🟢 v3 §1-9 의 불일치도 풀렸다**

*「차주 실수령을 운송료 65,000 이라 하는데 송금할 운임은 87,650 이라 서로 안 맞는다」*고
적혀 있던 것 — **87,650 은 화주가 차주에게 줄 총액**(합계 부가세포함 − 차주 산재)이고
**65,000 은 그중 차주 몫**이다. 차주가 받아서 수수료를 낸다.
🟢 **35차 선착불 모델**(받을 돈 = 주선수수료 · 줄 돈 = 0 · 수수료는 차주가 낸다)**과 맞는다.**

**⑥-5 🔴 산재 기준액이 서로 다르다 — 새로 드러난 것**

같은 요율(필요경비공제 49.9% · 산재 1.76% · 절반 부담)로 검산했다:

```
  합계 80,000 기준   floor(80,000 × 0.501) = 40,080  →  floor(40,080 × 0.0088) = 352  →  350
  운송료 65,000 기준  floor(65,000 × 0.501) = 32,565  →  floor(32,565 × 0.0088) = 286
```

🔴 **24시콜은 합계(80,000) 기준이고 10원 단위로 절사한다**(화면값 350 과 맞는다).
🔴 **우리 `calcSettlement()` 는 `driverBaseFare`(65,000) 기준이라 286 이 나온다** — 같은 건의
산재가 **350 vs 286** 으로 갈린다. ⓐ 지시서가 **「가져온 값을 그대로 둘지 우리 식으로 다시
계산할지」**를 정해야 한다. 🔴 **말없이 재계산하면 24시콜 정산서와 대조가 어긋난다** —
v12 C장 반올림이 만든 것과 **같은 자리**다.

**⑥-3b 🔴 사용자 확정 셋 — 위 ⑥-3·⑥-5 의 결론이 바뀌었다**(2026-09-16)

```
  1  "선착불 오더에서 적힌 수수료는 부가세 포함가이다. 그래서 15,000원(부가세포함가)로
     적는게 맞다."
  2  "산재는 일단 고려하지 말자."
  3  "접수중 배차는 일단 다루지 말자."
```

🔴 **1번은 내 제안을 뒤집은 것이다.** 나는 ⑥-3 에서 *「합계 80,000 이 공급가액이니 수수료
15,000 도 공급가액이고, 35차가 포함가 기입으로 정했으니 ⓐ 는 16,500 을 넣어야 한다」*고
적었는데, 사용자가 **실무 기준으로 15,000 이 이미 포함가**라고 확정했다.
🟢 **그래서 변환 없이 그대로 넣는다** — 35차 확정과 그대로 맞물린다.
🔴 **「×1.1 해서 16,500」을 되살리지 말 것.**

⚠️ **다만 산술은 여전히 갈려 있고 그것을 지운 것이 아니다.** 24시콜 화면은
`합계 80,000 × 1.1 = 88,000` 으로 계산하므로 **화면상 80,000 이 공급가액**이다. 그 안의
15,000 도 화면 기준으로는 공급가액처럼 읽힌다. 🔴 **그래도 실무 기준이 이긴다** — 합계·
송금액은 **화주↔차주 운임 흐름**의 계산이고, 수수료는 그와 별개로 **차주가 위캐리에 내는
돈**이다(35차 선착불 모델). ⚠️ **두 시스템이 같은 건의 수수료 공급가액을 다르게 본다**
(24시콜 15,000 / 우리 15,000÷1.1 = 13,636) — **세금계산서 대조에서 어긋날 수 있다.**
어긋나는 줄이 나오면 이 문단을 볼 것.

🔴 **2번 — 산재는 범위 밖이다.** ⓐ 는 `industrial_insurance_*` 를 건드리지 않는다.
⚠️ **닫힌 것이 아니라 미뤄둔 것**이고, ⑥-5 의 실측(24시콜 350 / 우리 286)은 그대로 유효하다.

**⑥-3c 🔴 「캡처만으로 되는가」 — 두 축을 가를 것**

### ⑤ C장 — 소계 반올림 + 견적서 가산 한 줄 (PR #158 · 코드 · DB 0)

**A·B 가 들어간 뒤에도 만원을 깨뜨리는 것이 넷 남는다** — 왕복/편도(유일하게 남은 요율) ·
대기료 · 경유지비(각 13행 중 4행이 5,000 단위) · 혼적 할인(율 방식).
🔴 **그 표들을 고쳐서 반올림을 없애려 하지 말 것** — 담당자가 정한 값이고 사용자가 현행 유지로
확정했다. **반올림이 그것을 흡수하는 것이 `lib/roundToUnit.ts` 의 존재 이유다.**

```
  surchargeTotal = roundToUnit(pctAmount + flatTotal + waitingExtra + waypointExtra, 차급)
  rawFinal       = max(base + surchargeTotal, 0)          ← 격자값
  혼적할인        = roundToUnit(rawFinal − applyMixedDiscount(rawFinal, …), 차급)
  final          = max(rawFinal − 혼적할인, 0)             ← 격자값
```

🔴 **개별 가산 줄이 아니라 소계에 건다** — 줄마다 반올림하면 작은 요율 줄이 통째로 올라가 과다 청구다.
🔴 **대기료·경유지비를 소계 밖으로 빼지 말 것.**

빠진다(35차 `lib/marginCalc.ts` 와 같은 결). 격자 상수는 `lib/constants.ts` 한 곳이다.

→ `customer_locations.company_name` 신설.
🔴 **`location_name` 을 없애지 않았다** — 별칭(「본사 창고」)은 상호와 다른 것이고
20차가 같은 자리에서 *「`name` 을 새로 만들지 말 것」* 이라고 못박았다. 상호만 제 칸으로 뺐다.

🔴 **「기존 정보들을 건드려서라도」를 「덮어쓴다」가 아니라 「옮겨 적는다」로 읽었다**
(지시와 다르게 판단한 것). 백필은 `location_name` 이 **주소와 다를 때만** 상호로 보고,
옮긴 뒤에도 `location_name` 을 **지우지 않는다.** 주소와 같으면 그건 「이름이 없어서 주소를
넣어둔 것」이라 상호가 아니다(폼의 `|| form.origin.trim()` 갈래가 그것이다).
지우면 되돌릴 길이 없고, 별칭으로 쓰던 화주의 카드 제목이 통째로 바뀐다. 🔴 **되돌리지 말 것.**

🟢 대신 카드 제목이 **별칭 → 상호 → 주소** 순으로 골라진다(`locLabel()`) — 보이는 것은
그대로이고 상호만 제 칸에서도 읽힌다. 🔴 **상호를 맨 앞에 두지 말 것**(별칭을 일부러 적은
화주는 그것으로 구분한다). 제목이 이미 상호면 아래 「상호」 줄을 **두 번 그리지 않는다.**

⚠️ **운영 실측(apply 로그)** — 배송지 **14건** 중 상호 **2** · 별칭 **2** · 담당자 **2** ·
상세주소 **0**. 옮겨 적힌 것은 **2건**이고 재실행하면 **0건**이다(멱등).

### ③ 🔴 관리자 화주 상세가 포털의 절반만 읽고 있었다

| | 전 | 후 |
|---|---|---|
| 읽는 칸 | `location_name`·`address`·`location_type`·`sido`·`sigungu` | **+ `company_name`·`address_detail`·`contact_name`·`contact_phone`·`notes`** |
| 쓰는 칸 | `address`(상세주소를 **합쳐서**)·`location_type`·시도·시군구 | 포털과 **같은 모양** — 상세주소를 나눠 저장 |
| 수정 | 주소 한 칸 인라인(`onBlur` 저장) | 전체 항목 폼(상호·별칭·주소·상세주소·담당자·연락처·특이사항) |

🔴 **상세주소를 주소에 합치지 말 것** — `fullOrigin` 관례(원칙 37번)는 상세주소 칸이
**없는** 표(`quotes`·`orders`)에 적용되는 것이다. 여기서 합치면 같은 표에 두 가지 모양이
섞이고, 포털에서 불러올 때 상세주소만 따로 채울 수 없다.

🔴 **칸을 도로 줄이지 말 것** — 줄이면 화주가 포털에서 적은 담당자·특이사항이 담당자
화면에서 다시 사라진다.

🔴 **견적관리도 같은 칸을 읽고 쓴다** — 저장된 주소 칩을 누르면 주소뿐 아니라
**상호·담당자·상세주소까지** 채워지고(`applySavedLocation()`), 견적에서 저장한 배송지도
포털과 같은 모양으로 남는다. 칩 이름도 주소가 아니라 **별칭/상호**를 보여준다
(`savedLocLabel()`). 🔴 거기서도 `fullOrigin` 을 되돌리지 말 것.

⚠️ **`.form-grid` 를 쓰지 말 것** — 그 클래스는 `padding: 22px` 를 가진 **카드 본문용**이라
주소검색·특이사항 칸과 좌우가 어긋난다. `.field` 만 쓰고 격자는 직접 준다(실제로 한 번
쓰고 렌더에서 확인해 고쳤다).

🔴 액션 실패는 **버튼 바로 아래**(원칙 33번, `locFormError`) — 페이지 맨 위 `error` 를
재사용하면 이미 불러온 상세 화면이 통째로 오류 문구로 덮인다(그 화면이 원칙 33번의
발원지다).

### ④ 조회기간 — 정의처 하나

`components/pv2/Pv2PeriodFilter.tsx` 신설. **견적 확인 · 배차/운송 조회 · 정산/결제 내역
세 화면**이 같이 쓴다. 세 화면에 각자 있던 `PERIOD_CHIPS` 배열을 이것으로 대체했다.

🔴 **화면마다 따로 만들지 말 것** — 「견적은 되는데 정산은 안 되는」 상태가 되고 프리셋
이름도 서서히 갈린다.
🔴 **네이티브 `<input type="date">` 금지**(원칙 57번) — `Pv2DatePicker`.
🔴 **프리셋 계산은 `getDateRange()` 를 그대로 쓴다** — 관리자와 「이번주」의 뜻이 같아야 한다.
🔴 **끝날은 그 날을 포함한다** — `to` 를 그대로 비교하면 그 날 00:00 이후가 통째로 빠진다.
한쪽만 골라도 동작한다(시작만 고르면 「그 날부터 지금까지」).

🔴 **`.pv2-period-custom .pv2-period-date` 는 두 클래스라야 한다**(원칙 58번) —
`.pv2-selectwrap` 의 `width: 100%` 를 못 이기면 **데스크탑에서 날짜 칸 둘이 세로로
쌓인다.** 실측으로 잡았다(1360px 에서 각 **1160px**). 모바일 규칙만 두 클래스였고
데스크탑은 `min-width` 뿐이라 안 걸렸다.

### ⑤ 묶음 목록 — 🔴 가독성 문제의 원인은 정보량이 아니라 무게였다

1차에는 오른쪽에 굵은 총액 + 회색 한 줄(`3건 · 공급가 622,000원 · 기한 …`)을 뒀는데
**「가독성이 떨어진다」** 는 지적을 받았다. 다시 재 보니 **정보량이 아니라 무게**였다 —
「확정」·「세금계산서 미발행」이 회사명·정산월과 **같은 무게의 평범한 글자**라 줄 전체가
한 덩어리로 읽혔고, 금액도 회사명과 같은 13.5px 이라 어느 것이 금액인지 구분이 안 됐다.

| | 1차 | 리뷰 반영 |
|---|---|---|
| 상태 | 평범한 글자 | **`Chip` 배지** |
| 건수 | 오른쪽 회색 줄 | **정산월 옆** 「2026-09 정산 · 3건」 |
| 금액 | 13.5px | **15.5px 굵게**(줄에서 가장 큰 글자) |
| 내역 줄 | 11.5px | 12px |
| 기한 | 「기한 2026-09-30」 | **「납부기한 2026-09-30」**, 연체면 빨강·굵게 |

🔴 **색은 셋뿐이다** — 회색 = 진행 중 · 파랑 = 확정 · 빨강 = 조치 필요. 종류가 늘면 색이
뜻을 잃는다.
🔴 **「기한」이 아니라 「납부기한」이다** — 정산 마감일(전 화주 월말 고정, 36차)과 헷갈린다.
이건 **화주가 입금할 날**이다.
🔴 **오른쪽은 두 줄이 상한이다** — 더 늘리면 여기 둔 의미가 없다.
🔴 **확정된 묶음의 금액은 얼려진 값**(`supply_amount`/`total_amount`)이고 작성 중은 담긴
항목의 합이다. **섞지 말 것** — 항목에서 세는 것은 **건수뿐**이다.
🔴 집계 대상이 작성중 묶음만이 아니라 **목록의 모든 묶음**이다(펼치기 전에 건수를 보여줘야
하므로). `draftTotalByBatchId` → **`aggByBatchId`**.

### ⑥ 「합계」 → 「공급가액」

화주포털 견적 펼침의 「합계 (부가세 별도)」를 **「공급가액 (부가세 별도)」**로.
바로 아래에 「총 견적금액」이 오므로 「합계」라고 적으면 **어느 쪽이 합계인지 헷갈린다.**

🟢 견적서 상세(`/customer/quotes/[id]`)와 엑셀(`lib/quoteExcel.ts`)이 **이미 「공급가액」**
이라 이것으로 **세 곳이 맞았다**(27차 「금액 줄이 줄 단위로 같아야 한다」).
🔴 **그 줄에 부가세를 더하지 말 것은 그대로다**(27차) — 라벨만 바꿨고, 부가세 포함가는
**새 줄**(「총 견적금액 (부가세 포함)」)이다.

### ⑦ 품목 필수

화면 표시(`field-required` + `RequiredMark` → 「품목 \*」)와 **제출 직전 검사가 한 벌이다.**
한쪽만 두면 표시만 있고 안 막히거나, 막히는데 왜인지 모르게 된다.
🟢 검사 자리는 「거리」 뒤·「거리 자동계산」 앞이다(브라우저 시험으로 순서까지 확인했다).
