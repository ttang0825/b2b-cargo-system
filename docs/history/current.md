### ② 🔴 무엇이 어긋나 있었나 — 상호가 별칭 칸을 쓰고 있었다

지시 ②·③ 의 뿌리는 하나였다. 화주포털 발주 폼이 **상호를 `location_name` 에 밀어 넣고
있었다**:

```ts
location_name: form.origin_company_name.trim() || form.origin.trim(),
```

`quotes`·`orders`·`portal_order_requests` 에는 상호가 **제 컬럼**으로 있는데
(`origin_company_name`/`destination_company_name`) `customer_locations` 에만 없었다.
그래서 ① 상호와 배송지 **별칭이 한 칸을 다퉜고** ② 관리자 화주 상세는 그 칸을
「주소 이름」으로만 읽어 **상호가 어디에도 안 보였다.**

→ `customer_locations.company_name` 신설.
🔴 **`location_name` 을 없애지 않았다** — 별칭(「본사 창고」)은 상호와 다른 것이고
20차가 같은 자리에서 *「`name` 을 새로 만들지 말 것」* 이라고 못박았다. 상호만 제 칸으로 뺐다.

🔴 **「기존 정보들을 건드려서라도」를 「덮어쓴다」가 아니라 「옮겨 적는다」로 읽었다**
(지시와 다르게 판단한 것). 백필은 `location_name` 이 **주소와 다를 때만** 상호로 보고,
옮긴 뒤에도 `location_name` 을 **지우지 않는다.** 주소와 같으면 그건 「이름이 없어서 주소를
넣어둔 것」이라 상호가 아니다(폼의 `|| form.origin.trim()` 갈래가 그것이다).
지우면 되돌릴 길이 없고, 별칭으로 쓰던 화주의 카드 제목이 통째로 바뀐다. 🔴 **되돌리지 말 것.**

🟢 대신 카드 제목이 **별칭 → 상호 → 주소** 순으로 골라진다(`locLabel()`) — 보이는 것은
그대로이고 상호만 제 칸에서도 읽힌다. 🔴 **상호를 맨 앞에 두지 말 것**(별칭을 일부러 적은
화주는 그것으로 구분한다). 제목이 이미 상호면 아래 「상호」 줄을 **두 번 그리지 않는다.**

⚠️ **운영 실측(apply 로그)** — 배송지 **14건** 중 상호 **2** · 별칭 **2** · 담당자 **2** ·
상세주소 **0**. 옮겨 적힌 것은 **2건**이고 재실행하면 **0건**이다(멱등).

### ⑤ 묶음 목록 — 🔴 가독성 문제의 원인은 정보량이 아니라 무게였다

1차에는 오른쪽에 굵은 총액 + 회색 한 줄(`3건 · 공급가 622,000원 · 기한 …`)을 뒀는데
**「가독성이 떨어진다」** 는 지적을 받았다. 다시 재 보니 **정보량이 아니라 무게**였다 —
「확정」·「세금계산서 미발행」이 회사명·정산월과 **같은 무게의 평범한 글자**라 줄 전체가
한 덩어리로 읽혔고, 금액도 회사명과 같은 13.5px 이라 어느 것이 금액인지 구분이 안 됐다.

| | 1차 | 리뷰 반영 |
|---|---|---|
| 상태 | 평범한 글자 | **`Chip` 배지** |
| 건수 | 오른쪽 회색 줄 | **정산월 옆** 「2026-09 정산 · 3건」 |
| 금액 | 13.5px | **15.5px 굵게**(줄에서 가장 큰 글자) |
| 내역 줄 | 11.5px | 12px |
| 기한 | 「기한 2026-09-30」 | **「납부기한 2026-09-30」**, 연체면 빨강·굵게 |

🔴 **색은 셋뿐이다** — 회색 = 진행 중 · 파랑 = 확정 · 빨강 = 조치 필요. 종류가 늘면 색이
뜻을 잃는다.
🔴 **「기한」이 아니라 「납부기한」이다** — 정산 마감일(전 화주 월말 고정, 36차)과 헷갈린다.
이건 **화주가 입금할 날**이다.
🔴 **오른쪽은 두 줄이 상한이다** — 더 늘리면 여기 둔 의미가 없다.
🔴 **확정된 묶음의 금액은 얼려진 값**(`supply_amount`/`total_amount`)이고 작성 중은 담긴
항목의 합이다. **섞지 말 것** — 항목에서 세는 것은 **건수뿐**이다.
🔴 집계 대상이 작성중 묶음만이 아니라 **목록의 모든 묶음**이다(펼치기 전에 건수를 보여줘야

### 🔴 ⓪ 가장 중요한 것 — 「담기가 안 된다」의 진짜 원인은 **DB 함수가 예외로 죽는 것**이었다

신고를 **세 번** 받고서야 찾았다. 앞의 세 라운드는 **화면 쪽 원인만** 고쳤다.

```
ERROR:  cannot cast type record to invoices
CONTEXT: PL/pgSQL function add_item_to_billing_batch(uuid,uuid) line 52 at IF
```

```sql
declare
  v_invoice record;                                    -- ← 여기
...
  if not is_billing_batch_candidate(v_invoice) then    -- ← 여기서 폭발
```

`is_billing_batch_candidate(p_invoice invoices)` 는 **`invoices` 행 타입**을 받는데
`record` 로 선언한 변수는 그 타입으로 캐스트되지 않는다. **관문을 전부 통과한 건이
마지막 줄에서 죽는다** — 거절 사유가 아니라 **에러**가 올라오므로 「담기」·「모두
담기」·운송완료 자동 담기가 **전부, 언제나** 실패했다.

🔴 **고친 것은 선언 한 줄이다**(`record` → `invoices%rowtype`). 나머지 본문은 운영
DB 에서 그대로 떠온 것이고 **한 글자도 안 바꿨다**(관문 순서·사유 이름·스냅샷 계산·
`unique_violation` 처리 전부 동일). 🔴 **이 기회에 다른 것을 같이 고치지 말 것** —
돈이 걸린 경로다.

🔴 **마이그레이션에 「고친 함수를 실제로 불러보고 되돌리는 단언」을 넣었다.** 여전히
못 담으면 `raise exception` 으로 **함수 교체까지 통째로 롤백**되고 워크플로가 멈춘다.
「배포했는데 여전히 안 담긴다」를 또 겪지 않기 위해서다. 🔴 **이 단언을 빼지 말 것.**

🟢 **곁다리 — 묶음 DB 함수가 처음으로 저장소에 들어왔다.** 12개가 14차 산출물이라
저장소 밖에 있었고(마이그레이션 자동화 47차보다 먼저), **그것이 원인 찾기를 어렵게
만든 바로 그 이유**였다.

### ① 운송완료 → 묶음 자동 생성

운송완료하면 **정산 건은 자동**인데 **묶음은 손으로** 만들어야 했다(실측: 월정산 2건 중
묶음에 담긴 것 **0건**). 이제 정산 건이 만들어지는 순간 그 화주·정산월의 묶음에
자동으로 담기고, 묶음이 없으면 작성 중 묶음이 새로 만들어진다.

🔴 **호출은 `lib/autoCreateInvoice.ts` 안에 있다 — 화면으로 옮기지 말 것.** 이 함수를
부르는 곳이 **배차 상세·배차 목록 둘**이고 24시콜 ⓒ 가 셋째가 된다. 화면에 두면 한쪽만
고쳐져 「목록에서 완료하면 묶음이 안 생긴다」가 된다(원칙 53번).

🔴 **fire-and-forget 이다**(`await` 금지) — 묶음 API 가 느리거나 죽으면 **배차 상태
변경 자체가 멈춘다.**

🔴 **조건 판정은 서버가 한다**(`app/api/admin/billing-batches/auto-attach`) —
클라이언트에서 미리 거르면 판정이 두 곳이 된다(원칙 44번과 같은 결).

🔴 **확정·해제된 묶음에는 자동으로 담지 않는다** — 확정 금액이 담당자도 모르게
흔들리거나, 일부러 해제한 묶음이 되살아나면 안 된다. 그때는 화면이 「보충 묶음」으로 안내한다.

🔴 **DB 함수를 새로 만들지 않았다** — 기존 12개 중 둘(`create_billing_batch` ·

⚠️ **`draft_already_exists` 는 실패가 아니다** — 운송완료 두 건이 거의 동시에 처리되면

돈은 0원이다.** 🔴 「`receivable_amount` 를 그대로 더하면 되지 않나」로 되돌리지 말 것.

🔴 **`customer_charge_total` 폴백을 지우지 말 것** — 35차 이전 옛 건에는
`receivable_amount` 가 없어서, 지우면 그 건들의 미수금이 통째로 0이 된다.

### ③ C장 리뷰 1라운드 — 식을 고쳐도 화면이 안 바뀐다

사용자 신고: *"여전히 활성화주 목록에서는 미수금이 뜬다."*

🔴 **내가 고친 것은 계산식이었고, 그것만으로는 화면이 안 바뀐다.**
`companies.outstanding_amount` 는 **저장 시점 스냅샷**이고 다시 쓰이는 경로가
**둘뿐**이다 — ① 새 정산 건 등록 ② 정산 상세에서 **입금완료 체크가 바뀔 때**.
신고된 화주는 **선착불이라 앞으로도 입금완료를 누를 일이 없어서**(받을 것이 없으니까)
갱신 경로가 영영 안 돌고, 먼저 잘못 적힌 180,000 이 그대로 남아 있었다.

🟢 **고친 방법은 「표시 시점에 다시 세기」다** — 35차가 마진에서 쓴 것과 같은 수법
(*"표시 시점 계산이라 옛 건도 자동으로 맞는다"*). `customerOutstandingByCompany()` 신설.

```
  app/admin/customers/page.tsx      활성 화주 목록 — 신고된 자리
  app/admin/companies/[id]/page.tsx 화주 상세 「실적」 — **같은 값을 그리던 둘째 자리**
```

🔴 **`won(c.outstanding_amount)` 로 되돌리면 이 신고가 그대로 돌아온다.**
🔴 **목록만 고치고 상세를 두면 두 화면이 서로 다른 금액을 말한다** — 표시를 고칠 때는
그 값을 그리는 화면을 **전수로 훑을 것**(33차 정기계약 배지에서 겪은 것과 같은 자리).
🔴 **옛 값을 SQL 로 일괄 수정해서 때우지 않았다** — 한 번 맞춰도 같은 방식으로 또
어긋난다. 고쳐야 하는 것은 **값이 아니라 출처**다.
🟢 저장 경로는 그대로 뒀다(식이 맞아졌으므로 저장값도 점점 맞아 간다).

### ④ D장 — 견적관리 하차 = 상차 +30분

견적관리는 **거리기반(100km당 1h · 2~5h)**이라 **10km 건에도 최소 2시간**이 강제됐고,
같은 화물을 포털에서 넣을 때(+30분)와 **화면마다 답이 달랐다.**

🔴 **정의처는 `lib/dropoffGap.ts` 하나이고 세 화면이 쓴다**(견적 등록 · 견적 수정 ·
화주포털 발주요청). 두 파일에 각자 복사돼 있던 `calcMinGapHours()` 는 없앴다 —
🔴 **되살리지 말 것.**
🔴 막는 곳은 화면마다 **둘**이다 — 입력창 하한 + **제출 직전 검사**(하한이 정해지기
전에 하차를 먼저 골라 두면 입력창만으로는 안 막힌다).
🟢 **화주포털은 동작 무변경**(같은 30분) — 지역 상수를 정의처로 옮긴 것뿐이다.

원칙 6번을 같은 커밋에서 다시 썼다 — **두 군데 낡아 있었다**:

```
  견적 관리    「거리기반 2~5h」  →  상차 +30분 (이번에 바꿈)
  발주요청     「고정 2시간」     →  30분 (25차 PR #103 부터 이미 그랬다)
  운송오더     고정 2시간        →  🟢 안 바꿨다
```

### ⑤ E장 — 견적서 「조정」 줄

담당자가 「최종금액 직접 입력」으로 금액을 고치면 `final_amount` 만 바뀌고 항목 줄은
그대로라, **화주가 받은 견적서에서 더해도 합계가 안 나왔다.**

🔴 **기본운임을 덮어쓰지 않고 줄을 하나 더한다**(사용자 확정) — 덮어쓰면 그 값이
**운임기준표 산출값이라는 사실이 사라져** 「왜 이 거리에 이 금액인가」를 되짚을 수 없다.

🔴 **지시서의 식이 틀렸다.** 지시서는 `기본운임 + 가산 − 혼적할인` 이라 했는데,
견적서가 실제로 그리는 줄은 `quote_items`(가산)와 `discount_amount`(할인)이고
**혼적할인은 이미 `quote_items` 안에 음수 행으로 들어 있다.** 따로 빼면 **두 번 빠진다.**

```
  조정 = final_amount − (base_fare + Σ quote_items.amount − discount_amount)
```

🔴 **커밋을 둘로 나눴다** — 정의처만 만든 커밋 직후 **조정 0 견적의 출력이 한 글자도
안 달라지는 것**이 회귀 0 의 근거다(diff 순수 추가 +100 / −0).
🔴 **`shouldShowAdjustment` 가드를 빼지 말 것** — 조정 0 견적에 `조정 0원` 줄이 생긴다.
🔴 **`quote_items` 조회 전에 계산하지 말 것** — 빈 배열이면 **가산액만큼이 통째로
「조정」**으로 보인다.
🔴 **엑셀만 부호를 문자로 안 쓴다** — 금액이 숫자 타입이라야 받는 쪽에서 SUM 검산이
된다(원칙 8번). 값 자체를 음수로 넣는다.

⚠️ **안 고친 불일치 하나** — 할인 줄이 PDF·엑셀에만 있고 두 상세 화면에는 없다.
`discount_amount` 가 전 건 0 이라 지금은 잠복 상태이고, 누가 할인을 넣는 순간
화면과 PDF 가 갈린다. **E장 범위 밖이라 안 건드렸다.**

### ⑥ 리뷰 2라운드 — 계산창이 상단메뉴에 가린다

사용자 신고: *"견적관리에서 스크롤할때 자동계산결과창이 상단메뉴에 일부 가려지게
되는데, 가려지면 안된다."*

🔴 **PR #150 이 상단바를 `sticky` 로 만들면서 생긴 자리다.** 계산창은 34차에
`top: 20` 으로 만들어졌는데 그때는 헤더가 같이 스크롤돼 사라졌다.

```
  실측(Chromium)   헤더 79px(데스크탑) · 71px(≤700px)
                   계산창 top 20px  →  **59px 이 헤더 뒤로 들어감**
  고친 뒤          헤더 bottom 79 · 계산창 top 99 · 간격 20px (겹침 0)
```

🔴 **`--admin-topnav-h` 를 신설했다**(globals.css) — `top: calc(var(--admin-topnav-h) + 20px)`.
**새로 `sticky` 를 쓰는 곳은 이 변수를 더할 것.** 숫자를 화면마다 적으면 헤더 여백이
바뀔 때 어디가 가려지는지 아무도 모른다.
🔴 **`.top-nav-inner` 의 padding 이나 로고 크기를 바꾸면 이 값도 다시 잴 것.**
🟢 **관리자에서 `sticky` 를 쓰는 곳은 이 계산창 하나뿐임을 확인했다** — 나머지 네 곳은
공개 화면·화주포털이라 이 상단바가 없다.
⚠️ 모바일 계산창은 `.drag-panel`(`position: fixed`)이라 이 변수를 쓰지 않는다.

### ⑦ 리뷰 2라운드 — 일정에 「지금 · 당착 · 내착」

사용자 신고: *"일정에서 발주요청과 마찬가지로 지금, 당착, 내착 등의 옵션이 있어야 한다."*

🔴 **공용 `DateTimePicker` 에 opt-in prop 으로 넣었다 — 기본값이 전부 꺼짐이다.**
같은 부품을 운송오더 2화면·랜딩 폼이 쓰는데 **새 prop 을 주는 곳은 견적 등록·수정
두 화면뿐**이고, 그것이 무회귀의 근거다. 🔴 **기본값을 켜지 말 것.**
🔴 **포털 부품(`Pv2DateTimeField`)을 끌어오지 않았다** — `.pv2-*` 스코프가 딸려온다
(원칙 57번). 같은 **동작**을 관리자 생김새로 옮긴 것이다.

🔴 **DB 0 이다** — `quotes` 에 도착구분 컬럼을 만들지 않는다(28차 결정 1). 값은
**특이사항 한 줄**로 오더·배차까지 이어진다(포털에서 넘어온 견적이 이미 쓰던 경로).
문구·중복 판정은 `lib/arrivalType.ts` 하나가 한다(`arrivalNoteLine` /
`buildNotesWithArrival`) — **이미 들어 있으면 다시 붙이지 않는다.**

🔴 **당착·내착이면 +30분 하한을 걸지 않는다**(27차 예외) — 안 그러면 **23:40 상차
건의 당착이 하한에 걸려 접수가 막힌다.**
🔴 **자리 채움 시각 `"23:59"` 가 세 파일에 흩어져 있던 것을 `lib/arrivalType.ts` 하나로
모았다**(견적 폼까지 넷이 될 뻔했다). 그 파일은 `.pv2-*` 스코프가 아니라 관리자·포털이
함께 쓸 수 있어서 원칙 57번을 어기지 않는 자리다.
🟢 칩을 켜면 날짜·시간 칸이 **잠기고**, 손으로 고치면 칩이 **풀린다**(「당착」이라 적혀
있는데 저장값은 딴 시각인 상태를 막는다). 「지금」은 **제출하는 순간의 시각**으로 저장된다.
⚠️ 「지금」·「당착」은 시각 칸이 **비어 보인다** — 시간 드롭다운이 30분 단위라 현재 시각도
23:59 도 선택지에 없다. **칸을 비운 채로 두는 것이 맞고**, 그 이유를 배지로 적어 뒀다.

**곁다리로 하나 고쳤다** — 상차 안내가 「현재 시각 이후로만 선택 가능합니다」라고 적고
있었는데 **하한이 걸려 있지 않았다**(35차 확정: *"지나간 날짜도 고를 수 있어야 한다"* —
끝난 운송을 뒤늦게 입력하는 일이 있다). 원칙 6번이 *"36차 D장이 하차만 다루기로 해서
일부러 안 고쳤다"* 고 적어둔 자리인데, 바로 옆에 「지금」 칩이 생기면서 더 헷갈리게 돼
같이 고쳤다. 🔴 **문구를 근거로 하한을 새로 걸지 말 것.**

### ⑧ 견적서 공유 링크 — 로그인 없이 열리는 견적서

사용자 원문: *"견적문자 발송에서 간단한 멘트와(견적서발송,위캐리운송포함) 견적서 url을
보낼수 있나? 가급적 (SMS) 문자이면 좋겠다."*

🔴 **조사해 보니 보낼 URL 자체가 없었다.** 견적서를 볼 수 있는 곳이
`/admin/quotes/[id]`(직원만 · middleware 가 막음)와 `/customer/quotes/[id]`(포털 계정
있는 화주만) 둘뿐이라, **전화로 받은 게스트 견적은 계정이 없어** 링크를 줘도 못 연다.
그래서 **별도 차수로 제안하고 결정 3건을 받았다** — 사용자 확정:

```
  ① 확인을 한 번 더 받는다(연락처 뒤 4자리)
  ② 유효기간이 지나면 막는다
  ③ 기존 견적안내 문자를 대체한다
```

```
  [위캐리운송] 견적서를 보내드립니다.
  https://wecarrylogis.co.kr/q/<토큰 22자>        실측 **87byte (SMS)**
```

🔴 **「문의 1661-2403」 한 줄을 넣으면 102byte 로 LMS 가 된다 — 넣지 말 것.** 대신
① 이 문자의 **발신번호가 담당자 본인 번호**라(35차) 그대로 회신·통화가 되고
② 대표번호는 **견적서 화면 안에** 있다.
🔴 **35차의 「90byte 압축을 되살리지 말 것」과 부딪히지 않는다 — 전제가 달라졌다.**
그때 LMS 로 간 이유는 *"압축하면 품목이 잘려 무슨 견적인지 알아보기 어렵다"* 였는데,
지금은 **링크가 견적서 전체를 대신 보여준다.** 🔴 **본문에 품목·금액을 다시 넣지 말 것.**
🔴 **URL 을 줄임주소로 감싸지 말 것** — 외부 서비스가 죽으면 이미 보낸 문자가 통째로
죽는다. 경로가 `/q/` 로 짧은 이유가 이것이다(29자 + 토큰 22 = 51byte).

**되돌리면 안 되는 설계**:

🔴 **주소만으로는 아무것도 안 보인다.** 화면은 처음에 입력칸 하나만 그리고, 서버가
뒤 4자리를 확인해 준 **뒤에야 견적 내용을 처음 받아온다**(미리 받아서 숨기면 페이지
소스에 그대로 남는다 — 30차 푸터 이메일에서 겪은 함정). **실측: 토큰만으로 연 HTML 에
견적 데이터 0건.**
🔴 **서버 컴포넌트로 바꾸지 말 것** — 토큰이 주소에 있으므로 서버에서 바로 렌더링하면
뒤 4자리 확인이 통째로 무의미해진다.
🔴 **API 는 POST 다** — GET 이면 토큰과 뒤 4자리가 **주소창·서버 로그·리퍼러**에 남는다.
🔴 **`quotes` 에 anon SELECT 정책을 만들지 말 것**(원칙 3번과 같은 결) — 그 순간 뒤
4자리 확인이 무의미해지고 **모든 견적이 열린다.** service_role 로만 읽는다.
🔴 **응답 필드를 늘리지 말 것** — 차주 지급액·마진은 한 칸도 없고 **연락처도 담지
않는다**(뒤 4자리를 맞힌 사람이 전체 번호를 가져가면 안 된다). `select("*")` 로 바꾸면
그 순간 전부 새어 나간다.
🔴 **만료 컬럼을 새로 만들지 말 것** — 유효기간은 **견적서 자신의 것**(발행일 + 7일)을
쓴다. 견적서 PDF·엑셀이 이미 그 값을 인쇄하므로, 별도 컬럼을 두면 **문서에 적힌
유효기간과 링크가 막히는 날짜가 갈린다.** 기준은 `created_at` 이고 발급 시각이 아니다.
🔴 **토큰은 견적당 한 번만 발급한다** — 보낼 때마다 새로 만들면 **먼저 받은 문자의
링크가 죽는다**(같은 견적을 두 번 안내하는 일은 흔하다). **백필하지 않는다** —
보낸 적 없는 견적서의 링크가 DB 에 쌓인다.
🔴 **실패 사유를 「토큰이 틀렸다/4자리가 틀렸다」로 가르지 않는다** — 가르면 남의 링크를
주운 사람에게 *"이 토큰은 맞다"*를 알려주는 셈이다(32차 로그인 문구와 같은 판단).
🔴 **원칙 11번** — `TopNav` 숨김 조건에 `/q/` 를 넣었다. 색인 차단은 **두 겹**
(`app/q/layout.tsx` 의 noindex + `app/robots.ts` 의 disallow).
🟢 `app/sitemap.ts` 는 동적 세그먼트를 건너뛰고 `/q` 에 `page.tsx` 가 없어서
**사이트맵에는 저절로 안 들어간다** — 손댈 것이 없었다.

⚠️ **한계를 정직하게 적어 둔다** — **뒤 4자리는 10,000 가지뿐이라 토큰을 이미 아는
사람에게는 벽이 아니라 과속방지턱이다**(32차 로그인 제한과 같은 성격이고 같은 부품
`LoginAttemptTracker` 를 쓴다). 진짜 방어선은 **토큰의 추측 불가능성**(22자 base62 ≈
