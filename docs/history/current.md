### ① 「왕복,편도 드롭메뉴 안됨」의 정체는 **키 한 글자**였다


`rate_surcharges.category` 의 실제 이름은 **`왕복/편도`**(슬래시 포함)다. 이 화면만
빠뜨려 그 칸이 **빈 배열**이 됐고, 드롭다운을 눌러도 항목이 하나도 없었다.
🔴 **예외도 경고도 나지 않는다** — 원칙 55번과 같은 결의 조용한 실패다.

🟢 **다른 화면 넷은 전부 맞았다**(포털 발주요청 4곳 · 관리자 견적 등록·상세 · 포털
견적확인). 같은 파일의 `물품특성`·`운송시간` 도 맞았고 **`왕복/편도` 하나만** 틀렸다.

🔴 **재현했다** — 목 데이터 3종을 내려주고 키에서 슬래시를 뺀 판본으로 실제 렌더링:

### ② 필수 표시는 **정말 0건**이었고, 리뷰에서 빨간 `*` 로 뒤집혔다

착수 전 실측: `req-marks`·`field-required`·`required` **전부 0건**. 카드 제목만
「필수 입력」이고 실제로 제출을 막는 넷 옆에 톤수·차종·운송물건이 **똑같은 모양**으로
섞여 있었다.

본작업에서는 `/apply` 에 이미 있던 `requiredMark`(회색 「필수」 글자)를
`components/landing/form/Fields.tsx` 로 옮겨 정의처를 하나로 만들었다.
🔴 **그런데 리뷰 1라운드에 사용자가 빨간 `*` 로 바꾸라고 했다** — 31차 리뷰가 확정했던
「빨간 `*` 가 아니라 회색 「필수」 글자」가 **뒤집힌 것이다. 그 옛 결정을 근거로
글자로 되돌리지 말 것.**

🔴 **범위가 화주포털까지 넓어졌다**(사용자 지시 *"이부분은 화주포털 발주요청도 마찬가지로"*).
⚠️ **포털에 필수 표시가 없던 게 아니었다** — **검정 `*` 가 부제와 placeholder 안에
문자로** 박혀 있었다(`"상차지 정보 *"` · `"출발지 주소 검색 또는 직접 입력 *"`).
🔴 **placeholder 는 값을 입력하면 사라져서 표시 역할을 못 한다** — 제목 옆으로 옮겼고
문자 `*` 는 지웠다. **문자로 되돌리지 말 것.**

🔴 **색은 한 값(`#B4423A`)이고 정의처를 둘로 갈랐다** — 공개 폼은 `Fields.tsx` 의
`REQUIRED_MARK_COLOR`(인라인 style), 포털은 `globals.css` 의 `.pv2-req`.
**공개 폼 부품을 포털에 import 하지 않으려고 가른 것**이고(원칙 57번),
🔴 **한쪽을 고치면 반대쪽도 같이 고칠 것.** 실제로 그려서 **색·크기·굵기가 같음을
확인했다**(`rgb(180,66,58)` · 15px · 700).
🔴 **`--pv2-*` 토큰을 새로 만들지 않은 것은 의도다** — 만들면 포털 전용이 되어 공개 폼과
값을 맞출 수 없다(PR #145 가 같은 판단을 했다).

🟢 **`/apply` 도 같은 정의처라 함께 바뀌었다** — 사용자가 든 것은 앞의 둘이지만
`/apply` 만 회색 글자로 남으면 공개 폼 둘이 갈린다. **merge 보고에 밝혔다.**
🔴 **동의 카드(`LandingConsentCard`)의 자체 「필수」 배지는 안 건드렸다** — 그것은
라벨 옆 표시가 아니라 카드 제목 옆 배지이고 12px `#8B8A85` 로 성격이 다르다.

⚠️ **네이티브 `required` 를 쓰지 않는 것은 그대로다**(폼에 `noValidate` 가 있다) —
브라우저 검사가 React 핸들러보다 먼저 걸리면 우리 오류 문구가 안 뜬다(PR #121).
**표시는 안내이고 막는 것은 제출 직전 검사다 — 둘이 어긋나지 않게 할 것.**

🟢 **곁다리 — 제출 검사 순서를 화면 순서와 맞췄다.** 출발지가 비었는데
「성함(업체명)과 연락처를 입력해주세요」가 뜨고 있었다. 「필수」 표시와 안내가

그래서 **제출 직전 검사가 필요한 경우는 「나중에 상차를 늦췄을 때」뿐이다** —

### ④ C장 — 운송시간 자동선택. **관리자에 이미 있었고 틀렸다**

🔴 **착수 전 확인에서 가장 값이 컸던 발견이다.** `app/admin/quotes/page.tsx` 에
「희망 상차일시 → 운송시간 자동선택」이 **이미 있었고 결함이 둘**이었다.

```
  ① 출퇴근/혼잡(+10,000)·새벽(+20,000)을 아예 안 썼다
     `hour < 8 || hour >= 20` 을 전부 「평일 야간」으로 봐서 새벽 3시도 야간이었다
  ② `options.find(o => o.includes("평일") || o.includes("주간"))`
     `평일 주간`·`평일 야간`이 둘 다 「평일」을 포함해서 배열 순서로 먼저 오는 쪽이 잡혔다
```
🔴 **부분일치로 되돌리지 말 것.**

규칙 정의처는 **`lib/transportTimeAuto.ts` 하나**이고 **세 화면**이 쓴다
(견적문의 · 화주포털 발주요청 · 관리자 견적 등록).

```
  토·일                주말            (🔴 시간대보다 먼저다)
  00:00 ~ 05:59       새벽            +20,000
  06:00 ~ 07:59       출퇴근/혼잡      +10,000
  08:00 ~ 17:59       평일 주간        0
  18:00 ~ 19:59       출퇴근/혼잡      +10,000
  20:00 ~ 23:59       평일 야간        +10,000
```

⚠️ **그래서 18:00~19:59 상차 건의 견적이 0원 → +10,000원으로 오른다.**
🔴 **사용자 확정이다**(AskUserQuestion — 「여섯 종 전부 자동」). 06:00~07:59 는
지금도 +10,000 이라 **이름만** 바뀐다. **금액이 바뀌는 자리라 물어서 확정받았다.**

🔴 **주말이 시간대보다 먼저다** — 기존 동작을 그대로 둔 것이다. 바꾸면 주말 새벽 건이
`주말`(+10,000) → `새벽`(+20,000)으로 **또 금액이 오른다.**
⚠️ 새벽이 더 어려운 시간이라 반대가 맞다는 의견이 있을 수 있다 — 🔴 **바꾸려면 먼저 물을 것.**

🔴 **`공휴일`은 자동으로 못 고른다** — 저장소에 공휴일 달력이 없다. 목록에는 그대로 있어
담당자·화주가 직접 고른다. 🔴 **달력을 하드코딩하지 말 것**(매년 바뀐다).

🔴 **실제로 내려온 선택지 목록 안에 있을 때만 값을 준다**(`autoTransportTime` 의
`available` 인자) — 이름이 바뀌면 틀린 값을 넣는 대신 **아무것도 안 고른다.**
`option_name` 완전일치라 한 글자만 달라도 가산이 조용히 빠지는 자리다.
🔴 **`available` 을 생략 가능하게 만들지 말 것.**

🟢 **직접 바꾼 값은 남는다.** 다만 **상차일시를 다시 고치면 또 자동으로 맞춰진다** —
관리자 화면이 전부터 그렇게 동작했고 세 화면이 같아야 한다.

### ⑤ 시각 비교는 **문자열로 하면 뒤집힌다**

🔴 Postgres 는 `…+00:00`(마이크로초), `toISOString()` 은 `…Z`(밀리초)라 **형식이 다르다.**
형식이 다르면 사전순은 못 믿는다 — **실측**:

```
  "2026-09-16T12:00:00.500+00:00" > "2026-09-16T12:00:00Z"   →  false   (`.` < `Z`)
  Date.parse 로 재면                                          →  true    (실제로 500ms 뒤)
```

🔴 **`isUpdatedSince()` 를 문자열 비교로 되돌리지 말 것.**
⚠️ **밀리초 아래는 `Date.parse` 가 버린다** — 기준값과 같은 밀리초에 바뀐 건은 표시되지
않는다. 그 한 건은 **화주 본인이 방금 일으킨 것**이라 실무에서 문제가 되지 않는다.
🔴 이것을 고치겠다고 문자열 비교로 돌아가지 말 것(위 함정이 훨씬 자주 걸린다).

곁다리 — 관리자 배너 제목이 `label` 과 `title` 두 이름으로 갈려 있던 것을
**`INTAKE_ALERTS[...].title` 한 곳**에서 가져오게 정리했다(`lib/pushNotify.ts` 도 같이).

### ③ 「포털에 윈도우 배너가 안 뜬다」 — **재서 보니 고장이 아니었다**

🔴 **신고를 받고 코드부터 열지 않고 `verify` ㉓ 로 운영 DB 를 쟀다.**

```
  직원(push_subscriptions)          전체 3 · 실패 0 · 성공이력 3 · 사람수 1
  화주(customer_push_subscriptions)  전체 2 · 실패 0 · **성공이력 1** · 사람수 1
  둘 다  rls_켜짐 = t · 정책수 = 0
```

🟢 **화주 쪽에 성공 이력이 1건 있고 실패가 0건**이라 **발송 경로 자체는 살아 있다.**
서비스워커 등록도 관리자와 대칭이다(`ServiceWorkerRegister` + `next.config.mjs` 의
`Service-Worker-Allowed` 헤더). 🔴 **구조적 결함이 아니다 — 「안 온다」를 코드 버그로
전제하고 뜯지 말 것.**

진짜로 갈리는 자리는 **A장과 B장의 신호가 다른 것**이다:

```
  A장(화면 안)  `updated_at > 마지막으로 본 시각`  →  담당자가 무엇을 만져도 뜬다
  B장(푸시)     사건 넷                          →  그 넷일 때만 간다
```

그래서 「화면에는 뜨는데 폰에는 안 온다」가 **정상 동작으로도 일어난다.** 이것을
그대로 보고하고 **넓힐지 좁힐지**를 물었더니 사용자가 **좁히는 쪽**을 골랐다.

### ④ 포털 알림 범위 — 넷 → 둘 / 다섯 → 셋

| | 전 | 후 |
|---|---|---|
| 화면 안 `PortalAlertKind` | 견적 · 배차 · **정산** · **공지** | 견적 · 배차 |
| 웹 푸시 `PortalPushEvent` | 견적 · 배차확정 · **상차완료** · **하차완료** · **정산확정** | 견적 · 배차확정 · **운송완료** |
| 배차 상태 매핑 | 배차확정 · 상차완료 · 하차완료 | 배차확정 · 운송완료 |
| **배지** `PortalCountKind` | 넷 | **넷 — 그대로** |

🔴 **배지와 알림을 가른 것이 이 차수의 핵심이다.** 같은 타입 하나로 두고 있었는데
**「볼 것이 생겼다」와 「불러야 한다」가 다른 것**이라 `PortalCountKind`(넷) /
`PortalAlertKind`(둘)로 갈랐다. 🔴 **다시 합치지 말 것** — 합치면 배지를 지우거나
알림을 되살리거나 둘 중 하나가 된다. 조회·Realtime 구독도 넷 그대로다.

🔴 **정산을 「종류째」 뺀 이유** — 사용자가 든 것은 셋(세금계산서 발행완료 · 화주입금
완료 · 차주지급완료)인데 포털 알림의 신호가 **`invoices.updated_at` 하나**라 **그 셋을
골라낼 수가 없다.** 담당자가 정산 건의 어느 칸을 만져도 똑같이 울린다.
🔴 되살리려면 「어떤 변경일 때만」을 먼저 정해야 하고 그것은 **사건별 신호를 새로
만드는 일**이다.

🔴 **공지를 뺀 자리에 「공지는 유일하게 새로 생기기만 하는 것이라 「새」가 맞다」는
주석이 있었다** — 그것은 **라벨이 맞다**는 말이지 **알려야 한다**는 말이 아니다.
🔴 그 문장을 근거로 되살리지 말 것.

🔴 **화면 안 알림과 푸시를 같이 없앴다** — 한쪽만 끄면 **「폰으로는 오는데 화면에는
안 뜨는」** 상태가 된다(그 반대도 마찬가지다).

### 🔴 `하차완료` 와 `운송완료` 는 DB 에서 **다른 값**이다 — 보고하고 그대로 갔다

`DISPATCH_STATUS_OPTIONS` 는 6종이고 `하차완료` · `운송완료` 가 **따로** 있다.
그런데 **화주 화면은 둘 다 「운송완료」로 보여준다**(`lib/dispatchStage.ts` 의 2단계 —
29차가 *"하차완료를 진행 중에 두지 말 것 — 화물은 이미 도착했다"* 로 정한 것이다).

사용자가 쓴 말(상차완료 · 하차완료 · 운송완료)이 **담당자 화면의 상태값 이름**이므로
**DB 값 `운송완료` 에만** 걸었다.

🔴 **그래서 담당자가 `하차완료` 에서 멈추면 화주에게 완료 알림이 가지 않는다** —
화주 화면에는 「운송완료」로 보이는데 알림만 안 온다. **merge 보고에 이것을 적었다.**
🔴 **단계(`getDispatchStage`)로 바꿔 걸면 `하차완료` 에서도 울리는데 그것은 이번
확정과 반대다 — 바꾸려면 사용자에게 먼저 물을 것.**
🟢 `운송완료` 는 죽은 값이 아니다 — `lib/autoCreateInvoice.ts` 의 정산 자동등록이
그 상태에서 도니 운영에서 실제로 쓰인다.
⚠️ **`문제발생` 도 안 넣었다** — 무슨 일인지 본문에 적을 수 없어서(잠금화면) 「문제가
생겼습니다」만 울리게 되는데, 그것은 담당자가 전화로 할 일이다.

## 화주포털 B장 — 웹 푸시 (견적·배차·정산) (PR #161, 2026-09-16)

🟢 **`main` 기준 +1,079 / −211 · 17파일 · 커밋 2개(squash `8d261cc`)** · 공개 화면 0줄 ·

새 `page.tsx` 0개 · 새 되풀이 타이머 0 · 실사용 리뷰 라운드 **0**.

🔴 **차수를 소비하지 않았다**(38차 B장의 연장이다).

바로 앞 차수(38차)가 화주포털에 **화면 안 알림**을 넣었는데, 그것은 **포털을 열어 둔

도착한 것을 닫아 둔 채로는 알 수 없었다.** 그 구멍을 메운 것이다.

범위는 사용자 확정 그대로 **견적 · 배차 · 정산 셋**이다(*「견적과 배차,운송 정산만」*).

### ① 🔴 표를 갈랐다 — 이 차수에서 가장 되돌리기 쉬운 결정이다

`push_subscriptions`(직원용, 38차)에 `customer_account_id` 컬럼 하나만 더하면 끝날
일처럼 보인다. **그렇게 하지 않았고, 다음 세션이 「정리」로 합칠 위험이 가장 큰 자리다.**

사유는 **롤**이다. 화주포털 계정과 직원 계정이 **둘 다 `authenticated`** 다(19차).
그래서 이 표들은 **RLS on + 정책 0개**로만 지켜진다 — 정책을 하나라도 만드는 순간
양쪽이 함께 열린다. 한 표에 두 종류를 담아 두면 언젠가 누가 「조회 편하게」 정책을
하나 열 때 **화주와 직원 기기가 한꺼번에 샌다.** 표가 둘이면 그 사고가 한쪽에서 끝난다.

🔴 **합치지 말 것.** 마이그레이션 단언이 `staff_id` 컬럼의 **부재**까지 확인한다.

### ② 🔴 `company_id` 를 구독 표에 복사해 두지 않았다

발송은 **회사 단위**(그 화주의 모든 담당자 기기)라 회사 id 를 이 표에 넣어 두면
조인 없이 끝난다. **그런데도 안 넣었다** — 담당자 계정이 다른 화주로 옮겨지면
복사해 둔 값이 낡아 **남의 회사 소식이 그 폰으로 간다.**

발송할 때마다 `customer_accounts` 를 조인해 회사를 정한다(조인 한 번).
⚠️ **그래서 이 표만 보고는 「어느 화주인가」를 알 수 없다 — 그것이 의도다.**
마이그레이션 단언이 `company_id` 컬럼이 **없는지**를 확인한다.

### ③ 🔴 서버에서는 `await`, 브라우저에서는 아니다 — 방향이 반대다

38차 B장이 실제로 겪은 자리다. **서버리스 함수는 응답을 돌려준 뒤 얼어붙어서** 떠 있는
약속이 끝나지 않는다 — 정산확정(`app/api/admin/invoices/confirm/route.ts`)처럼
**서버 안에서** fire-and-forget 으로 두면 **푸시가 아예 안 나간다.**

반대로 견적·배차는 **브라우저가** 서버 API 를 부르는 구조(원칙 53번)라 `await` 하면
담당자의 상태 변경이 알림을 기다리며 멈춘다. **거기서는 `void fetch(...)` 가 맞다.**

```
  견적 상세 · 배차 상세 · 배차 목록   브라우저 → /api/admin/notify-portal-push   await 금지
  정산확정                           서버 라우트 안에서 notifyPortalPush()        await 필수
```

🔴 **한쪽 규칙을 다른 쪽에 옮기지 말 것.** `lib/notifyPortalPush.ts`(브라우저용)와
`lib/portalPushNotify.ts`(서버 발송 정의처)의 **이름이 비슷해서** 헷갈리기 쉽다 —
**`notify-` 로 시작하는 쪽이 브라우저**다.

### ④ 🔴 부르는 곳이 넷이라 매핑을 화면에 적지 않았다

배차 상태를 바꾸는 자리가 **넷**이다(원칙 53번이 문서화한 그대로) — 배차 상세의
**확정 버튼 · 상태 드롭다운 · 상차/하차 체크박스**, 그리고 **배차 목록의 드롭다운**.
상태 → 사건 매핑을 화면마다 적으면 **「목록에서 바꾸면 알림이 오고 상세에서 바꾸면
안 오는」** 상태가 된다. `lib/notifyPortalPush.ts` 의
`notifyPortalPushForDispatchStatus()` **한 곳**이다.

🔴 **수동 재발송 버튼(배차 상세 「문자 발송」 섹션의 셋)에서는 부르지 않는다** —
거기는 담당자가 **문자**를 다시 보내는 자리라, 며칠 뒤 눌러도 「배차가 확정되었습니다」

🔴 **바뀌지 않았으면 안 보낸다** — 같은 값을 다시 고르는 일이 흔하고, 그때마다 화주

⚠️ **「운송완료」·「문제발생」은 일부러 없다** — 하차완료가 곧 운송완료라 두 번 울린다.

### ② 실제로 돌려 보고 잡은 결함 둘 — 둘 다 눈으로는 안 잡힌다

🔴 **「화면을 보고 있으면 푸시를 건너뛰자」로 바꾸지 말 것**(사용자가 고른 것이다).

**② 볼륨 3단계 + 소리 3종**을 종 모양 **옆 `▾`** 에 달았다.

```
  볼륨   작게 0.07   [보통 0.18]   크게 0.38
  소리   [두 음 880·1318.5]   단음 1046.5   세 음 659.3·880·1174.7
```

- 🔴 **기본값(보통 · 두 음)은 A장이 넣은 그 소리 그대로다** — 아무것도 안 고른
  담당자의 소리가 **말없이 달라지면 안 된다.** 음 높이·길이·게인을 바꾸지 말 것
- 🔴 **고르면 그 자리에서 들려준다.** 그 클릭이 곧 사용자 제스처라 **자동재생 정책이
  그때 풀린다** — 안 그러면 첫 접수가 올 때까지 소리가 나는지 알 수가 없다
- 🔴 **고른 값을 인자로 넘긴다**(`playAlertChime({volume, tone})`) — 저장을 읽게 두면
  `localStorage` 가 막힌 브라우저에서 옛 소리가 나 「눌러도 안 바뀐다」로 보인다
- 🔴 **기억하는 곳은 브라우저(`localStorage`)다.** `staff_accounts` 컬럼으로 옮기지
  말 것 — 수신 설정 화면을 안 만들기로 한 **38차 0-3 과 어긋나고**, DB 변경이 0 이던
  A장이 DB 변경을 갖게 된다. 볼륨·소리는 **그 사람이 앉은 자리의 취향**이다
- 🔴 **끄기(🔔)와 펼침(▾)은 다른 단추다** — 합치면 소리를 끄려다 창이 열린다

### ① 범위가 작업 중에 두 번 줄었다 — 그것이 이 차수의 전부다

지시서 초안(그리고 설계 v4 5장 매핑표)은 **차주 3칸 + 운송료 + 수수료 + 화물번호**를
가져오는 것이었다. 착수해서 마이그레이션(`dispatches.external_order_no`)까지 써 둔
상태에서 사용자가 범위를 줄였다.

> *"잠시만, 지금 작업은 좀더 심플하게 가자. 배차 접수중일때 24시 배차망에서 배차가
> 되면, 배차된 차주의 차주명, 전화번호, 차량번호만 복사해서 붙여넣으면 이 정보만
> 자동으로 입력되게 하자."*

🔴 **그래서 `dispatches.external_order_no` 신설이 없어졌고 DB 변경이 0이 됐다.**
🔴 **금액·화물번호로 넓히지 말 것** — 저장 경로가 다르고(`handleSave` / 계산기 저장),
수수료 칸은 **수금방식이 선착불이어야** 그려진다. 넓히려면 그때 지시를 받는다.

그리고 붙여넣을 글의 모양도 줄었다.

> *"「(차주명) (차량번호) (연락처)」 앞으로 이정도 정보만 붙여 넣겠다."*
> 🔴 **원문에는 실제 차주 이름·차량번호·연락처가 들어 있었다 — 이 저장소는 public 이라
> 여기에도 옮겨 적지 않았다.** 모양만 남긴 것이고, 잃은 것은 없다(⑦ 참고)

🔴 **그래서 목록 행 40열 탭 파서를 통째로 버리고 「한 줄 · 토큰 셋」 파서로 다시 썼다.**
설계 v4 의 「라벨로 가른다」가 **성립하지 않는 입력**이 된 것이다(라벨 줄이 없다).
🔴 **40열 탭 파서를 되살리지 말 것** — 아래 ③ 이 그 이유다.

### ② 왜 「접수중의 외부 배정 분기」 안인가 — 다른 자리가 없다

🔴 **차주 이름·연락처·차량번호 입력칸은 `dispatch_status === "접수중"` 의
`assignment_type === "external"` 분기 안에만 있다.** 배차확정 이후에는 세 값이
**읽기 전용**이라 채울 자리 자체가 없다.

```
                          접수중    배차확정 이후
   차주 3칸 입력            ✅        ❌ 읽기 전용
   배차확정 버튼            ✅        ❌
   차주 기본운임 계산기      ❌        ✅          ← 렌더 조건이 정확히 반대다
```

🔴 **「차주 기본운임 계산기 옆에 두자」가 성립하지 않는 이유가 이것이다** — 그 계산기는
`!== "접수중"` 일 때만 그려진다. 착수 전에 사용자에게 자리를 물었을 때 **내가 계산기만
근거로 들어 질문이 한쪽으로 기울었고**, 그 사실을 사용자에게 알린 뒤 다시 물어 확정했다.
🔴 **「어디에 둘까」를 묻기 전에 그 칸의 렌더 조건부터 읽을 것.**

### ③ 라벨이 없으니 순서가 아니라 「모양」으로 가른다

붙여넣는 글에 라벨이 없다. 사람이 손으로 옮겨 적는 값이라 **순서도 믿을 수 없다.**
그래서 토큰마다 정규식으로 무엇인지 판정한다(`lib/wecarry24Paste.ts`, 의존성 0).

```
  차량번호  /^[가-힣]{0,2}\d{2,3}[가-힣]\d{4}$/
            신형 `12가3456` · 영업용 `12바3456` · 지역 있는 `서울12가3456` · `경기12자3456`
  이름      위 둘이 아닌 첫 토큰
```

🟢 `010-1234-5678 홍길동 서울12가3456` 처럼 순서를 바꿔 적어도 같은 결과가 나온다.
🔴 **구분자는 `/\s+/` 다** — 탭·줄바꿈·공백을 똑같이 본다(창에서 드래그하면 탭이 섞인다).
🔴 **토큰이 8개를 넘으면 거절한다** — 목록 행을 통째로 붙여넣으면 값이 40개라
**전화번호가 여럿**이고, 잘못 집으면 **엉뚱한 사람에게 배차 문자가 나간다.**
그래서 막고 「이름 차량번호 연락처 세 가지만」이라고 안내한다.

### ④ 채우기만 하고 저장하지 않는다

🔴 **저장은 기존 「배차확정」 버튼이 한다.** 새 저장 경로를 만들면 그 버튼이 하는 검사
(선착불 지급조건 확인 등)와 낙관적 잠금을 **우회하게 된다.** 그래서 채운 뒤 그 자리에
**「아직 저장되지 않았습니다 — … 배차확정을 눌러 주세요」**를 적는다(원칙 33번 — 오류·
안내는 누른 자리에).

지킨 것 넷:
- 🔴 **빈 값으로 덮어쓰지 않는다** — 차량번호를 못 읽었으면 담당자가 손으로 적어 둔 값을
  그대로 두고 그 사실을 알린다
- 🔴 **읽지 못한 토큰을 조용히 버리지 않는다**(원칙 55번) — `unknownTokens` 로 돌려 화면에 나열한다

  포맷을 안 입히므로 **화면이 입힌다** — 파서 안으로 옮기지 말 것
- 🔴 **서버에 보내지도 저장하지도 않는다** — 브라우저에서 갈라 입력칸에 넣고 버린다.

### ③ 🟢 v4 7장 「착수 전 확인」 실측 — 넷

**ⓐ 지시서는 이 값을 전제로 쓴다.** 코드로 잴 수 없는 것(붙여넣은 텍스트의 실제 모양)은 샘플

**ⓐ-1 `dispatches.external_order_no` 가 정말 없는가 → 🔴 없다.**


코드·마이그레이션 양쪽에 한 줄도 없다. v3 조사 시점 그대로이고 **신설이 맞다**(24시콜 화물번호가

**ⓐ-2 `brokerage_fee` 를 채우는 자리와 부가세 토글의 관계 → 🔴 그 칸에는 토글이 없다.**

블록** 안이고, **`settlementValue.collection_method === "driver_direct"` 일 때만 그려진다.**

라벨이 **「주선수수료(부가세 포함가, 원)」**로 못박혀 있고, 아래 캡션이 `toSupplyAmount()`(÷1.1)로
공급가액·부가세를 보여줄 뿐이다. `VatBasisSelect`(부가세 구분 토글)는 **화주 청구금액**과
**차주 지급운임** 두 칸에만 붙는다.

```
  화주 청구금액(원)            + VatBasisSelect   ← customer_charge_vat_included
  차주 지급운임(원)            + VatBasisSelect   ← driver_vat_included
  전체 운송료(원)              (선착불 블록)
  차주 직접수금액(공급가액, 원) (선착불 블록)
  주선수수료(부가세 포함가, 원) 🔴 토글 없음 — 포함가 고정
```

🔴 **그래서 ⓐ 가 24시콜 「합계」를 `customer_charge` 에 넣을 때는 `customer_charge_vat_included` 를
함께 정해야 한다** — 기본값이 `false`(부가세 별도)다. 이것이 v3 §5 대조 블록의 **미결 「부가세
기준」과 같은 자리**이고, 🔴 **v12 가 라벨을 「공급가액 (부가세 별도)」로 통일했다고 해서 이 미결이
닫힌 것은 아니다**(라벨과 `brokerage_fee` 기입 기준은 다른 축이다).

🔴 **선착불이 아니면 그 블록 자체가 안 그려진다** — 24시콜 건은 **수금방식이 먼저 선착불이어야**
`brokerage_fee` 칸이 화면에 나타난다. ⓐ 가 값을 채우려면 수금방식부터 세워야 한다는 뜻이다.
⚠️ 화면 주석의 실측 — **DB 에 5,000(포함가)과 4,545(공급가액)가 섞여 들어가 있다**(35차가 라벨을
바꾸기 전에 저장된 것). 통계는 항상 ÷1.1 로 공급가액을 쓴다.

**ⓐ-3 붙여넣기 칸을 넣을 자리 → 🔴 저장 경로가 셋이라는 것이 핵심이다.**

v4 가 *「줄 번호가 아니라 계산 흐름으로 찾을 것」*이라 한 자리다. 흐름으로 보면 카드 순서는
**배정방식·배차확정 → 상차지·하차지 담당자 → 정산 정보 → 클레임 → 현장 추가비 → POD → 문자 발송**
이고, 24시콜 한 건의 값이 **서로 다른 세 state 와 세 저장 버튼**으로 흩어진다:

```
  차주 이름·연락처·차량번호·확정 정보망
      → externalDriverName / externalDriverPhone / externalVehiclePlate / confirmedNetworkId
        (editForm 이 아니라 **별도 state**)
      → 저장은 **handleConfirm()** — 배정방식 카드의 「배차확정」 블록,
        `assignment_type === "external"` 분기 안에 있다
  화주 청구금액 · 부가세 구분 · 전체 운송료 · 주선수수료
      → editForm      → 저장은 **handleSave()**(맨 아래 「변경사항 저장」)
  차주 기본운임
      → payoutCalcForm → 저장은 **handlePayoutCalcSave()**(접이식 안의 전용 버튼)
```

🔴 **붙여넣기 칸 하나가 두 카드에 걸쳐 값을 채운다.** 자리는 **배정방식 카드 위**가 자연스럽다
(맨 위에서 붙여넣고 아래로 내려가며 눈으로 확인). 🔴 **「한 번 붙여넣으면 저장까지 끝난다」로
설계하지 말 것** — 저장 버튼이 셋이라 어느 하나만 누르면 나머지가 조용히 안 들어간다. ⓐ 지시서가
**이 셋을 명시적으로 다뤄야 한다.**
🔴 **줄 번호로 찾지 말 것** — 35차가 이 화면을 크게 고쳤고 지금 **2,525줄**이다.

**ⓐ-4 `driver_base_fare` 경로 재확인 → 🔴 `driver_payout` 에 직접 넣지 말 것.**

`handlePayoutCalcSave()`(718행)가 `calcSettlement()` 결과로 **`driver_payout` 을 덮어쓴다**
(`driver_payout: result.driverTotalPayout || null`). 직접 넣으면 **계산기를 여는 순간 사라지고**
24시콜 「송금할 운임」과 대조할 근거도 없어진다.
⚠️ **그 칸은 「차주 운임 상세 계산」 접이식 안이고 `dispatch_status !== "접수중"` 일 때만
그려진다** — 접수중 배차에 붙여넣으면 **그 칸이 화면에 아예 없다.** ⓐ 가 접수중 건을 다룰지
여부를 정해야 한다.

### ⑥ 🟢 샘플 실측 — 창 캡처 + 목록 행 복사 텍스트(2026-09-16)

사용자가 **24시콜 화물등록 창 캡처**와 **복사 텍스트**를 함께 보냈다. 🔴 **실제 차주·의뢰자
정보(이름·전화·차량번호·사업자번호)는 저장소에 넣지 않았다** — 이 저장소는 public 이다.
**숫자만 원본**이고 구조·계산을 재려면 그것이 필요했다.

**⑥-1 🔴 복사되는 것은 창이 아니라 「아래쪽 목록의 한 행」이다**

이것이 가장 큰 발견이다. v4 는 *「창에서 드래그 복사」*라 적었는데, **창 위쪽 입력 폼은
위젯이라 드래그 복사가 안 된다.** 실제로 복사된 것은 창 **아래쪽 목록 그리드**의 한 행이고,
모양은 **헤더 줄 + 데이터 줄 두 줄 · 탭 구분 · 40열**이다:

```
  화물번호 · SMS · 상태 · 처리시간 · 공유 · 혼적 · 고객명 · 고객전화 · 상차지 · 하차지 ·
  화물정보 · 운송료 · 수수료 · 요금구분 · 톤수 · 차종 · 차량번호 · 차주이름 · 차주전화 ·
  적재옵션 · 차량종류 · 차량톤수 · 차주사업자번호 · 계산서발행일 · 계산서금액 ·
  도착지 연락처 · 하차일시 · 접수경로 · 등록자전화번호 · 등록자명 · 화주명 ·
  차주실적지위 · 차주 사업자명 · 대표자명 · 산재보험료 차주분 · 송금할 운임 (부가세포함) ·
  산재적용 · 상차일 · 왕복 · 정산일
```

🟢 **v4 의 「순서가 아니라 라벨로 가른다」가 실측으로 뒷받침됐다** — 헤더 줄이 곧 라벨이라
24시콜이 열 순서를 바꿔도 이름으로 찾을 수 있다. **그 원칙을 세워둔 것이 맞았다.**

**⑥-2 🔴 그래서 빠지는 것이 열 가지다**

캡처에는 있는데 **목록 행에는 없는 것**:

```
  메모(의뢰자 특이사항)      거리 31.7km        금액 55,000        합계 80,000
  할인액                    수수료율 18%        상세주소            화물중량 1.00톤 이하
  상하차 방법(6종 라디오)    상차/하차 시점(지금·당일·내일·월착·당착/내착)
```

🟢 **ⓐ(배차 정보 채우기)에는 이것으로 충분하다** — 차주 이름·연락처·차량번호·운송료·
수수료·화물번호가 전부 있다.
🔴 **부족해지는 것은 ⓑ(견적 폼)다** — 상하차 방법·시점·특이사항·상세주소가 통째로 안 온다.
**ⓑ 지시서는 「목록 행만으로는 안 된다」를 전제로 써야 한다**(창을 한 칸씩 복사하게 하거나,
그 값들은 담당자가 직접 고르게 하거나).

**⑥-3 🟢 부가세 기준 미결이 닫혔다 — v3 부터 열려 있던 것이다**

캡처의 두 값이 서로를 증명한다:

```
  합계 80,000 × 1.1 = 88,000
  88,000 − 산재보험료 차주분 350 = 87,650   ← 화면의 「송금할운임(부가세포함)」과 정확히 일치
```

🔴 **부가세가 가산됐으므로 합계 80,000 이 공급가액이다.** 따라서 그 안의 **운송료 65,000 과
수수료 15,000 도 둘 다 부가세 별도**다.
🔴 **그런데 35차는 `brokerage_fee` 를 「부가세 포함가 기입」으로 확정했다**(사용자 6·9번).
그대로 15,000 을 넣으면 포함가로 읽혀 공급가액이 13,636 이 되고 **마진이 10% 적게 잡힌다** —
ⓐ 는 **15,000 × 1.1 = 16,500** 을 넣거나 그 칸의 기준을 바꿔야 한다. **ⓐ 지시서가 정할 것.**

**⑥-4 🟢 v3 §1-9 의 불일치도 풀렸다**

*「차주 실수령을 운송료 65,000 이라 하는데 송금할 운임은 87,650 이라 서로 안 맞는다」*고
적혀 있던 것 — **87,650 은 화주가 차주에게 줄 총액**(합계 부가세포함 − 차주 산재)이고
**65,000 은 그중 차주 몫**이다. 차주가 받아서 수수료를 낸다.
🟢 **35차 선착불 모델**(받을 돈 = 주선수수료 · 줄 돈 = 0 · 수수료는 차주가 낸다)**과 맞는다.**

**⑥-5 🔴 산재 기준액이 서로 다르다 — 새로 드러난 것**

같은 요율(필요경비공제 49.9% · 산재 1.76% · 절반 부담)로 검산했다:

```
  합계 80,000 기준   floor(80,000 × 0.501) = 40,080  →  floor(40,080 × 0.0088) = 352  →  350
  운송료 65,000 기준  floor(65,000 × 0.501) = 32,565  →  floor(32,565 × 0.0088) = 286
```

🔴 **24시콜은 합계(80,000) 기준이고 10원 단위로 절사한다**(화면값 350 과 맞는다).
🔴 **우리 `calcSettlement()` 는 `driverBaseFare`(65,000) 기준이라 286 이 나온다** — 같은 건의
산재가 **350 vs 286** 으로 갈린다. ⓐ 지시서가 **「가져온 값을 그대로 둘지 우리 식으로 다시
계산할지」**를 정해야 한다. 🔴 **말없이 재계산하면 24시콜 정산서와 대조가 어긋난다** —
v12 C장 반올림이 만든 것과 **같은 자리**다.

**⑥-3b 🔴 사용자 확정 셋 — 위 ⑥-3·⑥-5 의 결론이 바뀌었다**(2026-09-16)

```
  1  "선착불 오더에서 적힌 수수료는 부가세 포함가이다. 그래서 15,000원(부가세포함가)로
     적는게 맞다."
  2  "산재는 일단 고려하지 말자."
  3  "접수중 배차는 일단 다루지 말자."
```

🔴 **1번은 내 제안을 뒤집은 것이다.** 나는 ⑥-3 에서 *「합계 80,000 이 공급가액이니 수수료
15,000 도 공급가액이고, 35차가 포함가 기입으로 정했으니 ⓐ 는 16,500 을 넣어야 한다」*고
적었는데, 사용자가 **실무 기준으로 15,000 이 이미 포함가**라고 확정했다.
🟢 **그래서 변환 없이 그대로 넣는다** — 35차 확정과 그대로 맞물린다.
🔴 **「×1.1 해서 16,500」을 되살리지 말 것.**

⚠️ **다만 산술은 여전히 갈려 있고 그것을 지운 것이 아니다.** 24시콜 화면은
`합계 80,000 × 1.1 = 88,000` 으로 계산하므로 **화면상 80,000 이 공급가액**이다. 그 안의
15,000 도 화면 기준으로는 공급가액처럼 읽힌다. 🔴 **그래도 실무 기준이 이긴다** — 합계·
송금액은 **화주↔차주 운임 흐름**의 계산이고, 수수료는 그와 별개로 **차주가 위캐리에 내는
돈**이다(35차 선착불 모델). ⚠️ **두 시스템이 같은 건의 수수료 공급가액을 다르게 본다**
(24시콜 15,000 / 우리 15,000÷1.1 = 13,636) — **세금계산서 대조에서 어긋날 수 있다.**
어긋나는 줄이 나오면 이 문단을 볼 것.

🔴 **2번 — 산재는 범위 밖이다.** ⓐ 는 `industrial_insurance_*` 를 건드리지 않는다.
⚠️ **닫힌 것이 아니라 미뤄둔 것**이고, ⑥-5 의 실측(24시콜 350 / 우리 286)은 그대로 유효하다.

🔴 **3번 — 접수중 배차는 범위 밖이다.** 🟢 **그래서 ③-④ 의 걱정이 없어졌다** — 차주 기본운임
칸이 `dispatch_status !== "접수중"` 일 때만 그려지는데 그 상태를 아예 안 다루므로 칸이 항상
화면에 있다. 🔴 **붙여넣기 칸을 접수중 배차에 그리지 말 것**(값을 받아도 넣을 자리가 없다).

**⑥-3c 🔴 「캡처만으로 되는가」 — 두 축을 가를 것**

사용자 질문: *"참고로 텍스트없이 첨부한 캡쳐이미지만으로도 가능한가?"*

🟢 **세션에게 주는 것은 캡처가 낫다.** 실제로 이번에 캡처만으로 복사 텍스트에 **없는 것
열 가지**를 잡았다(⑥-2). **복사 텍스트는 목록 한 행이라 창보다 좁다.**
⚠️ 다만 **숫자는 내가 눈으로 읽는 것이라 판독 오류가 날 수 있다** — 이번에는
`80,000 × 1.1 − 350 = 87,650` 이 화면값과 맞아떨어져 확신할 수 있었다. 🟢 **서로 맞물리는
값이 화면에 같이 있으면 검산이 되어 안전하다.** ⚠️ 작은 글씨·잘린 부분은 못 읽는다(이번
캡처도 하단 목록은 열 제목만 보이고 데이터 행이 안 보였다).

🔴 **그러나 기능이 읽는 것은 캡처가 아니라 복사 텍스트다 — 바꾸지 말 것.** 이미지를
붙여넣어 읽으려면 OCR 이 필요하고 그 길은 둘 다 막혀 있다:
① **서버로 이미지를 보내 OCR API 호출** → v4 가 확정한 **「서버에 보내지도 저장하지도
않는다」가 통째로 무너지고** 처리방침 변경·비용·계약이 따라온다
② **브라우저 내장 OCR** → 한국어 정확도가 낮고 학습 데이터가 수 MB 라 번들이 무거워진다
🔴 **v3 가 OCR 이었고 v4 가 버린 이유가 정확히 이것이다.** 🟢 **목록 행 복사가 실제로 된다는
것이 확인됐으므로 OCR 이 필요 없다.**
🔴 **「사용자가 캡처를 편하게 준다」와 「기능이 캡처를 읽는다」는 다른 얘기다** — 앞은 기획·
조사 단계의 편의이고 뒤는 제품 설계다.

**⑥-6 🔴 「화주명」이 우리 회사다**

목록 행의 `화주명` = **(주)디자인에그**(= 위캐리)이고, 실제 고객은 창 왼쪽의 **「의뢰자」**다
(의뢰자구분 「비운수사」 · 담당자 · 메모가 그 블록에 있다).
🔴 **`화주명` 을 `companies` 에 매핑하지 말 것** — 그러면 모든 24시콜 건의 화주가 우리
회사가 된다.

**⑥-7 🔴 수수료율 18% 를 믿지 말 것**

캡처에 「수수료적용 **18** %」가 있지만 실제는 `15,000 / 80,000 = 18.75%` 이고, 18% 로 역산한
기준액도 83,333 이라 어느 숫자와도 안 맞는다. **버튼의 기본 요율이고 15,000 은 손으로 넣은
값**으로 보인다. 🔴 **요율로 금액을 재계산하지 말고 금액을 그대로 쓸 것.**

**⑥-8 파싱 규칙(실측)**

```
  구분자          탭
  빈 칸           빈 문자열로 남는다(라벨이 사라지지 않는다)
  🔴 줄 끝 빈 칸   잘린다 — 헤더가 40열인데 데이터가 38개에서 끝났다
                  (`왕복`·`정산일`이 빈 칸이라 사라졌다). 길이가 같다고 전제하지 말 것
  금액            콤마 있음 · 「원」 없음 (`65,000`)
  날짜            `2026-09-07` · 처리시간은 **연도 없이** `09-07 11:30`
  선택형          함께 온다 (`공유` · `Y` · `선/착불` · `전기차`)
```

**⑥-9 🟢 말이 맞는 자리 · ⚠️ 이사 화물**

캡처의 상차 **「지금」** · 하차 **「당일」** · **「당착/내착」** 체크박스와 화물정보의
`지금상 당착-A` 가 **36차 PR 2 의 「지금·당착·내착」 칩과 같은 개념**이다 — 옮겨 담을 자리가
이미 있다.
⚠️ 샘플 메모가 *「이사짐_이사보조…」* 다. 🔴 **위캐리는 이사를 취급하지 않는다**(34차·65차
확정 · 고객 접점 문구에서 뺐다). 24시콜에서 가져오는 건에는 섞여 들어오므로 **그 메모를
화주 접점 화면에 그대로 내보내지 말 것.**
