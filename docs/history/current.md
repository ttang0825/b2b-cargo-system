### ② 🔴 지시서와 다르게 판단한 것 — `source_id` 에 FK 를 걸지 않았다

지시서는 `source_id` 를 **`on delete set null`** 로 하라고 했다(정산을 지워도 원장이

Postgres 에는 다형 FK 가 없다.

🟢 **FK 를 아예 걸지 않는 것이 `set null` 보다 강하다.**

```
  · 정산을 지워도 원장은 그대로 남는다        ← 요구사항 충족(FK 가 없으니 cascade 도 없다)
  · `source_id` 값이 **그대로 남아** 부분 UNIQUE 가 계속 막는다
      🚨 `set null` 이면 **그 순간 유니크에서 빠져 재적립이 가능해진다**
  · 지워진 원본을 가리키던 id 가 남아 **무엇이 지워졌는지 추적**할 수 있다
```

### ⑤ 🔴 잔액 컬럼을 만들지 않았다 · 원장은 append-only

잔액은 **원장 합계의 표시 시점 계산**이다. `companies.outstanding_amount` 가 저장
스냅샷이라 **선착불 화주는 영영 안 고쳐졌던** 사고가 이 저장소에 있다(36차 C장).
🔴 **`companies` 에 리워드 컬럼을 더하지 말 것** — 마이그레이션 단언이 그것을 막는다.
🔴 **원장 행을 DELETE 하거나 `amount` 를 UPDATE 하는 경로를 만들지 말 것** —
잘못 적립됐으면 **반대 부호로 한 줄 더** 넣는다(수동 조정은 **사유가 필수**다).

### ⑥ 🔴 RLS 는 정책 0개 · `is_active_staff()` 를 일부러 안 썼다

표 셋 다 **RLS on + 정책 0개**이고 서버 라우트 다섯이 유일한 통로다. 화주포털 계정과
직원 계정이 **둘 다 `authenticated` 롤**이라(19·21차) 정책을 하나라도 열면 **화주가 남의
회사 적립금을 읽는다.** 🔴 **「관리자 화면이 못 읽으니 정책을 열자」로 되돌아가지 말 것** —
`supabase.from("reward_` 가 `app/` 아래 **0건**이어야 한다.

⚠️ **PR #179(전화응대 매뉴얼)가 「읽기만 정책 + `is_active_staff()`」 구조를 만들었는데
일부러 안 썼다.** 사유는 둘이다 —

```
  1  리워드는 **돈과 화주 상호**다. `call_script` 는 내부 문서 한 행이라 새어도 손해가
     글자뿐이지만 이것은 다르다
  2  그 함수의 **실전 이력이 이틀치**다 — 실측하지 않은 채 돈 데이터에 걸지 않는다
```

🔴 **나중에 읽기만 그 방식으로 옮기는 것은 정당하다. 그때도 쓰기는 service_role 이다.**

### ⑦ 🔴 설정 넷은 각각 독립이고 둘은 1차에서 아무도 안 읽는다

`enabled`(적립 ON/OFF) · `portal_visible`(포털 노출) · `reward_method`(운임 할인 /
상품권 / 담당자 협의) · `sms_notification_enabled`(문자 안내).
🔴 **enum 한 칸으로 묶지 말 것** — 묶으면 **「적립은 하되 포털에는 안 보이고 상품권으로
주는」 고객**을 운영할 수 없다(전달문서 §38 ②).
🔴 **`portal_visible`·`sms_notification_enabled` 는 저장만 되고 읽는 코드가 0건이다**(2차용).
「쓰이지 않는 칸이니 지우자」로 지워지지 않게 **화면에 「2차 작업 후 동작합니다」**를 붙였고
DB 컬럼 주석에도 적었다.
🔴 **`enabled = false` 는 「신규 적립 중단」**이고 기존 적립금을 없애지 않는다 — 화면에도
그렇게 적었다(「끄면 새로 쌓이지 않습니다 — 이미 쌓인 적립금은 그대로 남습니다」).

### ⑧ 🔴 트리거가 둘이고 월정산도 원장은 운송건별이다

```
  건별    invoices.payment_received                    false → true  (양방향)
  월정산   customer_billing_batches.payment_status → 'paid'
```

🔴 **`lib/rewardAccrue.ts` 하나가 정의처**이고 부르는 곳이 셋이다(건별 저장 · 묶음 ·
입구 라우트). 화면·라우트마다 적으면 한쪽만 고쳐진다(원칙 53번).
🔴 **묶음 한 줄짜리 원장을 만들지 말 것** — 어느 건이 얼마씩 쌓였는지 되짚을 수 있어야 한다.
🔴 **묶음 항목을 읽는 조건(`released_at is null`)은 DB 함수가 쓰는 것과 같아야 한다** —
다르면 **갱신된 건과 적립된 건이 갈린다.**
🔴 **RPC 가 `success` 를 돌려줬을 때만 적립한다** — 그 함수는 실패를 예외가 아니라
`{success:false}` 로 돌려주므로(`batch_not_confirmed`·`already_paid`), 안 보면
**입금 처리가 안 됐는데 적립만 나간다.**

### ⑨ 🔴 체크 해제 = 회수 · 재적립은 수동 조정으로만

`payment_received` 가 `true → false` 로 가면 **`reversal` 로 반대 부호 한 줄**이 들어가고
**원본 적립행은 남는다.** 다시 체크해도 **UNIQUE 때문에 재적립이 막히는데 그것이 맞다** —
돈이 걸린 경로를 자동으로 왔다 갔다 하게 만들지 않는다. 필요하면 **수동 조정**이다.
🔴 **원본 적립행이 없으면 회수도 안 한다**(빈 회수를 만들지 말 것).
🟢 **배차 취소(§5-23)는 정산 전 단계라 적립이 아직 없다** — 손댈 것이 없다.

### ⑩ 🔴 적립 기준은 「기본 운임 공급가액」 하나다

```
  부가세 구분 = 선착불이면 **무조건 「별도」** · 그 밖에는 저장된 값   ← 🚨 ⑲
  공급가액   = splitVat(customer_charge_total − 스냅샷에 섞인 추가비, 그 구분).supply
  적립액     = 내림(공급가액 × 캠페인 요율, **10원 단위**)             ← 🚨 ⑳
```

⚠️ **두 줄이 리뷰에서 바뀌었다** — 착수 시점에는 「저장된 부가세 구분 그대로 · **1원 미만
절사**」였다. 🔴 **이 절의 옛 문장을 근거로 되돌리지 말 것**(⑲·⑳ 에 사유가 있다).
🔴 **부가세를 1.1 로 직접 나누지 말 것** — `splitVat` 이 정의처다(11,000원마다 1원).
🔴 **`Math.round` 가 아니다**(99,999 × 5% = 4,999.95 → **4,990**).
🔴 **요율을 코드에 리터럴로 적지 말 것** — 캠페인에서 읽고 `earn_rate_snapshot` 에 남긴다.
🔴 **빼는 추가비는 그 정산 건 생성 시점에 이미 포함된 것만**이다
(`created_at <= invoice.created_at` · `status='active'` · `correction_invoice_id is null` —
35차 A-7 과 같은 세 규칙). **그 뒤에 등록된 것은 스냅샷에 없으므로 빼면 두 번 깎인다.**
🔴 **추가비를 못 읽으면 0 으로 때우지 않고 `error` 로 돌려준다** — 0 이면 적립이 커지고
청구액 전체를 빼면 0 이 된다. **둘 다 조용히 틀린 값이다.**

### ⑪ 🚨 선착불은 **제외였다가 포함으로 뒤집혔다** (2026-09-21)

⚠️ **아래는 착수 시점(2026-09-20)의 「제외」 근거이고, 다음 날 사용자가 뒤집었다.**
🔴 **되돌리지 말 것** — 지금 선착불은 **적립 대상**이다(⑰). 그래도 이 근거를 지우지
않는 이유는, 「없다」고 봤던 **시점과 기준**을 무엇으로 채웠는지가 ⑰ 에서만 읽히기 때문이다.

선착불(`driver_direct`)은 **화주가 위캐리에 입금하지 않는다.** 운임은 차주가 직접 받고
위캐리가 받는 것은 주선수수료뿐이며 화주 미수금은 **0**이다(§5-12). 그래서 —

```
  ① 「화주 입금 확인」이라는 **사건 자체가 일어나지 않는다**   ← 적립 트리거가 없다   → ⑰ 이 채웠다
  ② `customer_charge_total` 은 **화주가 우리에게 낸 돈이 아니다** ← 적립 기준이 없다  → ⑰ 이 채웠다
```

🔴 **「부담이 크다」로 적으면 다음 세션이 「그럼 요율을 낮춰서 넣자」로 간다** — 이 문장은
**여전히 유효하다**(포함으로 바뀐 뒤에도 매출 대비 비중은 크다 · ⑰).
🔴 **선착불 판정을 새로 쓰지 않았다** — `lib/receivableCalc.ts` 와 같은 값이다.

`created_at.slice(0,10)` 이 **함수가 아니라는 오류**를 낸다. 🔴 **목이 실제와 다른 모양을
주면 시험이 거짓이 된다.**

### ⑳ 🚨 리뷰 5라운드 — 적립 단위 100원 → **10원** (`9bb7440`)

**적립 단위는 같은 차수에 두 번 바뀌었다** — 1원 절사(09-18) → **100원**(09-21) →
**10원**(09-21). 🔴 **100원으로도 1원으로도 되돌리지 말 것.**

담당자가 **월 정산에서 찾아냈다** — 공급가액 **1,172,000원 13건**의 5% 는 58,600 인데
화면이 **58,500** 을 보여줬다. 100원 단위가 **5%가 100원으로 안 떨어지는 건에서 50원씩**
깎은 것이다(65,000 → 3,250 → **3,200** · 125,000 → 6,250 → **6,200**).

🔴 **합계에 5% 를 걸어 58,600 을 만드는 길은 없다** — 적립은 **운송 건별로 원장에 한 줄씩**
쌓이므로(월정산 묶음도 마찬가지) 합계 기준 금액은 원장 줄의 합과 어긋난다. **그 어긋남을
없애려고 단위를 둔 것이고**, 답은 단위를 **줄이는** 것이다.
🟢 10원이면 그 두 건이 그대로 남아 **건별 합 = 합계의 5% = 58,600**.
⚠️ **깎이는 것 자체는 단위를 두는 한 없어지지 않는다**(10원이면 최대 9원).
🚨 **「표시만 10원 단위」로 만들지 말 것** — 적립액 자체를 10원 단위로 낸다. 화면에서만
내리면 **원장 합계(1원)와 화면 잔액(10원)이 갈리고** 건이 쌓일수록 커진다.
🟢 시험에 **이 달의 실제 13건을 그대로 넣어** 「건별 합 = 합계의 5% = 58,600」을 단언으로
못박았다 — 다음에 단위를 건드리면 **그 줄이 먼저 깨진다.**

### ① 🔴 줄 목록을 **행이 아니라 jsonb 배열**로 담았다

한 줄 = 한 행(표)로 두면 ⓐ 순서가 있는 목록이라 `sort_order` 를 줄 하나 지울 때마다
다시 매겨야 하고 ⓑ 저장이 여러 문장(insert·update·delete)으로 쪼개져 **절반만 반영된
상태**가 생긴다. 배열이면 저장이 **UPDATE 한 문장**이라 원자적이고 순서가 곧 배열 순서다.

🔴 **행은 하나뿐이다** — `id boolean primary key default true` + `check (id)`.
원칙 40번(`insurance_rate_settings`)은 **「가장 최근 1행」을 읽는 방식**인데, PR #136 이
그 표가 3행이 되면서 **한 행만 읽는 헬퍼가 조용히 틀린 값을 주는** 일을 겪었다.
여기는 **두 행이 될 수 없게 못박았다** — 그래서 같은 사고가 구조적으로 불가능하다.
🔴 **「나중에 팀별 매뉴얼이 필요할 수 있으니 여러 행으로」로 되돌리지 말 것** —
필요해지면 그때 열쇠를 추가하는 마이그레이션을 쓰는 것이 맞고, 지금 열어 두면
「어느 행이 진짜인가」를 읽는 쪽마다 정해야 한다.

⚠️ 상한은 **60줄 · 한 줄 200자**(`lib/callScript.ts`). 화면이 sticky 로 따라다니므로
무한정 길어지면 안 된다.

### ② 🚨 쓰기 정책을 **아예 만들지 않았다** — 이것이 이 작업의 안전 구조다

```
  쓰기   정책 0개                           →  service_role 인 저장 API 말고는 아무도 못 쓴다
```

🔴 **`call_script` 에 insert/update/delete 정책을 만들지 말 것.** 만드는 순간 `staff`

(19·21차가 세운 규칙 그대로다). 그 함수는 security definer 라 `staff_accounts` 자신의

계정이 지워져도 **매뉴얼 본문은 남아야 한다.**

### ④ 🔴 sticky 를 **계산 카드에서 `.quote-side` 로 올렸다**

그전에는 계산 결과 카드 자신이 `position: sticky` 였다. 패널을 하나 더 두면서

**서로 겹친다.** 그래서 둘을 감싼 `.quote-side` 를 sticky 로 만들고 계산 카드에서는
`position`·`top`·`alignSelf` 를 뗐다. 🔴 **계산 카드에 sticky 를 되돌리지 말 것.**

🔴 **`align-self: start` 를 빼지 말 것** — 격자 항목이라 안 주면 행 높이만큼 늘어나
sticky 가 움직일 자리가 없어진다.

🔴 **안에서 스크롤하는 것은 매뉴얼 목록뿐이다.** 처음에는 `.quote-side` 전체를

⚠️ **폼이 접혀 있으면 따라다니지 않는다 — 고장이 아니다.** sticky 는 **자기 격자 칸

```
  110km 이내            85,000            **85,100**
  400km 이내           225,000           **225,100**
```

`_verify.sql` ㉒-b 의 **`오천배수아님_다마스라보` = 2**(1톤 이상 만원 배수 위반은 0).

100원 오타**로 보인다 — 그 화면은 **클릭이 곧 저장이고 되돌리기가 없다**(65차 ⑨ 가
「10km 이내」 × 게시 차급에만 확인 창을 단 이유이고, 이 두 칸은 게시 차급이 아니라
확인 창 없이 저장된 자리다).

🟢 **이번 통일이 그 두 칸도 함께 정리했다**(80,000 · 215,000).
🔴 **「85,100 이 의도한 값이었다」로 되돌리지 말 것** — 5,000 격자
(`DAMAS_LABO_ROUND_UNIT` · v12 C장)를 깨는 값이고 **반올림이 흡수하지 못한다**.

⚠️ **이것은 문서와 DB 가 갈린 세 번째 사례다**(혼적 30km 15 → 20 · 다마스·라보 적재 한도 ·
이번 100원). 🔴 **적용이 끝난 SQL 의 값을 근거로 「지금 값」을 말하지 말 것 — DB 가 정본이다.**

### ③ 🔴 지시와 다르게 판단한 것 — 차급 역전 검사를 「완화」하되 좁게

기존 검사는 `다마스 < 라보 < 1톤 < …` **엄격 증가**였다(v12 A장 ④ · `_verify.sql` ⑥-b).
다마스 = 라보 가 되면 **그 검사가 15칸 전부를 역전으로 잡아 마이그레이션이 멈춘다.**

🔴 **`<=` 를 전부 `<` 로 바꾸지 않았다** — 그러면 나머지 11쌍의 동가까지 통과해
검사가 통째로 헐거워진다. **다마스↔라보 한 쌍만** 동가를 허용했다:

```sql
  case when oa.vt = '다마스' then b.base_fare <  a.base_fare
                            else b.base_fare <= a.base_fare end
```

🔴 **고친 곳이 둘이고 같은 커밋에 있다** — 마이그레이션 ④(5)와 **`_verify.sql` ⑥-b**.
한쪽만 고치면 다음 `verify` 가 「차급 역전 15칸」으로 빨간불을 띄우고, 그것을 본 세션이
멀쩡한 값을 되돌린다.

🟢 **완화가 정확히 좁은지 재서 확인했다** — 다마스=라보 통과(0) · **라보<다마스 는 여전히
위반(1)**. 즉 「라보가 다마스보다 싸지는 것」은 지금도 막힌다.

🔴 **②의 상태 조건(`접수`·`배차중`)을 지워서 고치지 말 것** — 관리자 「+ 배차 등록」
후보와 **같은 두 단계 판정**이다(PR #167 ⑦). 상태로 좁히고 → 실제 배차가 있는 것을 뺀다.
조건을 지우면 **운송이 끝난 오더까지 「접수」 카드로 되살아난다.**

🔴 **①의 「오더가 있는가」 검사에는 상태 조건을 걸지 않는다** — 이미 운송이 끝난 오더도
「그 견적에는 오더가 있다」는 뜻이다. 좁히면 완료된 건의 견적이 다시 카드로 뜬다.

🔴 **취소된 배차가 있는 오더는 여기 안 걸린다** — 취소도 `dispatches` 행이라 ②의
「배차가 있다」에 해당하고, 그 건은 취소 카드가 이미 말한다.
🔴 **`lib/portalCancelledDispatches.ts` 와 합치지 말 것** — 저쪽은 「있는 배차를 어떻게
보여줄까」이고 이쪽은 「없는 배차를 어떻게 메울까」다.

가상 행의 모양 — 🔴 **셋 다 이유가 있다.**

```
  dispatch_status·pickup_confirmed·delivery_confirmed = null
      → getDispatchStage() 가 0(접수) 을 돌려준다. 화면에서 단계를 따로 정하지 않는다.
  order_id = null
      → getPortalCancelNotice() 가 취소 이력을 찾는 열쇠다. 채우면 「배차가 하나도
        없는 건」에 취소 배지가 붙을 길이 생긴다.
  updated_at = null
      → 이 카드가 생기는 계기는 화주 본인의 승인이다. 「업데이트」 알약을 띄울 일이
        아니다(PR #164 가 배너에서 세운 기준과 같다).
```

🔴 **접수 시각은 `approved_by_customer_at`**(승인한 때)이고 없으면 `created_at` 으로
떨어진다. `created_at`(견적을 만든 때)만 쓰면 **며칠 전에 낸 견적을 오늘 승인한 건이
목록 한참 아래에 묻힌다.**

🔴 **오더번호가 아직 없으면 「견적 20260918007」로 보여준다.** 접두어 「견적」을 빼지
말 것 — 두 번호가 같은 `YYYYMMDD+일련번호` 모양이라 접두어가 없으면 오더번호로 오해한다.
검색으로도 걸린다(`useListSearchSort` 의 `searchFields` 에 `quote_no` 를 더했다).

🔴 **합치기도 정의처가 한다**(`mergePortalPendingRows`) — 홈이 상위 5건만 자르므로 화면이
각자 정렬하면 「홈에 뜨는 5건」과 「조회 맨 위 5건」이 서로 다른 건이 된다.

⚠️ **알아 둘 구멍 하나** — 담당자가 `?from_quote=` 를 거치지 않고 오더를 직접 만들면
`orders.quote_id` 가 비어서 ①이 그 견적을 계속 「오더 없음」으로 본다. 그러면 같은 건이
가상 카드와 진짜 배차 카드로 **두 번** 보인다.
🔴 **새 판정 기준을 만들지 말 것** — 관리자 쪽이 **이미 같은 기준으로** 배지를 띄우고

뒤늦게 잇는 길이다. 🟢 실측상 지금 어긋나 있는 건은 **0건**이다.

### ⑥ 이메일 도메인 고르기 — `EmailField`(리뷰 1라운드)

`[아이디] @ [도메인]` + 아랫줄에 **도메인 고르기** 드롭다운. 목록은 **11종**
(`직접 입력 · naver.com · gmail.com · daum.net · hanmail.net · nate.com · kakao.com ·
outlook.com · hotmail.com · icloud.com · yahoo.com`) — 국내 주요 사이트 공통.
🔴 **임의로 늘리지 말 것**(길어지면 고르는 것이 치는 것보다 느려진다).

🔴 **저장값은 여전히 문자열 하나다**(`contact_email`) — 컬럼을 쪼개지 않았다. 그래서 **DB 0** 이다.
🔴 **아이디·도메인을 별도 state 로 들지 않는다** — **값에서 매번 갈라 읽는다**(마지막 `@`
기준 · `splitEmail`/`joinEmail`). 별도 state 를 두면 프리필·초기화 때 두 값이 조용히 어긋난다.
🔴 **도메인 칸을 잠그지 않았다** — 잠그면 `naver.com` 을 고른 뒤 회사 도메인으로 바꾸려면
「직접 입력」을 먼저 골라야 한다. **고르기는 바로가기일 뿐**이고 손으로 치는 길이 언제나
열려 있어야 한다.
🔴 **고른 값을 따로 기억하지 않는다** — 드롭다운에 보이는 것은 **지금 도메인 값**이 목록에
있으면 그것, 없으면 「직접 입력」이다. 그래서 손으로 고쳐도 표시가 항상 맞는다.
🔴 **아랫줄 배치는 실측해서 정했다** — 칸 셋을 한 줄에 놓으면 3열 격자(한 칸 약 380px)와
360px 화면에서 둘 다 눌린다.

⚠️ **곁다리로 제출 직전 검사 하나를 넣었다**(지시에 없던 것) — 아이디만 적고 도메인을
비우면 `hong` 이 그대로 저장돼 발송도 안 되고 담당자가 원인을 모른다.

오류 문구가 안 뜬다 — PR #121 이 같은 자리에서 겪었다). **빈 값은 그대로 통과**한다.

### ⑦ 🚨 모바일 동의 설명글 — **내 판단이 리뷰에서 뒤집혔다**

최초 커밋에서는 **약관 요약만** 감췄다. 개인정보 카드의 설명이 **개인정보보호법 제15조
2항 1호의 수집·이용 목적 고지**라 감추면 모바일에서만 법정 고지가 사라진다고 봤기 때문이다.
사유를 보고했고 **사용자가 다시 빼라고 결정**해서 두 카드 모두 켰다(그리고 리뷰 2라운드에
`/quote` 까지 넓어졌다).

🔴 **그 옛 판단을 근거로 개인정보 쪽을 되살리지 말 것.**
🔴 **대신 두 가지를 반드시 남긴다** — 카드마다 **「전문 보기」**(처리방침 전문이 목적·항목·

**둘 중 하나라도 감추면 그때는 정말로 법정 고지가 사라진다.**

구조 — 🔴 **감출지 말지는 카드가 정한다.**

```

  CSS(app/landing.css ≤700px)  .landing-consent-desc-wide { display: none !important }
```
🔴 **선택자를 `.landing-consent-desc` 전체로 바꾸지 말 것**(지금은 셋 다 켜져 있지만
「카드가 정한다」는 구조를 유지한다) · 🔴 **`!important` 를 빼지 말 것**(인라인
`display: block` 을 이겨야 한다 — 원칙 58번) · 🔴 **폭을 JS 로 재서 감추지 말 것**
(첫 그림에서 잘못된 쪽이 한 번 번쩍인다).

⚠️ 최초 커밋에서 `APPLY_CONSENT.detail` 을 한 문장으로 줄였다(「승인 여부와 무관하게
안전하게 관리됩니다」를 뗐다 — **법이 요구하는 항목이 아니라 안심 문구**였다).

줄 수가 아깝다고 합치면 **한 화면이 조용히 무채색**이 된다.
🔴 기존 규칙(`.guide-h2`·`.pv2-guide-title`)에 속성을 더할 때는 **선택자를 한 겹 더 써서
특성도로 이겼다**(`.guide-main .guide-h2`) — 순서로 이기게 두면 다음에 누가 이 파일을
정렬할 때 조용히 되돌아간다(원칙 58번).
🔴 **`figure` 는 `width: auto` + `max-width: 100%` 다 — `width: 100%` 로 두지 말 것.**
248px 짜리 사이드바 캡처가 카드 폭까지 늘어나 **뭉갠 채로** 보인다(실제로 그렇게 짰다가 고쳤다).

### ⑦ 리뷰 2·3라운드 — 고객센터 시간, 갈랐다가 도로 합쳤다

2라운드 — *"고객센터 문의 시간 조절이 필요하다.(화주포털내에 표시되는 부분만) 09:00~19:00
으로 바꾸자. 랜딩페이지에서는 이 시간 부분을 뺐는데 랜딩페이지는 없느채로 유지하자."*
→ 상수를 **둘로 갈라**(`COMPANY_SUPPORT_HOURS_PORTAL`) 포털만 19시로 올렸다.
3라운드 — *"공개화면도 19시로 통일하자."* → **값이 같아져 갈라 둘 이유가 없어져 다시 합쳤다.**

🔴 **지금은 `COMPANY_SUPPORT_HOURS = "평일 09:00 ~ 19:00"` 하나뿐이다. 다시 둘로 가르지 말 것** —
값이 같은 상수를 둘로 두면 언젠가 한쪽만 고쳐져 **화주가 로그인 전후로 다른 시간**을 본다
(대표번호 상수 둘이 같은 이유로 「함께 고칠 것」 경고를 달고 있다).
🔴 **`GuideBlock` 의 `only?: "public" | "portal"` 도 함께 지웠다 — 다시 만들지 말 것.**
시간이 갈렸던 그 하루만 쓰던 장치다. 화면을 가르는 일은 항목의 **`scope`** 가 한다 —
블록 단위로 가르면 두 화면이 각각 무엇을 보는지 **코드만 읽어서는 알 수 없어진다**.
사유를 그 타입 위 주석에 남겼다.

🚨 **여기서 하나 잡았다 — 로그인 화면의 시간 줄은 둘이고 뜻이 다르다.**
「접수 기준 당일 발급」 위의 것은 **고객센터 문의 시간이 아니라 발급 약속**이고, 31차가
**랜딩 FAQ(`components/landing/data.ts` 의 `account`)와 일부러 맞춰 둔 값**이었다
(*"두 화면이 다른 시간을 약속하면 지키지 못하는 쪽이 생긴다"* — 그 주석을 읽고 알았다).
2라운드에서 그것까지 19시로 올렸다가 **되돌렸고**, 3라운드에서 **랜딩 FAQ 를 같이 올리면서**
셋을 함께 19시로 맞췄다. 🔴 **이 셋(로그인 · `/apply` 접수완료 · 랜딩 FAQ)은 한쪽만 고치지 말 것.**
🔴 **랜딩 푸터의 운영시간 줄은 그대로 비어 있다**(2026-09-01 에 뺀 것을 사장님이 재확정).

⚠️ **주석을 읽지 않았으면 발급 약속을 조용히 바꿀 뻔했다** — 시간 문자열 하나를 고칠 때도
**그 줄이 무엇을 약속하는지**부터 볼 것.
