### ① 정의처가 `lib/` 이 아니라 부품 파일 안에 있었다

### ② 🔴 끝날은 그 날을 포함한다 — `to` 는 「종료일 **다음 날** 자정」이고 `.lt()` 로 쓴다

화주포털 `Pv2PeriodFilter` 가 PR #155 에서 겪은 그 자리이고, 이번에는 **정의처 주석에

### ③ 🔴 `"YYYY-MM-DD"` 를 `new Date(문자열)` 로 읽지 않는다

`new Date("2026-09-01")` 은 **UTC 자정**이라 KST 에서는 **9월 1일 09:00** 이 된다 —
그대로 쓰면 하루가 밀려 **8월 31일 09:00 이전 건이 딸려 들어온다.** 정규식으로 갈라
`new Date(y, m-1, d)`(로컬 자정)로 만든다. 원칙 41번(`lib/localDateTime.ts`)과 같은 결이다.
🟢 **검증을 `timezoneId: "Asia/Seoul"` 로 돌려 `from === "2026-08-31T15:00:00.000Z"` 까지
확인했다** — 🔴 **이 컨테이너는 TZ 가 UTC 라 그냥 재면 이 버그가 안 잡힌다.**

### ④ 🔴 화주포털 부품을 끌어오지 않았다 (원칙 57번)

`Pv2PeriodFilter` 를 그대로 쓰면 `--pv2-*` 토큰이 `.portal-v2` 스코프 안에만 있어서
**관리자에서는 색이 안 나온다**(PR #145 가 `--pv2-yellow` 로 실측한 자리). 같은 동작을
관리자 생김새(`.date-range-*`)로 옮겼고 **프리셋 계산만 정의처를 함께 쓴다.**
🔴 **프리셋(오늘·이번주·이번달·전체) 계산은 한 글자도 안 바꿨다** — 화주포털과 뜻이
갈리면 같은 「이번주」가 두 값이 된다.
🔴 모바일 규칙은 `.date-range-custom .date-range-date` **두 클래스**다(원칙 58번) —
`.date-range-date` 한 클래스로 내리면 데스크탑 폭까지 같이 줄어든다.

### ⑤ opt-in 이라 나머지 네 화면은 한 글자도 안 바뀐다

`DateRangeFilter` 를 쓰는 관리자 화면은 **여덟**이다(견적·오더·배차·정산 + **화주신청 ·
발주요청 · 공개문의 · 문자이력**). `custom`/`onCustomChange` 를 **선택 prop** 으로 두고
**`onCustomChange` 가 없으면 「직접지정」 버튼 자체를 안 그린다.**
🟢 나머지 넷을 실제로 렌더링해 **프리셋이 여전히 넷**이고 예외 0 인 것을 확인했다.
🔴 **기본으로 켜지 말 것** — 사용자가 고른 것은 네 화면이고, 나머지 넷은 목록 성격이
다르다(신청·문의·문자 이력). 필요해지면 그 화면에서 두 prop 만 넘기면 된다.

### ⑥ 빈 구간을 만들지 않는다

직접지정을 처음 켜면 **이번달 1일 ~ 오늘**로 채운다 — 둘 다 비면 조회 조건이 없어져

노란색으로"* 가 **그 사실을 알고 하는 말**로 읽혀 **같은 토큰**을 쓰기로 했고(보고함),
종류는 「발주요청」 배지와 상태 캡이 말하게 했다. 🔴 **새 색을 만들어 갈라놓지 말 것** —
둘 다 「담당자가 지금 손대야 하는 줄」이고, 색을 늘리면 뜻을 잃는다.

🟢 **리터럴을 토큰으로 바꿨다** — 발주요청 행의 `#FFFBEB` 도 같은 변수를 읽는다.
🔴 **화면 파일에 리터럴로 다시 적지 말 것**(갈리면 두 줄이 미묘하게 다른 노랑이 된다).

🔴 **모바일 카드에도 같이 걸었다**(원칙 13번) — `AdminMobileList` 에 `highlight` prop 신설.
한쪽만 칠하면 **같은 목록이 화면 크기에 따라 다르게 읽힌다.**

### ③ 상세 입력 접기 — 🔴 `<details>` 가 아니라 state + **조건부 렌더**

경계는 사용자 말 그대로 **「화주 업체 검색」까지**다. 항상 보이는 것은 기존 화주/개인
토글 · 정산방식 · 화주 업체 검색(또는 개인 고객 두 칸)이고, **블록 1~4 와 저장 버튼**이
접힌다.

🔴 **`<details>` 를 쓰지 않았다** — 열림을 **코드가 정해야 하는 자리가 넷**이라
(화주 선택 · 개인/신규 전환 · 프리필 진입 · 저장 성공 후) `<details>` 로는 **사용자가 연
것과 코드가 연 것을 구분할 수 없다.** 함정 22번과 같은 이유다.

🔴 **`display: none` 으로 숨기지 않았다 — 조건부 렌더다.** 숨긴 채 두면 `required` 가
달린 주소 칸(`AddressSearch` 둘)이 DOM 에 남아 브라우저가 *"An invalid form control is
not focusable"* 로 **제출을 조용히 막는다.** 폼 값은 전부 `form` state 에 있어서 떼었다
붙여도 **잃는 것이 없다**(실측 — 접었다 펴도 고른 화주가 남는다).

```
  펼치는 자리 넷
    화주를 고르면            회사 검색 결과 클릭 핸들러 안 (사용자 확정 「회사명 입력시」)
    개인/신규 고객으로 바꾸면  고를 화주가 없으니 바로 (한쪽만 두면 반쪽 기능이 된다)
    프리필로 들어오면         useState 초기값 (?from_request= · ?from_quote_request=)
    손잡이를 누르면          토글
  접는 자리 둘
    손잡이를 누르면          토글
    저장에 **성공**하면       🔴 실패 분기는 전부 그 줄에 닿기 전에 return 한다
```

🔴 **저장에 실패했을 때 접지 말 것** — 값은 남지만 담당자는 **방금 적은 것이 통째로
사라진 것처럼** 본다. `handleSubmit` 의 실패 분기 12개가 전부 `setDetailsOpen(false)`
앞에서 `return` 하는 것을 실측으로 확인했다.

🔴 **손잡이 화살표는 글자가 아니라 SVG 다.** 처음에 `▸`·`▾` 를 넣었는데 렌더링을 재 보니
**폭 6px · 높이 14px** 로 그려져 **손잡이인지 알아볼 수 없었다**(본문 서체 SUIT 에 맞는
글리프가 없어 위쪽에 작게 붙는다). **PR #129 의 `⋯` 가 네모 상자로 나오던 것과 같은
자리**다 — 🔴 **글자로 되돌리지 말 것.** 지금은 14×14 인라인 SVG 이고 펼치면 90° 돈다.

🟢 **실측 — 목록 머리 y 가 `2005px → 635px`.** 사용자가 말한 *"그러면 견적목록도 한눈에
들어올것 같다"* 가 그대로 나왔다(1,370px).

⚠️ **접힌 상태에서 「몇 가지를 더 적어야 하는지」를 말한다** — 손잡이만 두면 「여기서
끝인가」로 읽힌다. 모바일(≤700px)에서는 그 안내가 줄을 밀어내서 감춘다.

🟢 **실측 대비 4.52 ~ 6.37:1 — 다섯 종 전부 WCAG AA 통과**(수주가 4.52 로 가장 낮다).

🔴 **모양은 `.status-cap`(globals.css), 색은 매핑이 인라인으로 준다** — 색을 CSS 로 옮기면
상태가 늘 때 두 곳을 고쳐야 하고, 갈리면 「목록에서만 회색인 상태」가 생긴다.

🔴 **발주요청 고정 행의 「대기중」도 같은 캡으로 그렸다** — 한쪽만 캡이면 같은 칸에 두
종류의 글씨가 섞여 상태를 훑는 눈이 걸린다(렌더링을 보고 뒤늦게 고친 자리다).

### ⑤ 운송오더 목록 「+ 배차 등록」 — 🔴 `status` 로 가르지 않는다

대상은 **배차가 없는 오더 전부**다(사용자 확정). 방금 등록한 건만 보여주면 **어제
등록하고 배차를 못 건 오더**에는 같은 길이 없어 담당자가 두 화면을 오간다.

🔴 **`orders.status` 만 보고 가르지 말 것** — `배차중` 은 배차를 걸면 자동으로 붙지만
담당자가 드롭다운에서 **손으로도 바꿀 수 있어서**, 그것만 보면 배차가 없는데도 버튼이
사라진다. `dispatches` 에 `order_id` 를 물어서 실제로 있는지 본다.
🟢 **무겁지 않다** — 운영 `dispatches` 는 실측 6행이다(PR #144 `verify` ⑮).

🔴 **`취소` 만 뺀다** — 취소된 건에 배차를 걸 일은 없고 버튼이 보이면 실수로 누른다.
`운송완료` 인데 배차가 없는 것은 **데이터가 어긋난 것이라 오히려 보여야 한다.**

🔴 **조회에 실패하면 감추지 않는다**(원칙 55번) — `null` 이면 전부 그린다. 없는 것을
있다고 하는 쪽이 「버튼이 통째로 사라졌다」보다 낫다.

🔴 **데스크탑 표와 모바일 카드에 같은 조건으로 그렸다** — 모바일은 상태 드롭다운 **아래**에
세로로 쌓는다(`action` 안이라 눌러도 카드 이동이 안 일어난다).

### ⑥ 차주 지급운임 필수 — 🔴 **배차확정에서만** 막는다

🔴 **등록 단계는 비워둘 수 있어야 한다**(사용자 확정) — 그때는 차주도 운임도 아직 협의
중이다. 확정은 「이 조건으로 간다」는 선언이고, 거기서 금액이 비면 **정산 자동등록이
0원으로 굳는다.**

🔴 **`> 0` 이 아니라 「비었는가」로 본다** — 0원 배차가 실무에 있을 수 있고(사급·회차 등)
그것까지 막으면 확정 자체를 못 한다. **막는 것은 누락이다.**

🔴 **화면 판정과 `handleConfirm()` 검사는 같은 조건이라야 한다**
(`String(editForm.driver_payout ?? "").trim() === ""`) — 갈리면 「노랗게 강조는 되는데
확정은 되는」 또는 그 반대가 된다.

🔴 **값이 있으면 강조를 끈다** — 다 채운 화면이 통째로 노래지면 강조가 뜻을 잃는다.
🔴 **`required` 를 붙이지 않았다** — 이 칸은 `<form>` 안이 아니라 버튼으로 저장하는
화면이라 네이티브 검사가 걸리지 않는다. 막는 자리는 `handleConfirm()` 하나뿐이다.

🟢 **착수 전 확인에서 지시서 걱정 하나가 사라졌다** — 「저장 경로가 달라서 확정 때
`driver_payout` 이 안 들어갈 수 있다」였는데, 실측하니 **`handleConfirm()` 이 이미
payload 에 넣고 있었다**(`driver_payout: editForm.driver_payout ? Number(...) : null`).

### ⑦ 배차 중복등록 — 🔴 **원인이 둘이었다**

```
  (1) 후보 목록이 안 줄었다
      DISPATCH_TO_ORDER_STATUS["접수중"] === "배차중" 인데
      후보 조건이 .in("status", ["접수", "배차중"]) 이라
      → 배차를 걸어 오더가 「배차중」이 된 뒤에도 후보에 그대로 남았다
  (2) 닫은 폼이 저절로 다시 열렸다
      ?from_order= effect 가 [fromOrderId, availableOrders] 에 걸려 있어
      loadAvailableOrders() 가 끝날 때마다 다시 돌며 setShowForm(true) 를 불렀다
```

🔴 **(1) 은 상태 조건을 지워서 고치지 말 것** — 담당자가 드롭다운으로 손수 `배차중` 으로
바꿔둔, **배차가 없는 오더는 후보여야 한다.** 그래서 「상태로 좁히고 → 실제 배차가 있는
것만 뺀다」 **두 단계**다. 🔴 한 단계로 줄이면 반드시 한쪽이 틀린다.

🔴 **(2) 의 ref 가드를 지우지 말 것**(`autoSelectedOrderRef`) — 한 오더당 한 번만 돈다.

그리고 **등록을 마치면 그 배차의 상세로 넘긴다**(사용자 지시 *"…접수중인 목록의 상세
페이지가 나와서 바로 차주정보채우기 쪽으로 이어지면 좋겠다"*). 37차가 만든 **차주 정보
붙여넣기 칸이 「접수중 + 외부 배정」 분기 안에** 있어서 그대로 이어진다.
🔴 **id 를 못 받았으면 목록에 남는다** — 없는 주소로 보내면 「등록은 됐는데 화면이
깨졌다」가 된다. 그래서 `.select("id").single()` 이다.

🟢 **두 고침이 서로를 받쳐 준다** — 상세에서 뒤로 와도 그 오더는 이미 후보에서 빠져
있어 `availableOrders.some(...)` 이 false 가 되므로 폼이 안 열린다.

🔴 **곁다리 — `loadAvailableOrders()` 가 `error` 를 버리고 있었다**(원칙 55번). 조회가
실패하면 후보가 빈 채로 조용히 「배차할 오더가 없습니다」가 되어 단서가 안 남는다.

### ⑧ 배차확정 오류 — 🔴 **`alert` 이 아니라 원칙 33번의 전체화면 가드였다**

사용자는 *"새로운 페이지에서 오류가 뜬다"* 고 신고했다. 원인은:

```
  app/admin/dispatches/[id]/page.tsx
    if (error || !dispatch) {           ← 액션 실패까지 이 state 를 쓰고 있었다
      return <main>배차 정보를 불러오지 못했습니다. {error}</main>
    }
    ...
    {error && <div className="error-box">오류: {error}</div>}   ← 한 번도 안 그려졌다
```

🔴 **아래 배너는 위 가드가 먼저 `return` 해서 존재한 적이 없다.**
🔴 **PR #153 이 운송오더 상세에서 고친 바로 그 버그가 여기 남아 있었다** — 그때 「범위를
내가 넓혀서」 오더 상세 10곳을 갈랐는데 배차 상세는 안 봤다. **이 저장소에서 네 번째다.**

→ `error`(로딩 실패 · `load()` 안 한 곳)와 `actionError`(액션 실패 · 20곳)를 갈랐고,
`actionError` 에 **`scope`** 를 뒀다.

```
  scope      그리는 자리                  담는 것
  page       페이지 머리                  상태 변경 · 정산 자동등록 · 삭제 등
  confirm    배차확정 버튼 바로 위         handleConfirm() 의 검사·저장 실패 (내부·외부 분기 둘 다)
  save       「변경사항 저장」 버튼 바로 위  handleSave() 의 검사·저장 실패
```

🔴 **`scope` 를 하나로 되돌리지 말 것** — 맨 위 한 곳에만 그리면 배차확정 버튼에서
**1,000px 넘게 떨어져** 「아무 일도 안 일어난다」가 된다(**PR #154 의 교훈**).
🟢 실측 — 오류가 **버튼 54px 위**에 뜬다.

### ① 「왕복,편도 드롭메뉴 안됨」의 정체는 **키 한 글자**였다

```
app/quote/page.tsx   surcharge["왕복편도"]   ← 슬래시가 없다
```

`rate_surcharges.category` 의 실제 이름은 **`왕복/편도`**(슬래시 포함)다. 이 화면만
빠뜨려 그 칸이 **빈 배열**이 됐고, 드롭다운을 눌러도 항목이 하나도 없었다.
🔴 **예외도 경고도 나지 않는다** — 원칙 55번과 같은 결의 조용한 실패다.

🟢 **다른 화면 넷은 전부 맞았다**(포털 발주요청 4곳 · 관리자 견적 등록·상세 · 포털
견적확인). 같은 파일의 `물품특성`·`운송시간` 도 맞았고 **`왕복/편도` 하나만** 틀렸다.

🔴 **재현했다** — 목 데이터 3종을 내려주고 키에서 슬래시를 뺀 판본으로 실제 렌더링:
고치기 전 `[]` → 고친 뒤 `["편도","왕복","회수/재방문"]`. **신고와 정확히 일치했다.**

🔴 **`SURCHARGE_KEYS` 상수를 두고 세 칸 모두 그것으로 바꿨다** — 화면에서 카테고리
문자열을 직접 적지 말 것. 이번에 고친 버그가 정확히 「직접 적다가 슬래시를 빠뜨린 것」이다.

### ② 필수 표시는 **정말 0건**이었고, 리뷰에서 빨간 `*` 로 뒤집혔다

착수 전 실측: `req-marks`·`field-required`·`required` **전부 0건**. 카드 제목만
「필수 입력」이고 실제로 제출을 막는 넷 옆에 톤수·차종·운송물건이 **똑같은 모양**으로
섞여 있었다.

본작업에서는 `/apply` 에 이미 있던 `requiredMark`(회색 「필수」 글자)를
`components/landing/form/Fields.tsx` 로 옮겨 정의처를 하나로 만들었다.
🔴 **그런데 리뷰 1라운드에 사용자가 빨간 `*` 로 바꾸라고 했다** — 31차 리뷰가 확정했던
「빨간 `*` 가 아니라 회색 「필수」 글자」가 **뒤집힌 것이다. 그 옛 결정을 근거로
글자로 되돌리지 말 것.**

🔴 **범위가 화주포털까지 넓어졌다**(사용자 지시 *"이부분은 화주포털 발주요청도 마찬가지로"*).
⚠️ **포털에 필수 표시가 없던 게 아니었다** — **검정 `*` 가 부제와 placeholder 안에
문자로** 박혀 있었다(`"상차지 정보 *"` · `"출발지 주소 검색 또는 직접 입력 *"`).
🔴 **placeholder 는 값을 입력하면 사라져서 표시 역할을 못 한다** — 제목 옆으로 옮겼고
문자 `*` 는 지웠다. **문자로 되돌리지 말 것.**

🔴 **색은 한 값(`#B4423A`)이고 정의처를 둘로 갈랐다** — 공개 폼은 `Fields.tsx` 의
`REQUIRED_MARK_COLOR`(인라인 style), 포털은 `globals.css` 의 `.pv2-req`.
**공개 폼 부품을 포털에 import 하지 않으려고 가른 것**이고(원칙 57번),
🔴 **한쪽을 고치면 반대쪽도 같이 고칠 것.** 실제로 그려서 **색·크기·굵기가 같음을
확인했다**(`rgb(180,66,58)` · 15px · 700).
🔴 **`--pv2-*` 토큰을 새로 만들지 않은 것은 의도다** — 만들면 포털 전용이 되어 공개 폼과
값을 맞출 수 없다(PR #145 가 같은 판단을 했다).

🟢 **`/apply` 도 같은 정의처라 함께 바뀌었다** — 사용자가 든 것은 앞의 둘이지만
`/apply` 만 회색 글자로 남으면 공개 폼 둘이 갈린다. **merge 보고에 밝혔다.**
🔴 **동의 카드(`LandingConsentCard`)의 자체 「필수」 배지는 안 건드렸다** — 그것은
라벨 옆 표시가 아니라 카드 제목 옆 배지이고 12px `#8B8A85` 로 성격이 다르다.

⚠️ **네이티브 `required` 를 쓰지 않는 것은 그대로다**(폼에 `noValidate` 가 있다) —
브라우저 검사가 React 핸들러보다 먼저 걸리면 우리 오류 문구가 안 뜬다(PR #121).
**표시는 안내이고 막는 것은 제출 직전 검사다 — 둘이 어긋나지 않게 할 것.**

🟢 **곁다리 — 제출 검사 순서를 화면 순서와 맞췄다.** 출발지가 비었는데
「성함(업체명)과 연락처를 입력해주세요」가 뜨고 있었다. 「필수」 표시와 안내가
서로 다른 곳을 가리키면 안 된다.

### ③ B장 — 일정을 발주요청과 맞췄다

착수 전 실측에서 **`/quote` 가 `DateTimePicker` 를 아예 안 쓴다**는 것이 드러났다.
자체 부품 `DatePicker`(달력) + `Dropdown`(시간, `timeSlots()` 06:00~22:00 30분)
**두 칸**이고, 빠른 버튼은 `quickDateButtons` 의 **「오늘」·「내일」 둘뿐**이었다.
하차 하한은 `minKey` 로 **날짜만** 막고 **+30분이 없었다.**

넣은 것 넷 — 상차 **「지금」 칩** · 하차 **「당착」·「내착」 칩** · **하차 +30분 하한**
(`lib/dropoffGap.ts`) · **안내 한 줄**.

🔴 **포털 부품(`components/pv2/Pv2DateTimeField.tsx`)을 끌어오지 않았다** — `.pv2-*`
스코프가 통째로 딸려온다(원칙 57번). **같은 동작을 랜딩 생김새로 옮긴 것**이고
자리 채움 시각(`ARRIVAL_FILLER_TIME`)과 하차 하한만 정의처를 함께 쓴다.
**36차 PR 2 가 관리자에 한 것과 같은 방식이다.**

🔴 **칩이 켜지면 날짜·시간 칸을 잠근다** — 「지금」·「당착」은 **시각을 담지 않는
선택지**라 손으로 고친 값이 남아 있으면 무엇이 요청인지 갈린다. `Dropdown`·`DatePicker`
에 `disabled` 를 넣었고 🟢 **둘 다 `/quote` 한 화면만 쓴다**(전수 확인) — 그것이
다른 화면 무회귀의 근거다.

🔴 **당착·내착이면 특이사항에 하차 일시를 적지 않는다** — `23:59` 는 자리 채움이라
「23:59 도착 요청」으로 읽히면 안 된다. `arrivalNoteLine()` 한 줄을 대신 쓴다.
**견적 전환 프리필과 같은 줄**이라 중복 판정이 성립한다.
🔴 **당착·내착은 +30분 하한의 예외다**(27차·36차 D장) — 규칙을 걸면 23:40 상차 건이 막힌다.
🔴 **`public_quote_requests` 에 도착구분 컬럼을 만들지 않았다**(28차와 같은 판단).

🔴 **상차 날짜를 바꾸면 당착·내착이 따라간다** — 안 따라가면 「당착」이라 적혀 있는데
하차 날짜는 옛 상차일에 묶인 상태가 되고, **칸이 잠겨 있어 손으로 못 고친다.**
🔴 **날짜 더하기는 `Date` 로 한다** — 문자열을 자르면 월말(09-30 → 10-01)에서 어긋난다.

🟢 **같은 날이면 상차 +30분보다 이른 시각을 목록에서 아예 뺀다**(달력은 날짜만 막는다).
그래서 **제출 직전 검사가 필요한 경우는 「나중에 상차를 늦췄을 때」뿐이다** —
시험 시나리오를 그렇게 짜야 재현된다(처음엔 슬롯이 막아서 재현이 안 됐다).

### ④ C장 — 운송시간 자동선택. **관리자에 이미 있었고 틀렸다**

🔴 **착수 전 확인에서 가장 값이 컸던 발견이다.** `app/admin/quotes/page.tsx` 에
「희망 상차일시 → 운송시간 자동선택」이 **이미 있었고 결함이 둘**이었다.

```
  ① 출퇴근/혼잡(+10,000)·새벽(+20,000)을 아예 안 썼다
     `hour < 8 || hour >= 20` 을 전부 「평일 야간」으로 봐서 새벽 3시도 야간이었다
  ② `options.find(o => o.includes("평일") || o.includes("주간"))`
     `평일 주간`·`평일 야간`이 둘 다 「평일」을 포함해서 배열 순서로 먼저 오는 쪽이 잡혔다
```
🔴 **부분일치로 되돌리지 말 것.**

규칙 정의처는 **`lib/transportTimeAuto.ts` 하나**이고 **세 화면**이 쓴다
(견적문의 · 화주포털 발주요청 · 관리자 견적 등록).

```
  토·일                주말            (🔴 시간대보다 먼저다)
  00:00 ~ 05:59       새벽            +20,000
  06:00 ~ 07:59       출퇴근/혼잡      +10,000
  08:00 ~ 17:59       평일 주간        0
  18:00 ~ 19:59       출퇴근/혼잡      +10,000
  20:00 ~ 23:59       평일 야간        +10,000
```

⚠️ **그래서 18:00~19:59 상차 건의 견적이 0원 → +10,000원으로 오른다.**
🔴 **사용자 확정이다**(AskUserQuestion — 「여섯 종 전부 자동」). 06:00~07:59 는
지금도 +10,000 이라 **이름만** 바뀐다. **금액이 바뀌는 자리라 물어서 확정받았다.**

🔴 **주말이 시간대보다 먼저다** — 기존 동작을 그대로 둔 것이다. 바꾸면 주말 새벽 건이
`주말`(+10,000) → `새벽`(+20,000)으로 **또 금액이 오른다.**
⚠️ 새벽이 더 어려운 시간이라 반대가 맞다는 의견이 있을 수 있다 — 🔴 **바꾸려면 먼저 물을 것.**

🔴 **`공휴일`은 자동으로 못 고른다** — 저장소에 공휴일 달력이 없다. 목록에는 그대로 있어
담당자·화주가 직접 고른다. 🔴 **달력을 하드코딩하지 말 것**(매년 바뀐다).

🔴 **실제로 내려온 선택지 목록 안에 있을 때만 값을 준다**(`autoTransportTime` 의
`available` 인자) — 이름이 바뀌면 틀린 값을 넣는 대신 **아무것도 안 고른다.**
`option_name` 완전일치라 한 글자만 달라도 가산이 조용히 빠지는 자리다.
🔴 **`available` 을 생략 가능하게 만들지 말 것.**

🟢 **직접 바꾼 값은 남는다.** 다만 **상차일시를 다시 고치면 또 자동으로 맞춰진다** —
관리자 화면이 전부터 그렇게 동작했고 세 화면이 같아야 한다.

### ④ 페이지 내 「업데이트」 표시 — 배너와 **별개로 넓다**

`components/pv2/Pv2UpdatedMark.tsx` · `lib/usePortalSeenAt.ts` 신규. 견적 확인 ·

배너를 좁힌 만큼 **무엇이 바뀌었는지는 목록이 말해야** 하고, 그래서 「상차완료 알림은
빼되 화면에서는 보이게」가 둘 다 성립한다.

민다(배지를 0으로 만들려고). 목록이 그 뒤에 `getLastSeen()` 을 읽으면 **언제나
「바뀐 것 없음」**이다. 🔴 **화면에서 `getLastSeen()` 을 직접 읽지 말 것.**
🟢 **순서는 React 가 보장한다** — 자식(페이지) effect 가 부모(셸) effect 보다 먼저 돈다.
게다가 셸은 `markSeen` 전에 세션·계정을 `await` 하므로 **두 겹으로** 안전하다.

하이드레이션에서 값이 갈린다.

(배너의 「첫 조회에는 울리지 않는다」와 같은 결).
🔴 **발주 요청 행에는 안 붙인다** — 그 행은 `대기중` 아니면 `반려` 뿐이고 반려는 빨간
「접수 반려」 알약으로 이미 눈에 띈다. 같은 뜻의 표시가 두 개가 된다.

### ⑤ 시각 비교는 **문자열로 하면 뒤집힌다**

🔴 Postgres 는 `…+00:00`(마이크로초), `toISOString()` 은 `…Z`(밀리초)라 **형식이 다르다.**
형식이 다르면 사전순은 못 믿는다 — **실측**:

```
  "2026-09-16T12:00:00.500+00:00" > "2026-09-16T12:00:00Z"   →  false   (`.` < `Z`)
  Date.parse 로 재면                                          →  true    (실제로 500ms 뒤)
```

🔴 **`isUpdatedSince()` 를 문자열 비교로 되돌리지 말 것.**
⚠️ **밀리초 아래는 `Date.parse` 가 버린다** — 기준값과 같은 밀리초에 바뀐 건은 표시되지
않는다. 그 한 건은 **화주 본인이 방금 일으킨 것**이라 실무에서 문제가 되지 않는다.
🔴 이것을 고치겠다고 문자열 비교로 돌아가지 말 것(위 함정이 훨씬 자주 걸린다).

### 🔴 두 신고가 한 뿌리였다

`lib/generateNumber.ts` 가 번호를 **「그날 만들어진 행 수 + 1」**로 만들고 있었다.

```
  오늘 001 · 002 · 003 을 만들고  002 를 지우면
    → 건수가 2 라 다음 번호가 003
    → 003 은 이미 있으므로 유니크 위반
    → 🔴 다시 눌러도 **같은 번호**를 뽑으므로 영영 실패
```

그리고 **발주요청은 「견적이 저장되는 순간」에 `승인됨` 이 된다**
(`app/admin/quotes/page.tsx` 의 `if (fromRequestId && newQuote)` — 화면 주석이
*「실제 상태 변경은 그 견적이 저장되는 순간 자동으로 처리됩니다」*라고 적고 있다).
insert 가 실패하면 `newQuote` 가 null 이라 그 블록이 안 돌고, 요청이 `대기중` 으로 남아
**「화주요청」 배지가 안 사라진다.**

🔴 **오류 메시지 한 줄과 배지 한 개가 같은 원인이었다** — 신고를 둘로 보고 각각
고치러 갔으면 배지 쪽에서 멀쩡한 코드를 한참 봤을 것이다.

### 🔴 코드부터 열지 않고 운영 DB 를 쟀다

`_verify.sql` 에 **㉔** 을 신설해서 `verify` 를 돌렸다:

```
  ㉔-a 견적번호 | 20260916 | 건수 2 | 최대번호 3 | 빈 번호 있음(삭제됨)   ← 이것
       견적번호 | 20260915 | 건수 3 | 최대번호 3 | OK
  ㉔-b 오더번호 | 다섯 날짜 전부 OK
  ㉔-c 실제 중복                                   0행(제약이 막고 있다)
  ㉔-d 제약     quotes_quote_no_key · orders_order_no_key  둘 다 UNIQUE
  ㉔-e 발주요청 | 대기중 1 · 승인됨 7             ← 저장이 막힌 그 건
```

🟢 **신고와 정확히 일치했다.** 🟢 **`orders` 에도 유니크 제약이 이미 있어서** 제약을
새로 거는 마이그레이션이 필요 없었고 그래서 **DB 변경이 0** 이다.

### 고친 것

🔴 **「그날 최대 번호 + 1」이다.** 지워진 번호는 다시 쓰지 않고 비워 둔다 —
**번호는 연속이 아니라 유일하기만 하면 된다.**

🔴 **동시 저장은 번호 계산만으로 막을 수 없다**(§7 의 「먼저 조회해서 없으면 insert」
함정). 두 사람이 같은 순간에 누르면 **둘 다 같은 최대값을 읽는다.** 그래서 **DB 유니크
제약을 방어선으로 두고 위반(`23505`)이면 번호를 다시 뽑아 재시도**한다 —
**`insertWithDailyNumber()` 한 곳**이고 상한 5회다.
🔴 **번호만 뽑아 쓰지 말고 그 함수를 쓸 것**(그래서 `generateDailyNumber` 를 export 에서
없애고 내부 함수 `nextDailyNumber` 로 바꿨다).
🔴 **호출부에서 `quote_no`·`order_no` 를 직접 넣지 말 것** — 함수가 채운다. 직접 넣으면
**재시도가 같은 번호를 다시 쓴다**(주석으로 못박았다).

🔴 **번호가 아닌 다른 유니크 위반은 재시도하지 않고 원문을 그대로 올린다** —
`error.code === "23505"` 만 보고 재시도하면 다른 유니크 컬럼(예: 사업자번호)이 겹친
경우에 몇 번을 다시 해도 같은 실패이고 **그동안 진짜 원인 메시지만 가려진다.**
`isDuplicateNumberError()` 가 **메시지·details 에 그 컬럼명이 있는지**까지 본다.

🔴 **조회 실패를 `001` 로 때우지 않는다**(원칙 55번) — 그러면 **그 자체가 중복**이 되어
화면에 **「중복」이라는 엉뚱한 원인**이 뜬다. 실패는 실패로 올리고 insert 를 아예 안 한다.

🔴 **`created_at` 이 아니라 번호 문자열로 그날을 고른다** — 번호에 박힌 날짜는 **로컬
날짜**인데 `created_at` 은 `timestamptz` 라 그 둘을 섞으면 **자정 전후에 어긋난다**
(원칙 41번과 같은 결).

🔴 **하루 1,000건을 넘어도 숫자로 비교한다** — `limit(1)` + 내림차순 정렬로 바꾸면
번호가 문자열이라 **`"1000" < "999"`** 가 되어 최대값을 잘못 집는다. 그날 것을 전부
받아(`DAILY_SCAN_LIMIT = 2000`) 코드에서 `parseInt` 로 비교한다. 형식이 깨진 옛 번호는
**건너뛴다**(`Number()` 로 바꾸면 `NaN` 이 최대값을 오염시킨다).

🟢 **`orders` 도 같은 함수를 쓰므로 함께 고쳐졌다.**
