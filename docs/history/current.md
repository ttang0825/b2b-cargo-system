### ③ B장 — 배차확정이 두 통이 됐다

```
  배차확정 저장 성공
    → 확인창 (1/2) 화물정보 안내 — 차주      [건너뛰기] [발송]
    → 확인창 (2/2) 배차확정 안내 — 고객      [건너뛰기] [발송]
```

🔴 **차주가 먼저다** — 고객이 문자를 받고 바로 전화하면 담당자가 응대가 되려면 차주 배차가
먼저 확정돼 있어야 한다. 🔴 **차주 키는 `dispatch_confirmed` 그대로**이고 **라벨만**
「배차확정 안내」 → **「화물정보 안내」**다(키를 바꾸면 옛 이력이 이름을 잃는다).

🔴 **라우트는 한 번에 한 통만 돌려주고 큐는 화면이 든다** — 지시서는 라우트가 **두
미리보기 배열**을 돌려주는 설계였는데, 그러면 **수동 버튼이 한 통만 띄울 수가 없다**
(「차주에게만 다시」를 눌렀는데 고객 창까지 지나간다). `lib/notifyDispatchSms.ts` 에
`fetchDispatchSmsPreviewByEvent()`(수동 · 단건) / `fetchDispatchSmsPreview()`(자동 · 배열)
둘을 뒀다.

🔴 **공용 `SmsConfirmModal` 을 두 통 동시 편집 창으로 뜯어고치지 말 것** — 그 창을 쓰는
**다른 다섯 곳**(화주신청 승인·거절 · 계정발급 · 비밀번호 재발급 · 견적)이 같이 흔들린다.
더한 것은 **선택 prop `step` 하나**뿐이고 **다섯 호출부 diff 0** 이다.

🚨 **`key={preview.templateType}` 가 없으면 둘째 창에 첫 통의 본문과 수신번호가 그대로
남는다** — 모달이 `useState(preview.message)` 로 초기값을 잡기 때문이다. **빼고 실제로
렌더링해 확인했더니 고객에게 차주 문구가 차주 번호로 나갔다.** 🔴 **지우지 말 것.**

🔴 **빈 칸 규칙이 두 문구에서 정반대다.**

```
  차주 「화물정보 안내」   빈 칸은 줄째 뺀다     「미정」·「-」를 찍지 않는다
  고객 「배차확정 안내」   기사 정보가 비면 「미등록」
```

차주용은 사용자 원문이 *「기입되어 있는 선안에서」* 이고, 없는 정보를 있는 것처럼 적으면
차주가 그 글자를 보고 전화를 걸 수 없다. 고객용은 **이 문자의 목적이 기사 정보 확인**이라
줄째 빠지면 담당자가 빠진 줄 모르고 보낸다 — 확인창에서 「미등록」이 보여야 채우고 보낸다.
🔴 **같게 만들지 말 것.**

🔴 **차주 문자에 화주 대표 연락처를 넣지 말 것** — PR #73 이 뺀 이유(*「오더 1건에 화주

칸을 따로 만들면서 해소됐고**, 들어가는 것은 **그 칸**이다(배차 값 → 비었으면 오더 값).
🔴 **두 문자 모두 운임·수수료·마진 0건** · 🔴 **고객 문자는 품목·특이사항도 0건**
(특이사항에 내부 메모가 섞인다).

🚨 **§5-4·§5-23 의 「차주 성명·연락처·차량번호 비노출」은 화면 기준이다** — 이 문자로는

### ⑤ 🚨 곁다리 — 날짜가 9시간 어긋나고 있었다

문구 함수는 **서버 라우트**에서 도는데 Vercel 함수의 시간대는 **UTC** 이고, 포맷터가
`getHours()`·`getDate()` 를 쓰고 있었다. 실측:

```
  KST 2026-09-18 00:00  →  getHours() 15      9시간 어긋남
  KST 2026-09-18 09:00  →  getHours()  0      ← 날짜까지 하루 앞으로 밀린다
```

🟢 **실피해는 없었다** — 배차확정 문자 발송 이력이 **0건**이다(㉚-c). 그런데 이 차수가
두 통에 일시를 **네 줄** 찍으므로 그대로 두면 바로 사고가 난다.
`Intl.DateTimeFormat` 에 **`timeZone: "Asia/Seoul"`** 을 명시해 고쳤고, 같은 함수를 쓰는
**견적 폴백 LMS 도 함께 맞아졌다.** 🔴 **되돌리지 말 것.**
🔴 **사용자에게 먼저 보고하고 승인받은 뒤에 고쳤다**(범위를 내가 넓힌 것이다).

🔴 **하차 `23:59` 는 시각이 아니라 당착·내착 자리 채움이다**(`lib/arrivalType.ts` ·
운영 오더 **3건** 실재 ㉚-g). 두 문자 모두 그런 건은 **날짜만** 찍는다 —
`ARRIVAL_FILLER_TIME` 을 import 했고 **새 리터럴 0건**이다.

### ⑥ C장 — 머리말 하나 · 견적 버튼 이름 · 재발송 제목 결함

**머리말은 `SMS_HEADER` 하나다**(`[위캐리운송]`). 7종이 전부 이 상수를 쓰고 **견적 LMS
제목**도 같다 — ⚠️ 그 제목에는 **띄어쓰기가 있었다**(`[위캐리 운송] 견적 안내`).
🔴 **이메일 2건의 영문 머리말은 범위 밖이다**(Resend 미가동 · diff 0).
🔴 **이미 나간 문자의 본문·제목은 고치지 않는다** — `sms_logs` 를 UPDATE 하지 말 것.
🟢 **견적 링크 문자는 상수로 바꾼 뒤에도 87byte 그대로다**(여유 3byte).

🚨 **재발송이 87byte 견적 단문에 제목을 붙여 LMS 로 올리고 있었다.** 솔라피는 제목이
있으면 단문을 장문으로 올린다. `send-sms` 와 `sms-logs/resend` **두 곳에 조건을 따로
적은 것**이 원인이고 **재발송 쪽이 길이를 안 봤다**. 에러가 아니라 **요금과 알림창 표기만**
달라져 눈치채기 어려운 자리다 — `smsSubjectFor()` **한 함수**로 모았다.
🔴 **`template_type` 만 보는 쪽으로 되돌리지 말 것** — 담당자가 확인창에서 본문을 길게
고치면 그때는 LMS 가 맞으므로 **판정 기준은 종류가 아니라 본문 길이**다.
⚠️ **운영에 시험 대상이 실재한다** — `quote_summary` 실패 **2건**(㉚-c).

견적 상세 버튼은 **「견적서 문자 발송」**이다(사용자 확정). 옆 두 버튼이 「견적서 출력
(PDF)」·「(Excel)」이라 **무엇을 어떻게 보내는지**가 한 형식으로 읽혀야 한다.
🔴 **「링크 문자 발송」으로 바꾸지 말 것** — 링크 생성이 실패하면 **옛 요약 LMS 로
내려가서**(`send-quote-sms`) 그때는 틀린 이름이 된다.

### ① 🚨 지시서가 통째로 뒤집혔다 — 착수 전 보고가 범위를 절반으로 줄였다

작업지시서(v1, 2026-09-16)는 **정식 편집기 도입**이었다 — 0-2 가 *"이것은 「신규 의존성 0」을
처음으로 깨는 작업입니다"* 로 시작하고, 0-3 ①번이 **「정식 편집기 도입 — 워드처럼 다 되게」**,
편집기 + HTML 정화 **둘**을 들이고 C장에서 Storage 버킷까지 만드는 설계였다.

지시서 1장이 *"🔴 고르지 말고 재서 보고한 뒤 대기하십시오"* 라 해서 라이브러리를 재서
보고했더니, **사용자가 작업량을 보고 범위를 줄였다**(원문):

```
그 전에 Tiptap을 써면 또 어딘가에 가입하고 api를 받아오고 해야하는 건가?
그리고 작업 과정이 긴가? 사실 공지사항 업데이트는 공지 사항을 좀더 보기좋게
꾸미고 싶은 이유가 있는데 너무 작업량이 과해지는게 아닌지 우려스럽다.
만약 지금 구조에서 최소한의 수정으로 공지내용에 글자볼드, 글자크기,
글자컬러, 이모티콘을 넣어서 보여줄수 있는 방법이 없나?
```

→ **ⓐ 간이 서식** 확정. 이어서 *"대신 이미 등록된 공지도 수정 할 수 있는 기능이 있어야 한다"*.

🔴 **그래서 「신규 의존성 0」이 그대로 지켜졌다 — 0-2 는 실행되지 않았다.**
🔴 **지시서가 *"기록에 「뒤집혔다」를 반드시 남기십시오"* 라 한 것을 반대 방향으로 이행한 것이다** —
다음 세션이 *"지시서가 정식 편집기라고 했는데 왜 없지"* 하고 라이브러리를 끌어오지 않도록.
🔴 **「지시서에 있으니 Tiptap 을 넣자」로 되돌리지 말 것.**

⚠️ **재서 보고한 것 자체는 값어치가 있었다** — 후보 넷 중 **셋이 스스로 탈락**했다
(CKEditor 5 = 상업 라이선스 / Quill = 본체 최근 1년 릴리스 **0회** / SunEditor = React 래퍼가
2023-06 에 멈춤). 정화도 「Node 에서 돌 것 + 최근까지 관리될 것」으로 거르면 **`sanitize-html`
하나**만 남았다(`dompurify` 단독은 브라우저 전용, `xss` 는 최근 1년 0회, `isomorphic-dompurify`
는 **jsdom 7MB** 를 끌고 온다). 🔴 **나중에 정식 편집기로 가게 되면 이 결과부터 볼 것** —
그때도 답은 **Tiptap + sanitize-html** 이다.

### ② 🚨 안전 구조가 정식 편집기와 **반대**다 — 이것이 이 작업의 핵심이다

```
  정식 편집기 : 담당자가 쓴 HTML 을 **받아서** 위험한 것을 골라낸다
                → 골라내기를 한 군데 빠뜨리면 구멍이 된다 → 정화 라이브러리가 필요하다
  이 방식     : 본문을 **전부 이스케이프한 뒤** 허락한 표기만 태그로 **만들어 낸다**
                → 통과시키는 HTML 이 애초에 없다 → 정화 라이브러리가 필요 없다
```

🔴 **이스케이프를 나중으로 미루거나 건너뛰지 말 것 — 그 한 줄이 이 구조의 전부다.**
`escapeHtml()` 이 `& < > " '` 다섯을 먼저 죽이고, 그 뒤에 `[b]`·`[color=red]` 만 태그로 바꾼다.
🔴 **원본 HTML 을 통과시키는 표기(`[html]` 같은 것)를 만들지 말 것** — 만드는 순간 이 구조가
무너지고 정화 라이브러리가 다시 필요해진다.

🟢 **속성 탈출이 원리적으로 불가능하다** — `"` 는 이미 `&quot;` 가 되어 있어서 `href` 안에
무엇이 들어가도 속성을 빠져나갈 수 없다. `[link=https://a.com"onmouseover="alert(1)]` 를
실제로 넣어 확인했다.
🔴 **`safeHref()` 가 `^https?://` 를 확인하는 것을 지우지 말 것** — `javascript:` 를 막는 자리다.
⚠️ 이스케이프 뒤라 URL 의 `&` 는 `&amp;` 로 들어 있고 **그대로 `href` 에 넣는 것이 맞다**
(HTML 속성 안에서는 그것이 정상 표기다). 🔴 되돌려서 `&` 로 풀지 말 것.

### ⑥ 🚨 「새 공지」 판정 기준을 `created_at` → `announced_at` 으로 옮겼다

수정 기능이 생기기 전에는 공지가 만들어지는 순간이 곧 알릴 순간이라 `created_at` 으로
충분했다. 이제 **오타 하나 고쳤는데 모든 화주에게 새 공지로 뜨는** 일을 막아야 한다.

```
  담당자가 고른다   저장 화면의 「화주에게 다시 알림」 체크 · 🔴 기본 꺼짐 (사용자 확정)
  켜면              announced_at = now()
  끄면              🔴 그 칸을 **건드리지 않는다**
  게시/숨김 토글     🔴 건드리지 않는다 (다시 게시한다고 새 공지로 뜨면 안 된다)
```

🔴 **정의처는 `lib/portalNotifications.ts` 의 `ANNOUNCEMENT_NOTICE_FIELD` 다.**
🔴 **`created_at`·`updated_at` 으로 되돌리지 말 것** — 앞엣것은 체크를 무의미하게 만들고,
뒤엣것은 체크를 켜지 않아도 새 공지로 뜨게 만든다(PR #164 가 포털 배너에서 겪은 그 자리).
🔴 **쓰는 곳이 셋이다** — 사이드바 배지(`CustomerPortalShell`) · 홈 「안 읽음 N」
(`app/customer/page.tsx`) · 목록 NEW 알약(`app/customer/announcements/page.tsx`).
**한 곳만 고치면 「배지는 올라갔는데 목록엔 NEW 가 없는」 상태가 된다.**

### ③ 수정 이력 — 🚨 표를 새로 만들지 않았고, 원칙 27번의 함정이 실재했다

⚠️ **처음에는 `record_change_logs` 를 새로 만들 생각이었다.** 그런데 착수 전 실측
(`_verify.sql` ㉘-b·㉘-f)에서 **이미 정확히 그 모양의 표가 있다**는 것이 드러났다.

```
activity_logs
  id · user_id · table_name · record_id · action · changed_fields(jsonb) · created_at
```

21차(`2026-08-26_rls_enable_13.sql`)가 「쓰이지 않는 6개」로 분류해 **RLS 만 켜고 정책은
만들지 않은** 레거시이고, 그 파일이 *「나중에 쓸 일이 생기면 그때 정책을 만들면 된다」*고
적어 뒀다. 🔴 **`record_change_logs` 같은 표를 새로 만들지 말 것** — 만들면 같은 일을 하는
표가 둘이 되고 다음 세션이 어느 쪽을 읽어야 하는지 알 수 없게 된다.

🚨 **그런데 그 표의 외래키가 죽은 `profiles` 를 가리키고 있었다**(㉘-g 실측).

```
activity_logs_user_id_fkey | FOREIGN KEY (user_id) REFERENCES profiles(id)
```

**원칙 27번이 기록한 그 사고**(`quotes.created_by` 가 `profiles` 를 참조해 `created_by`
자동기록이 FK 위반으로 막혔다)**와 같은 시대·같은 원인**이다. 그대로 뒀으면 직원 id 를
넣는 순간 insert 가 통째로 막히고, **화면에는 「이력이 안 쌓인다」로만 보여** 원인을 짚을
단서가 하나도 없었을 것이다. 🔴 **마이그레이션이 고친 뒤 실제로 넣어 보고 되돌리는
단언을 포함한다 — 빼지 말 것**(PR #154 가 DB 함수에서 겪은 그 자리다).

🔴 **레거시 표를 되살려 쓸 때는 제약·인덱스를 반드시 실측할 것** — 컬럼 이름만 맞는다고
쓸 수 있는 게 아니다. 이번에 그것이 이 차수에서 가장 컸다.

**구조**
- `lib/recordChangeLog.ts` — 라벨 맵 + `diffRecordFields()` + 쓰기·읽기. **유일 정의처.**
- `components/RecordChangeLogPanel.tsx` — 접이식 패널(견적 상세·오더 상세 공용).
- 정책: `staff_all_activity_logs`(`is_active_staff()`). 🔴 **화주 정책을 만들지 말 것** —
  화주포털과 직원이 **둘 다 `authenticated` 롤**이라(19차) 하나라도 열면 화주가 내부
  수정 이력을 통째로 읽는다.
- `user_id` FK 는 **`on delete set null`**(원칙 32번 — 이력이지 발송 대상이 아니다).

🔴 **값은 기록 시점의 「보이는 문자열」로 굳혀 저장한다**(`130,000원` · `혼적가능` ·
`2026. 09. 17. 14:00`). 감사 기록이라 **그때 화면에 뭐라고 쓰여 있었는지**가 남아야 하고,
나중에 라벨을 바꿔도 옛 기록의 뜻이 달라지면 안 된다. 🔴 **원본 값만 저장하고 읽을 때
포맷하지 말 것.** 🔴 **직원 이름도 같은 이유로 `changed_fields.by` 에 굳힌다**(FK 가
`set null` 이라 퇴사 직원 행이 지워져도 「누가」가 남아야 한다 · 원칙 32번의 텍스트 스냅샷).

🔴 **비교도 표시 문자열끼리 한다** — `numeric` 130000.00 과 입력창 130000 을 그냥 견주면
**안 고친 필드가 매번 「바뀜」으로 남아** 이력이 쓸모없어진다.
🔴 **`quotes` 의 차량형태·상차조건 등은 컬럼이 아니라 `selected_options`(jsonb) 안의 한글
키다** — `flattenSelectedOptions()` 가 한 겹 펴서 비교한다. 안 펴면 **차량형태를 바꿔도
이력에 아무것도 안 남는다**(§7 의 그 함정 · PR #152·#153 이 같은 자리에서 두 번 걸렸다).
🔴 **저장 payload 에 없는 필드는 「비웠다」가 아니라 안 건드린 것이다**(`if (!(field in a)) return`).
🔴 **일부러 뺀 필드** — `*_sido`/`*_sigungu`(주소에서 파생) · `updated_by`/`updated_at`
(이력 자체가 담는다) · `settlement_type`(파생 · 원칙 45번) · `selected_options.톤수`
(`vehicle_type` 과 같은 값) · `첫거래지원할인`(담당자가 고치는 값이 아니다).

⚠️ **위조를 막는 장치가 아니다.** 화면이 직접 insert 한다(`lib/settlementTypeChangeLog.ts`
와 같은 방식) — 그 담당자는 애초에 **그 레코드 자체를 고칠 수 있는 사람**이라 서버 API 를
하나 더 둬도 얻는 것이 없고 저장 경로만 둘로 갈린다. **되짚기 위한 기록이지 부인방지
장치가 아니다.**
⚠️ **백필하지 않았다** — 2026-09-17 이전 수정은 기록이 없고 **화면이 그렇게 말한다.**
지어내면 감사 기록이 아니다.
⚠️ **정산방식 3필드와 겹치지 않는다** — 오더의 그 필드는 전용 모달이 사유와 함께
`settlement_field_change_logs` 에 따로 남긴다(원칙 39번). 오더 일반 저장 폼에는 그 필드가
**없다**(실측). 견적에는 그 로그 자체가 안 걸려 있어 여기서 처음 남는다.

🔴 **패널은 기본 접힘이고 펼쳤을 때 처음 조회한다** — 상세가 이미 길다(PR #167 이 견적

### ② 취소 배지를 재배차 접수중에도 유지 — 🔴 규칙이 「배차확정까지」로 바뀌었다

🔴 **규칙 한 줄 — 취소 배지는 「취소된 순간부터 배차확정까지」 뜬다.** 취소된 카드에도
뜨고, **재배차가 접수된 뒤에는 그 새 카드가 이력을 이어받는다.** 배차가 확정되면(단계 1)
사라진다.

🔴 **그전에는 재배차가 접수되는 순간 배지가 사라졌다.** 이유는 구조다 —
`filterCancelledForCustomer` 가 **살아 있는 배차가 있는 오더의 취소 카드를 감추는데**
(카드가 둘이 되는 것을 막으려고) **새 카드는 취소 이력을 모른다.** 그래서 화주 화면에서
「배차 취소 · 재배차 접수 중」이 **한 순간에 그냥 「접수」로** 바뀌었다.

🔴 **카드가 둘이 되는 것은 그대로 막는다** — 취소 카드는 여전히 감춘다. 다만 **감춰도
정보가 사라지지 않는다**(새 카드가 말한다). 🟢 **감췄던 이유(어느 것이 유효한지 모른다)가
이것으로 해소됐다.**

🔴 **판정의 정의처는 `lib/portalCancelledDispatches.ts` 하나**이고 **홈·조회 두 화면이
같이 쓴다** —
```
  filterCancelledForCustomer()  →  { rows, redispatch }
      rows       : 보여줄 행(취소 카드 정리 후)
      redispatch : order_id → 그 오더의 가장 최근 취소 사유
                   🔴 **아직 배차확정 전인 살아 있는 배차가 있는 오더만** 담는다
                      → 배차가 확정되는 순간 배지가 저절로 사라진다(화면이 지울 필요 없다)
  getPortalCancelNotice(row, redispatch)  →  { reason } | null
      ① 취소된 카드 자체        → 그 카드의 사유
      ② 재배차 접수중(단계 0)   → 그 오더의 가장 최근 취소 사유
      ③ 그 밖                   → null
```
🔴 **화면에서 `isDispatchCancelled(d.dispatch_status)` 로 다시 적지 말 것** — 그러면
재배차 접수 순간 배지가 사라진다(고치기 전 동작으로 정확히 되돌아간다).

🔴 **단계 판정은 `lib/dispatchStage.ts` 가 한다** — 이 파일에 `"접수중"` 문자열을 적지
말 것. `문제발생` 처럼 **상태값이 단계를 안 말해주는 값**이 있어서 boolean 두 개로
복원해야 한다(29차가 세운 규칙).

🔴 **형제 배차를 화면이 들고 있는 목록에서 찾지 말 것** — 조회 화면은 최근 100건, 홈은
5건만 받고 홈은 `운송완료`·`하차완료` 를 **아예 빼고** 받는다. 그 안에서 찾으면
① 재배차가 끝났는데 취소 카드가 남고 ② **취소 카드가 목록 밖이면 새 카드가 이력을 영영
모른다.** 그래서 필요할 때만 DB 에 한 번 더 묻는다 — 🟢 **취소도 없고 단계 0 도 없으면
질의 0회**(실측으로 확인).

🔴 **취소 카드를 고를 때는 DB 가 아니라 `rows` 안에서 가장 최근 것을 고른다** — 처음엔
DB 결과로 고르게 썼다가 되돌렸다. DB 기준이면 **그 행이 목록 밖일 때 어느 카드도 안
남아 통째로 사라진다**(홈은 5건이다).

🔴 **조회 실패는 「아무것도 감추지 않고 아무 배지도 안 붙이는」 쪽으로 떨어진다**
(원칙 55번) — 중복 카드는 눈에 보이지만 사라진 카드는 안 보인다.

🟢 **검색어도 같이 넓혔다** — 재배차 카드도 화면에 「배차 취소」라고 떠 있으므로

🟢 **보조 문구도 따라온다** — 재배차 접수중 카드의 알약 보조가 「배차 대기」가 아니라

### ③ 오더 상세 「배차 상세보기」 — 🔴 원인은 정렬이 아예 없던 것이다

오더이고, 배차의 화주 청구금액은 **배차 담당자가 배차 상세에서 정한다**(혼적 할인·현장
조정이 거기서 붙는다). 🔴 **조용히 같이 고치지 말 것** — 돈이고, 고치는 사람이 다르다.
대신 **화면이 「배차·정산 금액은 따로 확인하라」고 알린다**(입력칸 아래 안내 + 저장 후
결과 문구 + 확인 창 본문, 세 자리).

🔴 **묻지 않고 바로 반영하는 것이 기본이다**(그것이 지시다) — 오더가 이미
`배차완료`·`운송중`·`운송완료`면 그때만 한 번 확인한다. 🔴 **그 목록은 원칙 39번이 오더의
정산방식을 잠그는 것과 같은 목록이다 — 갈라 적지 말 것**(`lib/quoteAmountSync.ts` 의
`ORDER_AMOUNT_SYNC_CONFIRM_STATUSES`). 사용자가 말한 상황(배차확정 전)은 확인 없이 지나간다.

🔴 **견적 금액이 비어 있으면 아무것도 하지 않는다** — 금액을 안 적은 견적으로 오더의
청구금액을 **지워 버리면** 배차·정산이 0원으로 흘러간다.
🔴 **금액이 그대로면 오더를 건드리지 않는다** — 괜한 `updated_at` 은 화주포털 목록에
**「업데이트」 알약**으로 뜬다(PR #164).

🔴 **견적 저장이 성공한 뒤에만 오더를 고친다** — 낙관적 잠금 충돌로 막힌 저장에서
오더만 바뀌면 두 화면의 금액이 갈린다. 반대로 **오더 반영이 실패해도 견적 저장을
되돌리지 않는다**(견적은 이미 저장됐고 오더는 오더 화면에서 고칠 수 있다) — 다만
**조용히 넘어가지 않는다**(원칙 55번).

🟢 **곁다리 — 연결 오더를 `count` 가 아니라 행으로 들고 있게 바꿨다.** 그전에는
`select("id", { count: "exact", head: true })` 로 **건수만** 셌다(`hasOrder` 는 이제 그
파생값이다). 🔴 **조회 실패를 삼키면 「금액을 고쳤는데 오더가 안 따라왔다」가 조용히
일어난다** — 그때는 저장이 오더를 **아예 손대지 않으므로** 배너로 말한다.

🟢 **정산방식 안내 문구도 고쳤다** — *「정산방식을 수정해도 기존 오더에는 자동 반영되지
않습니다」* 옆에 **「최종 견적금액은 함께 반영됩니다」**를 붙였다. 🔴 **안 붙이면 담당자가

### ③ 🔴 헤더 로고의 원인은 렌더링 결함이 아니라 「픽셀 수」였다 (커밋 4)
