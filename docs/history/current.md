### ③ 🟢 v4 7장 「착수 전 확인」 실측 — 넷

**ⓐ 지시서는 이 값을 전제로 쓴다.** 코드로 잴 수 없는 것(붙여넣은 텍스트의 실제 모양)은 샘플
대기이고, 나머지 넷을 이 세션이 실측했다.

**ⓐ-1 `dispatches.external_order_no` 가 정말 없는가 → 🔴 없다.**

```bash
grep -rn "external_order_no" --include=*.ts --include=*.tsx --include=*.sql .   # → 0건
```

코드·마이그레이션 양쪽에 한 줄도 없다. v3 조사 시점 그대로이고 **신설이 맞다**(24시콜 화물번호가
연결 열쇠이므로 unique).

**ⓐ-2 `brokerage_fee` 를 채우는 자리와 부가세 토글의 관계 → 🔴 그 칸에는 토글이 없다.**

자리는 배차 상세(`app/admin/dispatches/[id]/page.tsx`)의 **「정산 정보」 카드 → 「선착불 정산 정보」
블록** 안이고, **`settlementValue.collection_method === "driver_direct"` 일 때만 그려진다.**

라벨이 **「주선수수료(부가세 포함가, 원)」**로 못박혀 있고, 아래 캡션이 `toSupplyAmount()`(÷1.1)로
공급가액·부가세를 보여줄 뿐이다. `VatBasisSelect`(부가세 구분 토글)는 **화주 청구금액**과
**차주 지급운임** 두 칸에만 붙는다.

```
  화주 청구금액(원)            + VatBasisSelect   ← customer_charge_vat_included
  차주 지급운임(원)            + VatBasisSelect   ← driver_vat_included
  전체 운송료(원)              (선착불 블록)
  차주 직접수금액(공급가액, 원) (선착불 블록)
  주선수수료(부가세 포함가, 원) 🔴 토글 없음 — 포함가 고정
```

🔴 **그래서 ⓐ 가 24시콜 「합계」를 `customer_charge` 에 넣을 때는 `customer_charge_vat_included` 를
함께 정해야 한다** — 기본값이 `false`(부가세 별도)다. 이것이 v3 §5 대조 블록의 **미결 「부가세
기준」과 같은 자리**이고, 🔴 **v12 가 라벨을 「공급가액 (부가세 별도)」로 통일했다고 해서 이 미결이
닫힌 것은 아니다**(라벨과 `brokerage_fee` 기입 기준은 다른 축이다).

🔴 **선착불이 아니면 그 블록 자체가 안 그려진다** — 24시콜 건은 **수금방식이 먼저 선착불이어야**
`brokerage_fee` 칸이 화면에 나타난다. ⓐ 가 값을 채우려면 수금방식부터 세워야 한다는 뜻이다.
⚠️ 화면 주석의 실측 — **DB 에 5,000(포함가)과 4,545(공급가액)가 섞여 들어가 있다**(35차가 라벨을
바꾸기 전에 저장된 것). 통계는 항상 ÷1.1 로 공급가액을 쓴다.

**ⓐ-3 붙여넣기 칸을 넣을 자리 → 🔴 저장 경로가 셋이라는 것이 핵심이다.**

v4 가 *「줄 번호가 아니라 계산 흐름으로 찾을 것」*이라 한 자리다. 흐름으로 보면 카드 순서는
**배정방식·배차확정 → 상차지·하차지 담당자 → 정산 정보 → 클레임 → 현장 추가비 → POD → 문자 발송**
이고, 24시콜 한 건의 값이 **서로 다른 세 state 와 세 저장 버튼**으로 흩어진다:

```
  차주 이름·연락처·차량번호·확정 정보망
      → externalDriverName / externalDriverPhone / externalVehiclePlate / confirmedNetworkId
        (editForm 이 아니라 **별도 state**)
      → 저장은 **handleConfirm()** — 배정방식 카드의 「배차확정」 블록,
        `assignment_type === "external"` 분기 안에 있다
  화주 청구금액 · 부가세 구분 · 전체 운송료 · 주선수수료
      → editForm      → 저장은 **handleSave()**(맨 아래 「변경사항 저장」)
  차주 기본운임
      → payoutCalcForm → 저장은 **handlePayoutCalcSave()**(접이식 안의 전용 버튼)
```

🔴 **붙여넣기 칸 하나가 두 카드에 걸쳐 값을 채운다.** 자리는 **배정방식 카드 위**가 자연스럽다
(맨 위에서 붙여넣고 아래로 내려가며 눈으로 확인). 🔴 **「한 번 붙여넣으면 저장까지 끝난다」로
설계하지 말 것** — 저장 버튼이 셋이라 어느 하나만 누르면 나머지가 조용히 안 들어간다. ⓐ 지시서가
**이 셋을 명시적으로 다뤄야 한다.**
🔴 **줄 번호로 찾지 말 것** — 35차가 이 화면을 크게 고쳤고 지금 **2,525줄**이다.

**ⓐ-4 `driver_base_fare` 경로 재확인 → 🔴 `driver_payout` 에 직접 넣지 말 것.**

`handlePayoutCalcSave()`(718행)가 `calcSettlement()` 결과로 **`driver_payout` 을 덮어쓴다**
(`driver_payout: result.driverTotalPayout || null`). 직접 넣으면 **계산기를 여는 순간 사라지고**
24시콜 「송금할 운임」과 대조할 근거도 없어진다.
⚠️ **그 칸은 「차주 운임 상세 계산」 접이식 안이고 `dispatch_status !== "접수중"` 일 때만
그려진다** — 접수중 배차에 붙여넣으면 **그 칸이 화면에 아예 없다.** ⓐ 가 접수중 건을 다룰지

🔴 **부족해지는 것은 ⓑ(견적 폼)다** — 상하차 방법·시점·특이사항·상세주소가 통째로 안 온다.
**ⓑ 지시서는 「목록 행만으로는 안 된다」를 전제로 써야 한다**(창을 한 칸씩 복사하게 하거나,
그 값들은 담당자가 직접 고르게 하거나).

**⑥-3 🟢 부가세 기준 미결이 닫혔다 — v3 부터 열려 있던 것이다**

캡처의 두 값이 서로를 증명한다:

```
  합계 80,000 × 1.1 = 88,000
  88,000 − 산재보험료 차주분 350 = 87,650   ← 화면의 「송금할운임(부가세포함)」과 정확히 일치
```

🔴 **부가세가 가산됐으므로 합계 80,000 이 공급가액이다.** 따라서 그 안의 **운송료 65,000 과
수수료 15,000 도 둘 다 부가세 별도**다.
🔴 **그런데 35차는 `brokerage_fee` 를 「부가세 포함가 기입」으로 확정했다**(사용자 6·9번).
그대로 15,000 을 넣으면 포함가로 읽혀 공급가액이 13,636 이 되고 **마진이 10% 적게 잡힌다** —
ⓐ 는 **15,000 × 1.1 = 16,500** 을 넣거나 그 칸의 기준을 바꿔야 한다. **ⓐ 지시서가 정할 것.**

**⑥-4 🟢 v3 §1-9 의 불일치도 풀렸다**

*「차주 실수령을 운송료 65,000 이라 하는데 송금할 운임은 87,650 이라 서로 안 맞는다」*고
적혀 있던 것 — **87,650 은 화주가 차주에게 줄 총액**(합계 부가세포함 − 차주 산재)이고
**65,000 은 그중 차주 몫**이다. 차주가 받아서 수수료를 낸다.
🟢 **35차 선착불 모델**(받을 돈 = 주선수수료 · 줄 돈 = 0 · 수수료는 차주가 낸다)**과 맞는다.**

**⑥-5 🔴 산재 기준액이 서로 다르다 — 새로 드러난 것**

같은 요율(필요경비공제 49.9% · 산재 1.76% · 절반 부담)로 검산했다:

```
  합계 80,000 기준   floor(80,000 × 0.501) = 40,080  →  floor(40,080 × 0.0088) = 352  →  350
  운송료 65,000 기준  floor(65,000 × 0.501) = 32,565  →  floor(32,565 × 0.0088) = 286
```

🔴 **24시콜은 합계(80,000) 기준이고 10원 단위로 절사한다**(화면값 350 과 맞는다).
🔴 **우리 `calcSettlement()` 는 `driverBaseFare`(65,000) 기준이라 286 이 나온다** — 같은 건의
산재가 **350 vs 286** 으로 갈린다. ⓐ 지시서가 **「가져온 값을 그대로 둘지 우리 식으로 다시
계산할지」**를 정해야 한다. 🔴 **말없이 재계산하면 24시콜 정산서와 대조가 어긋난다** —
v12 C장 반올림이 만든 것과 **같은 자리**다.

**⑥-3b 🔴 사용자 확정 셋 — 위 ⑥-3·⑥-5 의 결론이 바뀌었다**(2026-09-16)

```
  1  "선착불 오더에서 적힌 수수료는 부가세 포함가이다. 그래서 15,000원(부가세포함가)로
     적는게 맞다."
  2  "산재는 일단 고려하지 말자."
  3  "접수중 배차는 일단 다루지 말자."
```

🔴 **1번은 내 제안을 뒤집은 것이다.** 나는 ⑥-3 에서 *「합계 80,000 이 공급가액이니 수수료
15,000 도 공급가액이고, 35차가 포함가 기입으로 정했으니 ⓐ 는 16,500 을 넣어야 한다」*고
적었는데, 사용자가 **실무 기준으로 15,000 이 이미 포함가**라고 확정했다.
🟢 **그래서 변환 없이 그대로 넣는다** — 35차 확정과 그대로 맞물린다.
🔴 **「×1.1 해서 16,500」을 되살리지 말 것.**

⚠️ **다만 산술은 여전히 갈려 있고 그것을 지운 것이 아니다.** 24시콜 화면은
`합계 80,000 × 1.1 = 88,000` 으로 계산하므로 **화면상 80,000 이 공급가액**이다. 그 안의
15,000 도 화면 기준으로는 공급가액처럼 읽힌다. 🔴 **그래도 실무 기준이 이긴다** — 합계·
송금액은 **화주↔차주 운임 흐름**의 계산이고, 수수료는 그와 별개로 **차주가 위캐리에 내는
돈**이다(35차 선착불 모델). ⚠️ **두 시스템이 같은 건의 수수료 공급가액을 다르게 본다**

### ⑤ C장 — 소계 반올림 + 견적서 가산 한 줄 (PR #158 · 코드 · DB 0)

**A·B 가 들어간 뒤에도 만원을 깨뜨리는 것이 넷 남는다** — 왕복/편도(유일하게 남은 요율) ·
대기료 · 경유지비(각 13행 중 4행이 5,000 단위) · 혼적 할인(율 방식).
🔴 **그 표들을 고쳐서 반올림을 없애려 하지 말 것** — 담당자가 정한 값이고 사용자가 현행 유지로
확정했다. **반올림이 그것을 흡수하는 것이 `lib/roundToUnit.ts` 의 존재 이유다.**

```
  surchargeTotal = roundToUnit(pctAmount + flatTotal + waitingExtra + waypointExtra, 차급)
  rawFinal       = max(base + surchargeTotal, 0)          ← 격자값
  혼적할인        = roundToUnit(rawFinal − applyMixedDiscount(rawFinal, …), 차급)
  final          = max(rawFinal − 혼적할인, 0)             ← 격자값
```

(지시와 다르게 판단한 것). 백필은 `location_name` 이 **주소와 다를 때만** 상호로 보고,
옮긴 뒤에도 `location_name` 을 **지우지 않는다.** 주소와 같으면 그건 「이름이 없어서 주소를
넣어둔 것」이라 상호가 아니다(폼의 `|| form.origin.trim()` 갈래가 그것이다).
지우면 되돌릴 길이 없고, 별칭으로 쓰던 화주의 카드 제목이 통째로 바뀐다. 🔴 **되돌리지 말 것.**

🟢 대신 카드 제목이 **별칭 → 상호 → 주소** 순으로 골라진다(`locLabel()`) — 보이는 것은
그대로이고 상호만 제 칸에서도 읽힌다. 🔴 **상호를 맨 앞에 두지 말 것**(별칭을 일부러 적은
화주는 그것으로 구분한다). 제목이 이미 상호면 아래 「상호」 줄을 **두 번 그리지 않는다.**

⚠️ **운영 실측(apply 로그)** — 배송지 **14건** 중 상호 **2** · 별칭 **2** · 담당자 **2** ·
상세주소 **0**. 옮겨 적힌 것은 **2건**이고 재실행하면 **0건**이다(멱등).

### 🔴 ⓪ 가장 중요한 것 — 「담기가 안 된다」의 진짜 원인은 **DB 함수가 예외로 죽는 것**이었다

신고를 **세 번** 받고서야 찾았다. 앞의 세 라운드는 **화면 쪽 원인만** 고쳤다.

```
ERROR:  cannot cast type record to invoices
CONTEXT: PL/pgSQL function add_item_to_billing_batch(uuid,uuid) line 52 at IF
```

```sql
declare
  v_invoice record;                                    -- ← 여기
...
  if not is_billing_batch_candidate(v_invoice) then    -- ← 여기서 폭발
```

`is_billing_batch_candidate(p_invoice invoices)` 는 **`invoices` 행 타입**을 받는데
`record` 로 선언한 변수는 그 타입으로 캐스트되지 않는다. **관문을 전부 통과한 건이
마지막 줄에서 죽는다** — 거절 사유가 아니라 **에러**가 올라오므로 「담기」·「모두
담기」·운송완료 자동 담기가 **전부, 언제나** 실패했다.

🔴 **고친 것은 선언 한 줄이다**(`record` → `invoices%rowtype`). 나머지 본문은 운영
DB 에서 그대로 떠온 것이고 **한 글자도 안 바꿨다**(관문 순서·사유 이름·스냅샷 계산·
`unique_violation` 처리 전부 동일). 🔴 **이 기회에 다른 것을 같이 고치지 말 것** —
돈이 걸린 경로다.

🔴 **마이그레이션에 「고친 함수를 실제로 불러보고 되돌리는 단언」을 넣었다.** 여전히
못 담으면 `raise exception` 으로 **함수 교체까지 통째로 롤백**되고 워크플로가 멈춘다.
「배포했는데 여전히 안 담긴다」를 또 겪지 않기 위해서다. 🔴 **이 단언을 빼지 말 것.**

🟢 **곁다리 — 묶음 DB 함수가 처음으로 저장소에 들어왔다.** 12개가 14차 산출물이라
저장소 밖에 있었고(마이그레이션 자동화 47차보다 먼저), **그것이 원인 찾기를 어렵게
만든 바로 그 이유**였다.

#### 🔴 어떻게 찾았나 — 짐작을 그만두고 쟀다

`_verify.sql` 에 절 셋을 새로 만들었다. **다음에 같은 종류의 신고를 받으면 여기부터 볼 것.**


### ① 운송완료 → 묶음 자동 생성

운송완료하면 **정산 건은 자동**인데 **묶음은 손으로** 만들어야 했다(실측: 월정산 2건 중
묶음에 담긴 것 **0건**). 이제 정산 건이 만들어지는 순간 그 화주·정산월의 묶음에
자동으로 담기고, 묶음이 없으면 작성 중 묶음이 새로 만들어진다.

🔴 **호출은 `lib/autoCreateInvoice.ts` 안에 있다 — 화면으로 옮기지 말 것.** 이 함수를
부르는 곳이 **배차 상세·배차 목록 둘**이고 24시콜 ⓒ 가 셋째가 된다. 화면에 두면 한쪽만
고쳐져 「목록에서 완료하면 묶음이 안 생긴다」가 된다(원칙 53번).

🔴 **fire-and-forget 이다**(`await` 금지) — 묶음 API 가 느리거나 죽으면 **배차 상태
변경 자체가 멈춘다.**

🔴 **조건 판정은 서버가 한다**(`app/api/admin/billing-batches/auto-attach`) —
클라이언트에서 미리 거르면 판정이 두 곳이 된다(원칙 44번과 같은 결).

🔴 **확정·해제된 묶음에는 자동으로 담지 않는다** — 확정 금액이 담당자도 모르게
흔들리거나, 일부러 해제한 묶음이 되살아나면 안 된다. 그때는 화면이 「보충 묶음」으로 안내한다.

🔴 **DB 함수를 새로 만들지 않았다** — 기존 12개 중 둘(`create_billing_batch` ·
`add_item_to_billing_batch`)을 순서대로 부를 뿐이다. 저장소 밖 로직을 더 늘리지 않는다.

⚠️ **`draft_already_exists` 는 실패가 아니다** — 운송완료 두 건이 거의 동시에 처리되면
(배차 목록에서 연달아 누르는 흔한 일) 뒤엣것이 걸린다. 그때는 앞엣것이 방금 만든 묶음을
다시 찾아 담는다. 🔴 **이 분기를 지우면 같은 순간에 완료한 둘째 건이 조용히 빠진다.**

### ② 화면을 묶음 목록 하나로 (실사용 리뷰 1라운드)

### ⑤ E장 — 견적서 「조정」 줄

담당자가 「최종금액 직접 입력」으로 금액을 고치면 `final_amount` 만 바뀌고 항목 줄은
그대로라, **화주가 받은 견적서에서 더해도 합계가 안 나왔다.**

🔴 **기본운임을 덮어쓰지 않고 줄을 하나 더한다**(사용자 확정) — 덮어쓰면 그 값이
**운임기준표 산출값이라는 사실이 사라져** 「왜 이 거리에 이 금액인가」를 되짚을 수 없다.

🔴 **지시서의 식이 틀렸다.** 지시서는 `기본운임 + 가산 − 혼적할인` 이라 했는데,
견적서가 실제로 그리는 줄은 `quote_items`(가산)와 `discount_amount`(할인)이고
**혼적할인은 이미 `quote_items` 안에 음수 행으로 들어 있다.** 따로 빼면 **두 번 빠진다.**

```
  조정 = final_amount − (base_fare + Σ quote_items.amount − discount_amount)
```

🔴 **커밋을 둘로 나눴다** — 정의처만 만든 커밋 직후 **조정 0 견적의 출력이 한 글자도
안 달라지는 것**이 회귀 0 의 근거다(diff 순수 추가 +100 / −0).
🔴 **`shouldShowAdjustment` 가드를 빼지 말 것** — 조정 0 견적에 `조정 0원` 줄이 생긴다.
🔴 **`quote_items` 조회 전에 계산하지 말 것** — 빈 배열이면 **가산액만큼이 통째로
「조정」**으로 보인다.
🔴 **엑셀만 부호를 문자로 안 쓴다** — 금액이 숫자 타입이라야 받는 쪽에서 SUM 검산이
된다(원칙 8번). 값 자체를 음수로 넣는다.

⚠️ **안 고친 불일치 하나** — 할인 줄이 PDF·엑셀에만 있고 두 상세 화면에는 없다.
`discount_amount` 가 전 건 0 이라 지금은 잠복 상태이고, 누가 할인을 넣는 순간
화면과 PDF 가 갈린다. **E장 범위 밖이라 안 건드렸다.**

### ⑥ 리뷰 2라운드 — 계산창이 상단메뉴에 가린다

사용자 신고: *"견적관리에서 스크롤할때 자동계산결과창이 상단메뉴에 일부 가려지게
되는데, 가려지면 안된다."*

🔴 **PR #150 이 상단바를 `sticky` 로 만들면서 생긴 자리다.** 계산창은 34차에
`top: 20` 으로 만들어졌는데 그때는 헤더가 같이 스크롤돼 사라졌다.

```
  실측(Chromium)   헤더 79px(데스크탑) · 71px(≤700px)
                   계산창 top 20px  →  **59px 이 헤더 뒤로 들어감**
  고친 뒤          헤더 bottom 79 · 계산창 top 99 · 간격 20px (겹침 0)
```

🔴 **`--admin-topnav-h` 를 신설했다**(globals.css) — `top: calc(var(--admin-topnav-h) + 20px)`.
**새로 `sticky` 를 쓰는 곳은 이 변수를 더할 것.** 숫자를 화면마다 적으면 헤더 여백이
바뀔 때 어디가 가려지는지 아무도 모른다.
🔴 **`.top-nav-inner` 의 padding 이나 로고 크기를 바꾸면 이 값도 다시 잴 것.**
🟢 **관리자에서 `sticky` 를 쓰는 곳은 이 계산창 하나뿐임을 확인했다** — 나머지 네 곳은
공개 화면·화주포털이라 이 상단바가 없다.
⚠️ 모바일 계산창은 `.drag-panel`(`position: fixed`)이라 이 변수를 쓰지 않는다.

### ⑦ 리뷰 2라운드 — 일정에 「지금 · 당착 · 내착」

사용자 신고: *"일정에서 발주요청과 마찬가지로 지금, 당착, 내착 등의 옵션이 있어야 한다."*

🔴 **공용 `DateTimePicker` 에 opt-in prop 으로 넣었다 — 기본값이 전부 꺼짐이다.**
같은 부품을 운송오더 2화면·랜딩 폼이 쓰는데 **새 prop 을 주는 곳은 견적 등록·수정
두 화면뿐**이고, 그것이 무회귀의 근거다. 🔴 **기본값을 켜지 말 것.**
🔴 **포털 부품(`Pv2DateTimeField`)을 끌어오지 않았다** — `.pv2-*` 스코프가 딸려온다
(원칙 57번). 같은 **동작**을 관리자 생김새로 옮긴 것이다.

🔴 **DB 0 이다** — `quotes` 에 도착구분 컬럼을 만들지 않는다(28차 결정 1). 값은
**특이사항 한 줄**로 오더·배차까지 이어진다(포털에서 넘어온 견적이 이미 쓰던 경로).
문구·중복 판정은 `lib/arrivalType.ts` 하나가 한다(`arrivalNoteLine` /
`buildNotesWithArrival`) — **이미 들어 있으면 다시 붙이지 않는다.**

🔴 **당착·내착이면 +30분 하한을 걸지 않는다**(27차 예외) — 안 그러면 **23:40 상차
건의 당착이 하한에 걸려 접수가 막힌다.**
🔴 **자리 채움 시각 `"23:59"` 가 세 파일에 흩어져 있던 것을 `lib/arrivalType.ts` 하나로
모았다**(견적 폼까지 넷이 될 뻔했다). 그 파일은 `.pv2-*` 스코프가 아니라 관리자·포털이
함께 쓸 수 있어서 원칙 57번을 어기지 않는 자리다.
🟢 칩을 켜면 날짜·시간 칸이 **잠기고**, 손으로 고치면 칩이 **풀린다**(「당착」이라 적혀
있는데 저장값은 딴 시각인 상태를 막는다). 「지금」은 **제출하는 순간의 시각**으로 저장된다.
⚠️ 「지금」·「당착」은 시각 칸이 **비어 보인다** — 시간 드롭다운이 30분 단위라 현재 시각도
23:59 도 선택지에 없다. **칸을 비운 채로 두는 것이 맞고**, 그 이유를 배지로 적어 뒀다.

**곁다리로 하나 고쳤다** — 상차 안내가 「현재 시각 이후로만 선택 가능합니다」라고 적고
있었는데 **하한이 걸려 있지 않았다**(35차 확정: *"지나간 날짜도 고를 수 있어야 한다"* —
끝난 운송을 뒤늦게 입력하는 일이 있다). 원칙 6번이 *"36차 D장이 하차만 다루기로 해서
일부러 안 고쳤다"* 고 적어둔 자리인데, 바로 옆에 「지금」 칩이 생기면서 더 헷갈리게 돼
같이 고쳤다. 🔴 **문구를 근거로 하한을 새로 걸지 말 것.**

### ⑧ 견적서 공유 링크 — 로그인 없이 열리는 견적서

사용자 원문: *"견적문자 발송에서 간단한 멘트와(견적서발송,위캐리운송포함) 견적서 url을
보낼수 있나? 가급적 (SMS) 문자이면 좋겠다."*

🔴 **조사해 보니 보낼 URL 자체가 없었다.** 견적서를 볼 수 있는 곳이
`/admin/quotes/[id]`(직원만 · middleware 가 막음)와 `/customer/quotes/[id]`(포털 계정
있는 화주만) 둘뿐이라, **전화로 받은 게스트 견적은 계정이 없어** 링크를 줘도 못 연다.
그래서 **별도 차수로 제안하고 결정 3건을 받았다** — 사용자 확정:

```
  ① 확인을 한 번 더 받는다(연락처 뒤 4자리)
  ② 유효기간이 지나면 막는다
  ③ 기존 견적안내 문자를 대체한다
```

```
  [위캐리운송] 견적서를 보내드립니다.
  https://wecarrylogis.co.kr/q/<토큰 22자>        실측 **87byte (SMS)**
```

🔴 **「문의 1661-2403」 한 줄을 넣으면 102byte 로 LMS 가 된다 — 넣지 말 것.** 대신
① 이 문자의 **발신번호가 담당자 본인 번호**라(35차) 그대로 회신·통화가 되고
② 대표번호는 **견적서 화면 안에** 있다.
🔴 **35차의 「90byte 압축을 되살리지 말 것」과 부딪히지 않는다 — 전제가 달라졌다.**
그때 LMS 로 간 이유는 *"압축하면 품목이 잘려 무슨 견적인지 알아보기 어렵다"* 였는데,
지금은 **링크가 견적서 전체를 대신 보여준다.** 🔴 **본문에 품목·금액을 다시 넣지 말 것.**
🔴 **URL 을 줄임주소로 감싸지 말 것** — 외부 서비스가 죽으면 이미 보낸 문자가 통째로
죽는다. 경로가 `/q/` 로 짧은 이유가 이것이다(29자 + 토큰 22 = 51byte).

**되돌리면 안 되는 설계**:

🔴 **주소만으로는 아무것도 안 보인다.** 화면은 처음에 입력칸 하나만 그리고, 서버가
뒤 4자리를 확인해 준 **뒤에야 견적 내용을 처음 받아온다**(미리 받아서 숨기면 페이지
소스에 그대로 남는다 — 30차 푸터 이메일에서 겪은 함정). **실측: 토큰만으로 연 HTML 에
견적 데이터 0건.**
🔴 **서버 컴포넌트로 바꾸지 말 것** — 토큰이 주소에 있으므로 서버에서 바로 렌더링하면
뒤 4자리 확인이 통째로 무의미해진다.
🔴 **API 는 POST 다** — GET 이면 토큰과 뒤 4자리가 **주소창·서버 로그·리퍼러**에 남는다.
🔴 **`quotes` 에 anon SELECT 정책을 만들지 말 것**(원칙 3번과 같은 결) — 그 순간 뒤
4자리 확인이 무의미해지고 **모든 견적이 열린다.** service_role 로만 읽는다.
🔴 **응답 필드를 늘리지 말 것** — 차주 지급액·마진은 한 칸도 없고 **연락처도 담지
않는다**(뒤 4자리를 맞힌 사람이 전체 번호를 가져가면 안 된다). `select("*")` 로 바꾸면
그 순간 전부 새어 나간다.
🔴 **만료 컬럼을 새로 만들지 말 것** — 유효기간은 **견적서 자신의 것**(발행일 + 7일)을
쓴다. 견적서 PDF·엑셀이 이미 그 값을 인쇄하므로, 별도 컬럼을 두면 **문서에 적힌
유효기간과 링크가 막히는 날짜가 갈린다.** 기준은 `created_at` 이고 발급 시각이 아니다.
🔴 **토큰은 견적당 한 번만 발급한다** — 보낼 때마다 새로 만들면 **먼저 받은 문자의
링크가 죽는다**(같은 견적을 두 번 안내하는 일은 흔하다). **백필하지 않는다** —
보낸 적 없는 견적서의 링크가 DB 에 쌓인다.
🔴 **실패 사유를 「토큰이 틀렸다/4자리가 틀렸다」로 가르지 않는다** — 가르면 남의 링크를
주운 사람에게 *"이 토큰은 맞다"*를 알려주는 셈이다(32차 로그인 문구와 같은 판단).
🔴 **원칙 11번** — `TopNav` 숨김 조건에 `/q/` 를 넣었다. 색인 차단은 **두 겹**
(`app/q/layout.tsx` 의 noindex + `app/robots.ts` 의 disallow).
🟢 `app/sitemap.ts` 는 동적 세그먼트를 건너뛰고 `/q` 에 `page.tsx` 가 없어서
**사이트맵에는 저절로 안 들어간다** — 손댈 것이 없었다.

⚠️ **한계를 정직하게 적어 둔다** — **뒤 4자리는 10,000 가지뿐이라 토큰을 이미 아는
사람에게는 벽이 아니라 과속방지턱이다**(32차 로그인 제한과 같은 성격이고 같은 부품
`LoginAttemptTracker` 를 쓴다). 진짜 방어선은 **토큰의 추측 불가능성**(22자 base62 ≈
131비트)이다. 이 확인이 막으려는 것은 「문자가 가족·동료에게 전달됐을 때 무심코
열리는 것」이고 그건 확실히 막는다.

### ⑨ 곁다리 — 클라이언트 화면이 `crypto` 를 import 하고 있었다

공유 견적서 화면은 **클라이언트 컴포넌트**인데 「유효기간 7일」 숫자 하나 때문에
`lib/quoteShare.ts` 를 import 하고 있었다. 그 파일은 토큰 생성용으로 **top-level 에서
`crypto` 를 import** 한다 — 번들러가 그 노드 모듈을 클라이언트 번들로 끌어오는 구조다.

⚠️ **재지 못해서 고쳤다.** 이 환경은 빌드가 프리렌더 단계에서 멈춰(46건, 기준선)
클라이언트 청크가 안 나온다 — 「괜찮을 것」으로 넘기는 대신 위험 자체를 없앴다.
🔴 **`lib/quoteValidity.ts`(의존성 0인 파일)로 분리했고 `quoteShare` 에서 재수출하지
않았다** — 재수출하면 클라이언트가 그 파일을 거쳐 가므로 같은 일이 그대로 벌어진다.
⚠️ 같은 「발행일 + 7일」이 **세 곳에 숫자로 박혀 있다**(견적서 print 2종 ·
`lib/quoteExcel.ts`). 지금은 넷이 우연히 같은 값이라 안 건드렸고 주석에 남겼다 —
🔴 **유효기간을 바꿀 일이 생기면 그 셋도 같이 볼 것.**

### ⑩ merge 직후 겪은 것 — 문자 링크가 404

사용자 신고: *"문자를 실제로 보냈는데 링크가 제대로 안열린다. 404 오류 메시지가 뜬다."*

🟢 **코드 버그가 아니라 배포 상태였다.** 문자에 실리는 주소는 `lib/siteUrl.ts` 의
**상수**(운영 도메인)인데 `/q/[token]` 화면은 **PR 브랜치(Preview)에만** 있었다.
운영에 그 경로가 없으니 Next 가 404 를 돌려준 것이다(`git ls-tree origin/main` 으로
확인 — `app/q/` 0건). `next.config.mjs` 에 redirect·rewrite 없고 middleware matcher 는
`/admin/:path*` 뿐이라 설정 쪽 원인은 전부 배제했다.

🔴 **`SITE_URL` 을 환경변수로 바꾸지 않았다** — `lib/siteUrl.ts` 가 **명시적으로 거부한
방식**이고(Vercel 에서 Production 만 체크하고 Preview 를 빠뜨리는 함정), 무엇보다
**고객에게 나가는 문자에 Preview 주소가 실릴 위험**이 지금 겪는 불편보다 훨씬 크다.
🟢 **이미 보낸 문자는 merge 와 함께 살아난다** — 토큰이 DB 에 그대로 있고 주소도
같아서 다시 보낼 필요가 없다.
🔴 **다음에 이런 기능을 또 만들면 「merge 전에는 문자를 보내지 말 것」을 먼저 말할 것** —
사용자가 실제 고객에게 죽은 링크를 보낼 뻔했다.
