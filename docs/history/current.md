### ② 취소 배지를 재배차 접수중에도 유지 — 🔴 규칙이 「배차확정까지」로 바뀌었다

🔴 **규칙 한 줄 — 취소 배지는 「취소된 순간부터 배차확정까지」 뜬다.** 취소된 카드에도
뜨고, **재배차가 접수된 뒤에는 그 새 카드가 이력을 이어받는다.** 배차가 확정되면(단계 1)
사라진다.

🔴 **그전에는 재배차가 접수되는 순간 배지가 사라졌다.** 이유는 구조다 —
`filterCancelledForCustomer` 가 **살아 있는 배차가 있는 오더의 취소 카드를 감추는데**
(카드가 둘이 되는 것을 막으려고) **새 카드는 취소 이력을 모른다.** 그래서 화주 화면에서
「배차 취소 · 재배차 접수 중」이 **한 순간에 그냥 「접수」로** 바뀌었다.

🔴 **카드가 둘이 되는 것은 그대로 막는다** — 취소 카드는 여전히 감춘다. 다만 **감춰도
정보가 사라지지 않는다**(새 카드가 말한다). 🟢 **감췄던 이유(어느 것이 유효한지 모른다)가
이것으로 해소됐다.**

🔴 **판정의 정의처는 `lib/portalCancelledDispatches.ts` 하나**이고 **홈·조회 두 화면이
같이 쓴다** —
```
  filterCancelledForCustomer()  →  { rows, redispatch }
      rows       : 보여줄 행(취소 카드 정리 후)
      redispatch : order_id → 그 오더의 가장 최근 취소 사유
                   🔴 **아직 배차확정 전인 살아 있는 배차가 있는 오더만** 담는다
                      → 배차가 확정되는 순간 배지가 저절로 사라진다(화면이 지울 필요 없다)
  getPortalCancelNotice(row, redispatch)  →  { reason } | null
      ① 취소된 카드 자체        → 그 카드의 사유
      ② 재배차 접수중(단계 0)   → 그 오더의 가장 최근 취소 사유
      ③ 그 밖                   → null
```
🔴 **화면에서 `isDispatchCancelled(d.dispatch_status)` 로 다시 적지 말 것** — 그러면
재배차 접수 순간 배지가 사라진다(고치기 전 동작으로 정확히 되돌아간다).

🔴 **단계 판정은 `lib/dispatchStage.ts` 가 한다** — 이 파일에 `"접수중"` 문자열을 적지
말 것. `문제발생` 처럼 **상태값이 단계를 안 말해주는 값**이 있어서 boolean 두 개로
복원해야 한다(29차가 세운 규칙).

🔴 **형제 배차를 화면이 들고 있는 목록에서 찾지 말 것** — 조회 화면은 최근 100건, 홈은
5건만 받고 홈은 `운송완료`·`하차완료` 를 **아예 빼고** 받는다. 그 안에서 찾으면
① 재배차가 끝났는데 취소 카드가 남고 ② **취소 카드가 목록 밖이면 새 카드가 이력을 영영
모른다.** 그래서 필요할 때만 DB 에 한 번 더 묻는다 — 🟢 **취소도 없고 단계 0 도 없으면
질의 0회**(실측으로 확인).

🔴 **취소 카드를 고를 때는 DB 가 아니라 `rows` 안에서 가장 최근 것을 고른다** — 처음엔
DB 결과로 고르게 썼다가 되돌렸다. DB 기준이면 **그 행이 목록 밖일 때 어느 카드도 안
남아 통째로 사라진다**(홈은 5건이다).

🔴 **조회 실패는 「아무것도 감추지 않고 아무 배지도 안 붙이는」 쪽으로 떨어진다**
(원칙 55번) — 중복 카드는 눈에 보이지만 사라진 카드는 안 보인다.

🟢 **검색어도 같이 넓혔다** — 재배차 카드도 화면에 「배차 취소」라고 떠 있으므로
그 말로 찾을 수 있어야 한다(`isDispatchCancelled` 로만 보면 화면과 검색이 갈린다).

🟢 **보조 문구도 따라온다** — 재배차 접수중 카드의 알약 보조가 「배차 대기」가 아니라
**「재배차 대기」**다.

### ③ 오더 상세 「배차 상세보기」 — 🔴 원인은 정렬이 아예 없던 것이다

```ts
  // 고치기 전
  .from("dispatches").select("id").eq("order_id", id).limit(1).maybeSingle()
```
🔴 **정렬도 상태 조건도 없다.** PostgREST 는 `order` 가 없으면 **순서를 보장하지
않으므로**, 한 오더에 배차가 둘 이상이면 **어느 것이 잡힐지 알 수 없었다** — 취소 건이
잡히면 담당자가 죽은 배차를 연다. 지금은 `created_at` 내림차순으로 받아 **취소가 아닌
것을 먼저** 고른다.

🔴 **취소 건만 있을 때는 그 취소 건으로 보낸다** — 「배차관리로 이동」으로 바꾸면 방금
취소한 배차를 여는 길이 사라진다(**사유·경위가 거기에만 있다**).

🔴 **조회 실패를 삼키지 않는다**(원칙 55번) — 실패하면 버튼이 「배차관리로 이동」으로
바뀌어 **배차가 없는 것처럼 보인다.** 그래서 배너로 말한다.

🟢 **전후 대조로 버그를 재현했다**(검증 절 참고) — 고치기 전에는 정말로 취소 배차로 갔다.

### ④ 견적 금액 → 연결된 오더 청구금액

🔴 **그전에는 견적 금액이 오더로 넘어가는 길이 「오더 등록 때 한 번」뿐이었다**
(`app/admin/orders/page.tsx` 의 `?from_quote=` 프리필 · PR #153 이 만든 것). 배차가 안
잡혀 견적을 올려도 오더는 옛 금액 그대로였고, 담당자가 두 화면에서 같은 숫자를 두 번
고쳐야 했다.

🔴 **부가세 구분을 같이 쓴다** — `quotes.final_amount` 는 **공급가액(부가세 별도)**이다.
금액만 덮어쓰면 오더가 `customer_charge_vat_included = true` 인 경우 **같은 숫자가
포함가로 읽혀 공급가액이 10% 줄어든 채로** 배차·정산까지 승계된다. 🔴 **`false` 를 빼지
말 것** — **PR #153 이 프리필에서 겪은 그 자리**이고 같은 함정이 여기 또 있었다.

🔴 **정산(`invoices`)은 따라오지 않는다** — 생성 시점 스냅샷이다(원칙 47번). 맞추는
자리는 정산 상세의 **「배차 기준으로 금액 다시 맞추기」**(35차 A-7)다. 🔴 **여기서
`invoices` 를 같이 고치지 말 것 — 그것이 원칙 47번이 막는 바로 그 일이다.**

🔴 **배차(`dispatches.customer_charge`)도 따라오지 않는다** — 사용자가 말한 것은
오더이고, 배차의 화주 청구금액은 **배차 담당자가 배차 상세에서 정한다**(혼적 할인·현장
조정이 거기서 붙는다). 🔴 **조용히 같이 고치지 말 것** — 돈이고, 고치는 사람이 다르다.
대신 **화면이 「배차·정산 금액은 따로 확인하라」고 알린다**(입력칸 아래 안내 + 저장 후
결과 문구 + 확인 창 본문, 세 자리).

🔴 **묻지 않고 바로 반영하는 것이 기본이다**(그것이 지시다) — 오더가 이미
`배차완료`·`운송중`·`운송완료`면 그때만 한 번 확인한다. 🔴 **그 목록은 원칙 39번이 오더의
정산방식을 잠그는 것과 같은 목록이다 — 갈라 적지 말 것**(`lib/quoteAmountSync.ts` 의
`ORDER_AMOUNT_SYNC_CONFIRM_STATUSES`). 사용자가 말한 상황(배차확정 전)은 확인 없이 지나간다.

🔴 **견적 금액이 비어 있으면 아무것도 하지 않는다** — 금액을 안 적은 견적으로 오더의
청구금액을 **지워 버리면** 배차·정산이 0원으로 흘러간다.
🔴 **금액이 그대로면 오더를 건드리지 않는다** — 괜한 `updated_at` 은 화주포털 목록에
**「업데이트」 알약**으로 뜬다(PR #164).

🔴 **견적 저장이 성공한 뒤에만 오더를 고친다** — 낙관적 잠금 충돌로 막힌 저장에서
오더만 바뀌면 두 화면의 금액이 갈린다. 반대로 **오더 반영이 실패해도 견적 저장을
되돌리지 않는다**(견적은 이미 저장됐고 오더는 오더 화면에서 고칠 수 있다) — 다만
**조용히 넘어가지 않는다**(원칙 55번).

🟢 **곁다리 — 연결 오더를 `count` 가 아니라 행으로 들고 있게 바꿨다.** 그전에는
`select("id", { count: "exact", head: true })` 로 **건수만** 셌다(`hasOrder` 는 이제 그
파생값이다). 🔴 **조회 실패를 삼키면 「금액을 고쳤는데 오더가 안 따라왔다」가 조용히
일어난다** — 그때는 저장이 오더를 **아예 손대지 않으므로** 배너로 말한다.

🟢 **정산방식 안내 문구도 고쳤다** — *「정산방식을 수정해도 기존 오더에는 자동 반영되지
않습니다」* 옆에 **「최종 견적금액은 함께 반영됩니다」**를 붙였다. 🔴 **안 붙이면 담당자가
금액도 안 넘어가는 줄 안다**(바로 위에 그렇게 적혀 있다).

### ⑤ 검증 — 목이 `order`·`limit`·`in` 을 실제로 적용한다

🔴 **원칙 56번을 처음부터 지켰다** — 목이 `select` 에 없는 컬럼을 요구하면 **42703 을
던지고**, `order`/`limit`/`in`/`not.in` 을 **진짜로 적용한다.**

⚠️ **그것이 실제로 값어치를 했다.** 처음 목은 `limit` 을 무시했는데, 그 상태로 ③ 의
「고치기 전」을 재니 `maybeSingle()` 이 **2행을 받아 에러**를 내며 `detailHref: null` 이
나왔다 — 「버그가 다르게 보이는」 거짓 재현이다. `limit` 을 구현하고 나서야 **before →
`d-cancel`** 이라는 진짜 증상이 나왔다.

```

### ① 정의처가 `lib/` 이 아니라 부품 파일 안에 있었다

`grep -rn "getDateRange" lib/` 가 **0건**이다. `DatePreset` 도 `getDateRange()` 도

### ② 🔴 끝날은 그 날을 포함한다 — `to` 는 「종료일 **다음 날** 자정」이고 `.lt()` 로 쓴다

`getDateRange()` 가 이제 `{ from, to }` 를 돌려주고, 직접지정일 때만 `to` 가 채워진다.
🔴 **그 날 자정을 `.lte()` 로 비교하는 쪽으로 바꾸지 말 것** — 종료일 **00:00 이후에
생긴 건이 통째로 빠진다**(9월 15일까지로 골랐는데 15일에 등록한 건이 하나도 안 나온다).
화주포털 `Pv2PeriodFilter` 가 PR #155 에서 겪은 그 자리이고, 이번에는 **정의처 주석에
「호출부는 반드시 `.lt()` 로 쓸 것」을 못박았다.**

### ③ 🔴 `"YYYY-MM-DD"` 를 `new Date(문자열)` 로 읽지 않는다

`new Date("2026-09-01")` 은 **UTC 자정**이라 KST 에서는 **9월 1일 09:00** 이 된다 —
그대로 쓰면 하루가 밀려 **8월 31일 09:00 이전 건이 딸려 들어온다.** 정규식으로 갈라
`new Date(y, m-1, d)`(로컬 자정)로 만든다. 원칙 41번(`lib/localDateTime.ts`)과 같은 결이다.
🟢 **검증을 `timezoneId: "Asia/Seoul"` 로 돌려 `from === "2026-08-31T15:00:00.000Z"` 까지
확인했다** — 🔴 **이 컨테이너는 TZ 가 UTC 라 그냥 재면 이 버그가 안 잡힌다.**

### ④ 🔴 화주포털 부품을 끌어오지 않았다 (원칙 57번)

`Pv2PeriodFilter` 를 그대로 쓰면 `--pv2-*` 토큰이 `.portal-v2` 스코프 안에만 있어서
**관리자에서는 색이 안 나온다**(PR #145 가 `--pv2-yellow` 로 실측한 자리). 같은 동작을
관리자 생김새(`.date-range-*`)로 옮겼고 **프리셋 계산만 정의처를 함께 쓴다.**
🔴 **프리셋(오늘·이번주·이번달·전체) 계산은 한 글자도 안 바꿨다** — 화주포털과 뜻이
갈리면 같은 「이번주」가 두 값이 된다.
🔴 모바일 규칙은 `.date-range-custom .date-range-date` **두 클래스**다(원칙 58번) —
`.date-range-date` 한 클래스로 내리면 데스크탑 폭까지 같이 줄어든다.

### ⑤ opt-in 이라 나머지 네 화면은 한 글자도 안 바뀐다

`DateRangeFilter` 를 쓰는 관리자 화면은 **여덟**이다(견적·오더·배차·정산 + **화주신청 ·
발주요청 · 공개문의 · 문자이력**). `custom`/`onCustomChange` 를 **선택 prop** 으로 두고
**`onCustomChange` 가 없으면 「직접지정」 버튼 자체를 안 그린다.**
🟢 나머지 넷을 실제로 렌더링해 **프리셋이 여전히 넷**이고 예외 0 인 것을 확인했다.
🔴 **기본으로 켜지 말 것** — 사용자가 고른 것은 네 화면이고, 나머지 넷은 목록 성격이
다르다(신청·문의·문자 이력). 필요해지면 그 화면에서 두 prop 만 넘기면 된다.

### ⑥ 빈 구간을 만들지 않는다

직접지정을 처음 켜면 **이번달 1일 ~ 오늘**로 채운다 — 둘 다 비면 조회 조건이 없어져

     `평일 주간`·`평일 야간`이 둘 다 「평일」을 포함해서 배열 순서로 먼저 오는 쪽이 잡혔다
```
🔴 **부분일치로 되돌리지 말 것.**

규칙 정의처는 **`lib/transportTimeAuto.ts` 하나**이고 **세 화면**이 쓴다

```

  06:00 ~ 07:59       출퇴근/혼잡      +10,000
  08:00 ~ 17:59       평일 주간        0
  18:00 ~ 19:59       출퇴근/혼잡      +10,000
  20:00 ~ 23:59       평일 야간        +10,000

⚠️ **그래서 18:00~19:59 상차 건의 견적이 0원 → +10,000원으로 오른다.**

🔴 **주말이 시간대보다 먼저다** — 기존 동작을 그대로 둔 것이다. 바꾸면 주말 새벽 건이

배차·운송 조회 카드의 번호 옆에 파란 알약을 단다.

🔴 **배너와 같은 조건으로 좁히지 말 것** — 사용자가 **「알림배너와 별개로」**라고 했다.
배너를 좁힌 만큼 **무엇이 바뀌었는지는 목록이 말해야** 하고, 그래서 「상차완료 알림은
빼되 화면에서는 보이게」가 둘 다 성립한다.
🔴 **훅이 필요한 이유 — 셸이 「마지막으로 본 시각」을 밀기 때문이다.**
`CustomerPortalShell` 은 그 화면에 들어온 순간 `markSeen(key)` 로 값을 **지금**으로
민다(배지를 0으로 만들려고). 목록이 그 뒤에 `getLastSeen()` 을 읽으면 **언제나
「바뀐 것 없음」**이다. 🔴 **화면에서 `getLastSeen()` 을 직접 읽지 말 것.**
🟢 **순서는 React 가 보장한다** — 자식(페이지) effect 가 부모(셸) effect 보다 먼저 돈다.
게다가 셸은 `markSeen` 전에 세션·계정을 `await` 하므로 **두 겹으로** 안전하다.
🔴 **`useState` 초기화 함수로 읽지 말 것** — 서버 렌더에서도 돌아 `null` 을 잡고
하이드레이션에서 값이 갈린다.
🔴 **첫 방문에는 아무것도 표시하지 않는다** — 기준값이 없으면 목록이 통째로 표시된다
(배너의 「첫 조회에는 울리지 않는다」와 같은 결).
🔴 **발주 요청 행에는 안 붙인다** — 그 행은 `대기중` 아니면 `반려` 뿐이고 반려는 빨간
「접수 반려」 알약으로 이미 눈에 띈다. 같은 뜻의 표시가 두 개가 된다.

### ⑤ 시각 비교는 **문자열로 하면 뒤집힌다**

🔴 Postgres 는 `…+00:00`(마이크로초), `toISOString()` 은 `…Z`(밀리초)라 **형식이 다르다.**
형식이 다르면 사전순은 못 믿는다 — **실측**:

```
  "2026-09-16T12:00:00.500+00:00" > "2026-09-16T12:00:00Z"   →  false   (`.` < `Z`)
  Date.parse 로 재면                                          →  true    (실제로 500ms 뒤)
```

🔴 **`isUpdatedSince()` 를 문자열 비교로 되돌리지 말 것.**
⚠️ **밀리초 아래는 `Date.parse` 가 버린다** — 기준값과 같은 밀리초에 바뀐 건은 표시되지
않는다. 그 한 건은 **화주 본인이 방금 일으킨 것**이라 실무에서 문제가 되지 않는다.
🔴 이것을 고치겠다고 문자열 비교로 돌아가지 말 것(위 함정이 훨씬 자주 걸린다).

### 🔴 두 신고가 한 뿌리였다

`lib/generateNumber.ts` 가 번호를 **「그날 만들어진 행 수 + 1」**로 만들고 있었다.

```
  오늘 001 · 002 · 003 을 만들고  002 를 지우면
    → 건수가 2 라 다음 번호가 003
    → 003 은 이미 있으므로 유니크 위반
    → 🔴 다시 눌러도 **같은 번호**를 뽑으므로 영영 실패
```

그리고 **발주요청은 「견적이 저장되는 순간」에 `승인됨` 이 된다**
(`app/admin/quotes/page.tsx` 의 `if (fromRequestId && newQuote)` — 화면 주석이

insert 가 실패하면 `newQuote` 가 null 이라 그 블록이 안 돌고, 요청이 `대기중` 으로 남아
**「화주요청」 배지가 안 사라진다.**

🔴 **오류 메시지 한 줄과 배지 한 개가 같은 원인이었다** — 신고를 둘로 보고 각각
고치러 갔으면 배지 쪽에서 멀쩡한 코드를 한참 봤을 것이다.

       견적번호 | 20260915 | 건수 3 | 최대번호 3 | OK
  ㉔-b 오더번호 | 다섯 날짜 전부 OK

```

### 고친 것

🔴 **「그날 최대 번호 + 1」이다.** 지워진 번호는 다시 쓰지 않고 비워 둔다 —
**번호는 연속이 아니라 유일하기만 하면 된다.**

🔴 **동시 저장은 번호 계산만으로 막을 수 없다**(§7 의 「먼저 조회해서 없으면 insert」
함정). 두 사람이 같은 순간에 누르면 **둘 다 같은 최대값을 읽는다.** 그래서 **DB 유니크
제약을 방어선으로 두고 위반(`23505`)이면 번호를 다시 뽑아 재시도**한다 —
**`insertWithDailyNumber()` 한 곳**이고 상한 5회다.
🔴 **번호만 뽑아 쓰지 말고 그 함수를 쓸 것**(그래서 `generateDailyNumber` 를 export 에서
없애고 내부 함수 `nextDailyNumber` 로 바꿨다).
🔴 **호출부에서 `quote_no`·`order_no` 를 직접 넣지 말 것** — 함수가 채운다. 직접 넣으면
**재시도가 같은 번호를 다시 쓴다**(주석으로 못박았다).

🔴 **번호가 아닌 다른 유니크 위반은 재시도하지 않고 원문을 그대로 올린다** —
`error.code === "23505"` 만 보고 재시도하면 다른 유니크 컬럼(예: 사업자번호)이 겹친
경우에 몇 번을 다시 해도 같은 실패이고 **그동안 진짜 원인 메시지만 가려진다.**
`isDuplicateNumberError()` 가 **메시지·details 에 그 컬럼명이 있는지**까지 본다.

🔴 **조회 실패를 `001` 로 때우지 않는다**(원칙 55번) — 그러면 **그 자체가 중복**이 되어
화면에 **「중복」이라는 엉뚱한 원인**이 뜬다. 실패는 실패로 올리고 insert 를 아예 안 한다.

🔴 **`created_at` 이 아니라 번호 문자열로 그날을 고른다** — 번호에 박힌 날짜는 **로컬
날짜**인데 `created_at` 은 `timestamptz` 라 그 둘을 섞으면 **자정 전후에 어긋난다**
(원칙 41번과 같은 결).

🔴 **하루 1,000건을 넘어도 숫자로 비교한다** — `limit(1)` + 내림차순 정렬로 바꾸면
번호가 문자열이라 **`"1000" < "999"`** 가 되어 최대값을 잘못 집는다. 그날 것을 전부
받아(`DAILY_SCAN_LIMIT = 2000`) 코드에서 `parseInt` 로 비교한다. 형식이 깨진 옛 번호는
**건너뛴다**(`Number()` 로 바꾸면 `NaN` 이 최대값을 오염시킨다).

🟢 **`orders` 도 같은 함수를 쓰므로 함께 고쳐졌다.**
