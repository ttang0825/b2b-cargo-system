### ⑤ 🚨 리뷰가 채널의 주종을 뒤집었다

2·3차는 **포털이 주**이고 문자가 거드는 구조였다. 사용자 한 줄로 **문자가 주**가 됐고
포털은 **원하는 화주에게만 켜 주는 선택지**가 됐다.
🔴 **앞으로 「포털에서 보면 되니까」로 문자를 줄이지 말 것.**

**그래서 결함이 하나 드러났다** — 적립·차감 문자가 둘 다 「운송관리에서 적립 내역을

메뉴가 아예 없다.** 없는 화면을 찾아가라는 말이었다.
→ **`portalLine()` 한 곳**으로 모아 **켜진 화주에게만** 적는다.
🔴 **기본값은 「안 붙인다」** — 인자를 안 넘긴 호출부가 생겼을 때 **거짓말을 하는 쪽이
아니라 말을 아끼는 쪽**으로 떨어져야 한다.
⚠️ 그래서 꺼진 화주의 적립 문자가 **5줄 → 4줄**이 됐다(시험 단언도 같이 고쳤다 —
🔴 **5로 되돌리지 말 것**).

🔴 **`reward_earned`(쌓였다)와 합치지 말 것** — 이것은 **아직 안 쌓인 예상**이다.
한 종류로 묶으면 화주가 받은 문자가 「적립됐다」인지 「적립될 것이다」인지 **이력에서

🔴 **「현재 적립금」은 0원이어도 적는다** — 이 문자의 목적이 「얼마가 쌓이고 있는지」다

### ④ 🔴 통로는 `/api/customer/reward` 하나다

리워드 표 셋은 **RLS on + 정책 0개** 그대로다(1차 확정). 화주포털 계정과 직원 계정이
**둘 다 `authenticated`** 라 정책을 하나라도 열면 화주가 남의 회사 적립금을 읽는다.

- 🔴 **회사는 `Authorization: Bearer` 세션에서만 정한다**(원칙 30번) — 바디·쿼리로 받으면
  콘솔에서 남의 회사 id 를 넣어 읽는 구멍이 된다. 시험이 `?company_id=OTHER` 를 무시하는 것까지 잰다.
- 🔴 **`portal_visible` 이 꺼져 있으면 `{ visible: false }` 뿐이고 원장을 읽지도 않는다.**
- 🔴 **`enabled` 로는 감추지 않는다** — 그것은 「신규 적립 중단」이고 이미 쌓인 적립금은
  그대로다. 끄자마자 화주 잔액이 사라지면 그게 사고다.
- 🔴 **`?menu=1`** 은 멤버십 관문까지만 보고 `{visible}` 만 준다 — 포털 셸이 화면마다
  원장·오더번호까지 읽으면 메뉴 한 줄에 질의가 셋 더 붙는다.
- ⚠️ **`lib/rewardServer.ts` 의 `loadActiveCampaign()` 을 안 썼다** — 그 파일이
  `getCurrentStaff()`(직원 쿠키 세션)를 들여서, 화주 라우트가 import 하면 **직원용 인증
  코드가 이 경로에 딸려 들어온다.** 질의는 여섯 줄이라 따로 적었다.

### ⑤ 🔴 참여하지 않은 화주에게는 **아무것도 그리지 않는다**

메뉴(10번째 「적립금」) · 홈 카드 · 금액 셋 다 `portal_visible` 이 정한다.

- 🔴 **「0원」이나 참여 안내를 띄우지 말 것** — 리워드는 **선택된 기업만** 참여하는
  프로모션이라, 안내를 띄우면 **신청하면 되는 것으로 읽힌다**(표시광고법 제3조 ·
  HANDOFF §5-3 의 이벤트 안내 페이지와 같은 문제를 화면 하나 더 늘리지 않는다).
  빈 화면 문구는 **「적립 혜택 참여 여부는 담당자에게 문의해주세요」**이고 「신청」이라는
  말이 안 들어가는 것을 시험이 단언한다.
- 🔴 **거르는 일은 `NavList` 한 곳이다** — 사이드바와 바텀시트가 같은 함수를 쓰므로
  화면마다 거르면 「모바일에만 보이는 메뉴」가 생긴다.
- 🔴 **`companyId` 가 바뀔 때만 한 번 묻는다**(`?menu=1`) — 화면을 옮길 때마다 물으면
  메뉴 한 줄 때문에 이동마다 질의가 는다. 🔴 **되풀이 타이머를 만들지 말 것**(38차 원칙).
- 🔴 **조회 실패는 「안 그림」으로 떨어진다** — 「켜짐」으로 떨어뜨리면 없는 메뉴를 그려
  빈 화면으로 보낸다.
- 🔴 **홈 카드 조회는 `Promise.all` 에 넣지 않았고 `setLoading(false)` 뒤다** — 서버
  라우트를 거쳐 왕복이 길고, 참여하지 않은 화주가 대부분이라 보통은 그릴 것도 없다.
- 🟢 `PortalIcon` **11번째**(`reward` · 동전에 원화 표시 · **이미지 파일 0건, 인라인 path**).
  🔴 `invoices`(서류)를 돌려쓰면 정산과 뜻이 겹친다.

### ⑥ 🚨 문자는 자동이 아니다 — 리뷰가 뒤집은 자리

**첫 판본은 서버가 적립과 동시에 보냈다.** 사용자가 *"merge하면 문자가 확인절차 없이
자동으로 바로 나가나?"* 라고 물어 세어 봤더니 `sendSmsWithLog` 를 부르는 곳이 **셋뿐**이고,
앞의 둘(`send-sms` · `sms-logs/resend`)은 **담당자가 확인창에서 [발송]을 눌러야** 도는
자리였다(PR #73 리뷰에 그렇게 정했다). 내 것만 자동이었다 —
**이 시스템에서 사람 확인 없이 나가는 유일한 문자**가 될 뻔했다.
사용자 확정 **「(A) 확인창을 붙인다」**.

```
  전            accrueReward → notifyRewardEarned → sendSmsWithLog → 솔라피   (사람 없음)
  후   accrueReward → buildRewardSmsPreview → 라우트 → 화면 → SmsConfirmModal
                   → 담당자가 [발송] → /api/admin/send-sms → sendSmsWithLog
```

- 🔴 **`lib/rewardNotify.ts` 에 `sendSmsWithLog` 를 다시 들이지 말 것** — 들이는 순간
  창은 뜨는데 문자는 이미 나간 뒤가 되어 확인창이 무의미해진다.
- 🔴 **`accrueReward` 의 인자 이름이 `notify` → `withSmsPreview` 다** — 「보낸다」가 아니라
  **「미리보기를 만든다」**임을 이름이 말해야 한다.
- 🔴 **창이 떠 있는 동안 목록으로 나가지 않는다.** 정산 상세는 저장에 성공하면 곧바로
  목록으로 나가는 화면이라, 그대로 두면 **창이 그려질 화면이 사라져** 확인도 건너뛰기도
  못 한다. 「그 뒤에 할 일」을 `afterSmsRef` 에 넣어 두고 창이 끝난 뒤에 실행한다.
- 🔴 **`RELATED_TYPES`(send-sms) · `SmsPreview.relatedType` · DB CHECK 셋이 같아야 한다** —
  하나만 빠지면 [발송]이 **400 「필수 값이 누락되었습니다」**로 막힌다. 시험이 이것을 잰다.
- 🔴 **`key={preview.relatedId}` 다** — 배차 상세는 `templateType` 을 열쇠로 쓰지만 여기는
  **전부 `reward_earned`** 이라 구분이 안 된다(원장 줄 id 가 회사마다 다르다).
- 🔴 **발신번호·안내번호가 담당자 것이 됐다** — 자동 발송이던 때는 대표 발신번호였다.
  확인창을 거치면서 다른 여섯 종과 같아졌다.
- 🚨 **발신번호 조회가 실패해도 미리보기를 버리지 않는다** — `buildRewardSmsPreview` 전체가
  try/catch 안이라 거기서 던지면 **창이 통째로 안 뜨고** 담당자는 문자 차례였다는 것조차
  모른다(조용한 실패). 실제로 시험 하네스에서 이 자리가 먼저 터져 미리보기가 0개가 됐다.
  안내번호만 대표번호로 떨어뜨린다.

### ⑦ 🔴 한 번의 적립에 창 하나다

- 🔴 **회사별로 묶어 금액을 합친다** — 월정산 묶음은 13건이 한꺼번에 적립되는데 건별로
  만들면 **창이 13번** 뜬다. 시험이 그 주장을 단언으로 잡는다(52,000원 = 4,000 × 13).
- 🔴 **`already`(이미 적립됨)는 세지 않는다** — 두 번째 클릭에 창이 또 뜬다.
- 🔴 **소급 적립(`/api/admin/reward/backfill`)·수동 적립에서는 안 띄운다** — 소급은 한 번에
  최대 100건이라 켜면 **창이 100번** 뜬다. 두 라우트에 사유를 주석으로 적어 뒀다.
- 🔴 **회수(`reverse`)에서도 안 뜬다** — 「적립이 취소됐습니다」를 문자로 알리는 것은
  사용자가 정한 적이 없다(담당자가 말할 일이다).
- 🔴 **만드는 곳은 `accrueReward` 안 한 곳이다**(원칙 53번) — 적립이 나는 경로가 셋이라
  라우트마다 적으면 한쪽만 창이 뜬다.
- 🔴 **`ledger_id` 를 얻으려고 insert 에 `.select("id")` 를 붙였다** — 빼면 문자의
  `related_id` 를 채울 수 없어 이력에서 원장 줄로 못 돌아간다.

### ⑧ 🔴 문구에 약속을 적지 않는다

`rewardEarnedMessage` — **151byte LMS**(다른 여섯 종과 같다). 머리말 `[위캐리운송]` +
이번 적립액 + 누적 잔액 + 「운송관리에서 적립 내역을 확인하실 수 있습니다」 + 문의.

- 🚨 **지급 방식(상품권·운임 할인)을 적지 말 것** — 세무·법무 검수 전이고 **나간 문자는
  회수되지 않는다**. 시험이 「상품권」·「운임 할인」·「자동 적립」·「신청」이 없는 것을 단언한다.
- 🚨 **사용 조건(최소 금액·기한)을 적지 말 것** — 캠페인 값이라 바뀔 수 있다.
  포털 화면이 **그때의 값**으로 말한다.
- 🔴 **건별로 쪼개지 말 것** — 어느 오더인지·몇 %인지는 포털 「적립금」 화면이 말한다.
  이 문자는 「가서 보라」는 신호다.
- 🔴 **90byte 안에 넣으려 하지 말 것** — 머리말이나 문의 줄을 빼야 하는데 둘 다 뺄 수 없다.

### ② 🔴 지시서와 다르게 판단한 것 — `source_id` 에 FK 를 걸지 않았다

지시서는 `source_id` 를 **`on delete set null`** 로 하라고 했다(정산을 지워도 원장이
남아야 하므로). **그런데 FK 를 걸 수가 없다** — `source_type` 이
`invoice | billing_batch | manual` 이라 한 컬럼이 여러 표를 가리키는 **다형 참조**이고
Postgres 에는 다형 FK 가 없다.

🟢 **FK 를 아예 걸지 않는 것이 `set null` 보다 강하다.**

```
  · 정산을 지워도 원장은 그대로 남는다        ← 요구사항 충족(FK 가 없으니 cascade 도 없다)
  · `source_id` 값이 **그대로 남아** 부분 UNIQUE 가 계속 막는다
      🚨 `set null` 이면 **그 순간 유니크에서 빠져 재적립이 가능해진다**
  · 지워진 원본을 가리키던 id 가 남아 **무엇이 지워졌는지 추적**할 수 있다
```

🔴 대신 `description` 에 **원본 번호를 글자로** 남긴다(「운송 적립 — 오더 20260919001」).
🟢 **실제로 지워서 둘 다 확인했다** — 원장 1줄이 남고, 그 뒤 재적립 시도가 UNIQUE 에 막혔다.

### ③ 🔴 「브라우저가 부르니 `await` 하지 말라」를 뒤집었다

지시서 4-2 는 *「브라우저가 부릅니다 — `await` 하지 마십시오」*(원칙 53번)였다.

### ⑨ 🔴 체크 해제 = 회수 · 재적립은 수동 조정으로만

`payment_received` 가 `true → false` 로 가면 **`reversal` 로 반대 부호 한 줄**이 들어가고
**원본 적립행은 남는다.** 다시 체크해도 **UNIQUE 때문에 재적립이 막히는데 그것이 맞다** —
돈이 걸린 경로를 자동으로 왔다 갔다 하게 만들지 않는다. 필요하면 **수동 조정**이다.
🔴 **원본 적립행이 없으면 회수도 안 한다**(빈 회수를 만들지 말 것).
🟢 **배차 취소(§5-23)는 정산 전 단계라 적립이 아직 없다** — 손댈 것이 없다.

### ⑩ 🔴 적립 기준은 「기본 운임 공급가액」 하나다

```
  부가세 구분 = 선착불이면 **무조건 「별도」** · 그 밖에는 저장된 값   ← 🚨 ⑲
  공급가액   = splitVat(customer_charge_total − 스냅샷에 섞인 추가비, 그 구분).supply
  적립액     = 내림(공급가액 × 캠페인 요율, **10원 단위**)             ← 🚨 ⑳
```

⚠️ **두 줄이 리뷰에서 바뀌었다** — 착수 시점에는 「저장된 부가세 구분 그대로 · **1원 미만
절사**」였다. 🔴 **이 절의 옛 문장을 근거로 되돌리지 말 것**(⑲·⑳ 에 사유가 있다).
🔴 **부가세를 1.1 로 직접 나누지 말 것** — `splitVat` 이 정의처다(11,000원마다 1원).
🔴 **`Math.round` 가 아니다**(99,999 × 5% = 4,999.95 → **4,990**).
🔴 **요율을 코드에 리터럴로 적지 말 것** — 캠페인에서 읽고 `earn_rate_snapshot` 에 남긴다.
🔴 **빼는 추가비는 그 정산 건 생성 시점에 이미 포함된 것만**이다
(`created_at <= invoice.created_at` · `status='active'` · `correction_invoice_id is null` —
35차 A-7 과 같은 세 규칙). **그 뒤에 등록된 것은 스냅샷에 없으므로 빼면 두 번 깎인다.**
🔴 **추가비를 못 읽으면 0 으로 때우지 않고 `error` 로 돌려준다** — 0 이면 적립이 커지고
청구액 전체를 빼면 0 이 된다. **둘 다 조용히 틀린 값이다.**

### ⑪ 🚨 선착불은 **제외였다가 포함으로 뒤집혔다** (2026-09-21)

⚠️ **아래는 착수 시점(2026-09-20)의 「제외」 근거이고, 다음 날 사용자가 뒤집었다.**
🔴 **되돌리지 말 것** — 지금 선착불은 **적립 대상**이다(⑰). 그래도 이 근거를 지우지
않는 이유는, 「없다」고 봤던 **시점과 기준**을 무엇으로 채웠는지가 ⑰ 에서만 읽히기 때문이다.

선착불(`driver_direct`)은 **화주가 위캐리에 입금하지 않는다.** 운임은 차주가 직접 받고
위캐리가 받는 것은 주선수수료뿐이며 화주 미수금은 **0**이다(§5-12). 그래서 —

```
  ① 「화주 입금 확인」이라는 **사건 자체가 일어나지 않는다**   ← 적립 트리거가 없다   → ⑰ 이 채웠다
  ② `customer_charge_total` 은 **화주가 우리에게 낸 돈이 아니다** ← 적립 기준이 없다  → ⑰ 이 채웠다
```

🔴 **「부담이 크다」로 적으면 다음 세션이 「그럼 요율을 낮춰서 넣자」로 간다** — 이 문장은
**여전히 유효하다**(포함으로 바뀐 뒤에도 매출 대비 비중은 크다 · ⑰).
🔴 **선착불 판정을 새로 쓰지 않았다** — `lib/receivableCalc.ts` 와 같은 값이다.

### ⑳ 🚨 리뷰 5라운드 — 적립 단위 100원 → **10원** (`9bb7440`)

**적립 단위는 같은 차수에 두 번 바뀌었다** — 1원 절사(09-18) → **100원**(09-21) →
**10원**(09-21). 🔴 **100원으로도 1원으로도 되돌리지 말 것.**

담당자가 **월 정산에서 찾아냈다** — 공급가액 **1,172,000원 13건**의 5% 는 58,600 인데
화면이 **58,500** 을 보여줬다. 100원 단위가 **5%가 100원으로 안 떨어지는 건에서 50원씩**
깎은 것이다(65,000 → 3,250 → **3,200** · 125,000 → 6,250 → **6,200**).

🔴 **합계에 5% 를 걸어 58,600 을 만드는 길은 없다** — 적립은 **운송 건별로 원장에 한 줄씩**
쌓이므로(월정산 묶음도 마찬가지) 합계 기준 금액은 원장 줄의 합과 어긋난다. **그 어긋남을
없애려고 단위를 둔 것이고**, 답은 단위를 **줄이는** 것이다.
🟢 10원이면 그 두 건이 그대로 남아 **건별 합 = 합계의 5% = 58,600**.
⚠️ **깎이는 것 자체는 단위를 두는 한 없어지지 않는다**(10원이면 최대 9원).
🚨 **「표시만 10원 단위」로 만들지 말 것** — 적립액 자체를 10원 단위로 낸다. 화면에서만
내리면 **원장 합계(1원)와 화면 잔액(10원)이 갈리고** 건이 쌓일수록 커진다.
🟢 시험에 **이 달의 실제 13건을 그대로 넣어** 「건별 합 = 합계의 5% = 58,600」을 단언으로
못박았다 — 다음에 단위를 건드리면 **그 줄이 먼저 깨진다.**

**형제 둘을 같은 `top` 으로 각각 sticky 로 둘 수 없다** — 둘 다 같은 자리에 붙으려 해서
**서로 겹친다.** 그래서 둘을 감싼 `.quote-side` 를 sticky 로 만들고 계산 카드에서는
`position`·`top`·`alignSelf` 를 뗐다. 🔴 **계산 카드에 sticky 를 되돌리지 말 것.**

🔴 **`align-self: start` 를 빼지 말 것** — 격자 항목이라 안 주면 행 높이만큼 늘어나
sticky 가 움직일 자리가 없어진다.

🔴 **안에서 스크롤하는 것은 매뉴얼 목록뿐이다.** 처음에는 `.quote-side` 전체를
스크롤시켰는데 **매뉴얼을 읽으려고 내리면 자동 계산 결과가 화면 밖으로 밀려났다**
(렌더링해서 발견 — 코드만 봤으면 못 봤다). 지금은
`.quote-side > .card { flex-shrink: 0 }`(계산 결과는 안 줄어든다) +
`.call-script-panel { flex: 1 1 auto; min-height: 0 }` +
`.call-script-list { flex: 1 1 auto; min-height: 0; overflow-y: auto }` 셋이 **한 벌**이다.
🔴 **`min-height: 0` 을 빼지 말 것** — flex 항목의 기본 `min-height: auto` 때문에
안쪽 스크롤 영역이 생기지 않고 패널이 통째로 늘어난다.

⚠️ **폼이 접혀 있으면 따라다니지 않는다 — 고장이 아니다.** sticky 는 **자기 격자 칸
안에서만** 움직인다. 접힌 상태(PR #167 ③ 이 기본 접힘으로 만들었다)에서는 왼쪽 열
311px · 오른쪽 781px 이라 **따라갈 거리가 −470px** 이다. 상세 입력을 펼치면
(통화 중의 실제 상태) 왼쪽이 1681px 이라 **900px 을 따라오고 99px**
(= `--admin-topnav-h` 79 + 20) 자리에 고정된다. 🔴 **계산 패널도 전부터 같은 조건이었다** —
이 작업이 만든 제약이 아니다.

### ⑧ 🟢 검증 — 로컬 Postgres 16 · 부정 시험 5건

함정 31번대로 **운영 구조를 로컬에 복제해 실제로 돌렸다**(`staff_accounts` +
`is_active_staff()` + `authenticated` 롤 최소 복제). 부정 시험 **5건이 전부 의도한
단언에서 멈추고 롤백**된다 — 0행 · 싱글턴 제약 없음 · 배열 검사 없음 · 저장 미반영 ·
되돌림 실패.

🚨 **그중 둘은 처음에 엉뚱한 단언이 걸렸다.** UPDATE 를 통째로 막는 트리거를 걸었더니
**앞 시험(배열 검사)이 먼저 통과해 버려** 「배열이 아닌 값이 들어갔습니다」가 떴다.
값에 따라 가르는 트리거로 바꿔서야 의도한 단언이 걸렸다. 🔴 **PR #178 이 남긴
「멈췄다가 아니라 **의도한** 단언이 멈췄다를 볼 것」과 정확히 같은 자리다.**

🚨 **단언 하나가 되돌림을 「10줄인가」로 재고 있어서 2회차에서 멀쩡한 DB 를 멈춰 세웠다.**
씨앗이 `on conflict do nothing` 이라 재실행 시점에는 담당자가 이미 줄 수를 바꿔 놨을 수
있는데, **고정 숫자로 재면 그 DB 에서 마이그레이션이 통째로 실패한다.**
**시험 직전에 떠 둔 값**과 견주도록 고쳤고 `updated_at` 도 함께 되돌린다
(안 되돌리면 시험이 저장 시각을 앞으로 밀어 **첫 저장이 409 로 거절된다**).
🔴 **마이그레이션 단언에 고정 숫자를 쓸 때는 「재실행 시점에도 그 숫자인가」를 볼 것.**

🟢 **멱등 확인** — 담당자가 2줄로 고쳐 둔 상태에서 재실행했더니 내용도 `updated_at` 도

40줄을 넣어도 계산 결과가 화면에 남고(t=99..298) `listScrollable: true` ·
`sideScrollable: false` · 「+ 줄 추가」(761-792)와 「저장」(819-859)이 화면 안이다.

🟢 프리렌더 **46**(`origin/main` 과 항목 diff 0 — 🔴 **커밋 전이라 `git stash -u` 로
