떨어지는 값을 쓴다. ⚠️ **첨부 엑셀 `2_화주청구_v11` 과 이 세 칸이 다르다**
(엑셀은 41,000·113,000·151,000). **엑셀이 낡은 것이 아니니 엑셀에 맞춰 되돌리지 말 것.**
🔴 세 칸을 **SQL 단언으로 못박았다** — 값이 어긋나면 아무것도 반영되지 않는다.
🟢 역전을 만들지 않는 것을 확인했다: 3.5톤 100,000 < 5톤 115,000 <
5톤 플러스/축 150,000 < 8톤 164,000.
⚠️ 18톤 `200km 이내` 한 칸이 다른 것과 **같은 성격**이다 —
🔴 **「왜 이 칸만 다르지」 하고 ×1.15 로 맞추지 말 것.**

**═══ ③ 🔴 지시서가 말한 범위보다 실제가 훨씬 컸다 — 실측으로 드러났다 ═══**
지시서 5장은 **「공개 기준가 5개가 바뀐다」**고만 적었는데, 165행을 전수 조회해
대조하니:
```
  165칸 중   인상 164칸 · 변화 없음 1칸(1톤 10km) · **인하 0칸**
  배율        최소 ×1.026 · 중앙 ×1.253 · 최대 ×1.376
  구간별      전 구간 ×1.215~1.225 로 균일 (특정 구간만 오르는 것이 아니다)
  차급별      1톤·1.4톤 +3% · 25톤 +15% · 2.5~15톤 +25~31% · 5톤+/축 **+37%**
```
🔴 **게시 6칸이 아니라 견적 전체가 평균 +22% 오르는 일이었다.** 그래서 착수 전
보고에서 이 사실을 따로 짚고 **승인을 두 번**(전체 인상 · 게시 6칸) 받은 뒤 진행했다.
⚠️ **지시서 숫자를 그대로 믿고 apply 했으면 사용자가 모르는 채로 전체 견적가가
올랐을 것이다** — 「현행」을 실측해서 대조표를 만드는 절차(1장 1·2번)가 실제로
값어치를 한 자리다.

**═══ ④ 🔴 차급명은 `5톤 플러스/축` 이다 (엑셀·지시서 표기와 다르다) ═══**
지시서 2-1 표와 엑셀 열 머리는 **「5톤+/축」**인데 **DB 값은 `5톤 플러스/축`**
(공백 포함 8글자)이다. 견적 매칭이 **문자열 완전일치**라 이걸 틀리면 그 15행이
**조용히 안 바뀐다**(에러도 경고도 없다). ② 단언에 「예상 밖의 차급명이 있으면 중단」을
넣어 막았다.

**═══ ⑤ 🔴 값을 손으로 옮기지 않았다 ═══**
엑셀에서 **프로그램으로 뽑아** SQL 을 생성하고, 생성 뒤 165행을 엑셀과 **다시 전수
대조**했다. 한 칸만 틀려도 **그 칸의 견적만** 조용히 어긋나서 한참 뒤에 발견된다.
```
  대조 4중   지시서 2-1 표 ↔ 엑셀 2_화주청구_v11 ↔ 생성 SQL ↔ 운영 DB(apply 후)
  결과       165칸 전부 불일치 0
  ×1.15 검산  v10 있는 135칸 중 어긋난 칸 = 위 ② 세 칸뿐
  보간 검산   8톤 = (5톤+/축+11톤)/2 · 15톤 = (11톤+18톤)/2 → 어긋난 칸 0
```
⚠️ **파이썬 `round(x, -3)` 을 쓰면 안 된다** — 부동소수점 때문에 `90000*1.15` 가
103499.99… 가 되어 103,000 으로 내려간다. `Decimal` + `ROUND_HALF_UP` 으로 재야
엑셀 `ROUND()` 와 같다. 이걸 모르고 처음에 「어긋난 칸 12개」라는 **거짓 ❌** 를 냈다.
