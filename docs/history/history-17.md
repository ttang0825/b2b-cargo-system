### ① 「왕복,편도 드롭메뉴 안됨」의 정체는 **키 한 글자**였다

```
app/quote/page.tsx   surcharge["왕복편도"]   ← 슬래시가 없다
```

`rate_surcharges.category` 의 실제 이름은 **`왕복/편도`**(슬래시 포함)다. 이 화면만
빠뜨려 그 칸이 **빈 배열**이 됐고, 드롭다운을 눌러도 항목이 하나도 없었다.
🔴 **예외도 경고도 나지 않는다** — 원칙 55번과 같은 결의 조용한 실패다.

🟢 **다른 화면 넷은 전부 맞았다**(포털 발주요청 4곳 · 관리자 견적 등록·상세 · 포털
견적확인). 같은 파일의 `물품특성`·`운송시간` 도 맞았고 **`왕복/편도` 하나만** 틀렸다.

🔴 **재현했다** — 목 데이터 3종을 내려주고 키에서 슬래시를 뺀 판본으로 실제 렌더링:
고치기 전 `[]` → 고친 뒤 `["편도","왕복","회수/재방문"]`. **신고와 정확히 일치했다.**

🔴 **`SURCHARGE_KEYS` 상수를 두고 세 칸 모두 그것으로 바꿨다** — 화면에서 카테고리
문자열을 직접 적지 말 것. 이번에 고친 버그가 정확히 「직접 적다가 슬래시를 빠뜨린 것」이다.

### ② 필수 표시는 **정말 0건**이었고, 리뷰에서 빨간 `*` 로 뒤집혔다

착수 전 실측: `req-marks`·`field-required`·`required` **전부 0건**. 카드 제목만
「필수 입력」이고 실제로 제출을 막는 넷 옆에 톤수·차종·운송물건이 **똑같은 모양**으로
섞여 있었다.

본작업에서는 `/apply` 에 이미 있던 `requiredMark`(회색 「필수」 글자)를
`components/landing/form/Fields.tsx` 로 옮겨 정의처를 하나로 만들었다.
🔴 **그런데 리뷰 1라운드에 사용자가 빨간 `*` 로 바꾸라고 했다** — 31차 리뷰가 확정했던
「빨간 `*` 가 아니라 회색 「필수」 글자」가 **뒤집힌 것이다. 그 옛 결정을 근거로
글자로 되돌리지 말 것.**

🔴 **범위가 화주포털까지 넓어졌다**(사용자 지시 *"이부분은 화주포털 발주요청도 마찬가지로"*).
⚠️ **포털에 필수 표시가 없던 게 아니었다** — **검정 `*` 가 부제와 placeholder 안에
문자로** 박혀 있었다(`"상차지 정보 *"` · `"출발지 주소 검색 또는 직접 입력 *"`).
🔴 **placeholder 는 값을 입력하면 사라져서 표시 역할을 못 한다** — 제목 옆으로 옮겼고
문자 `*` 는 지웠다. **문자로 되돌리지 말 것.**

🔴 **색은 한 값(`#B4423A`)이고 정의처를 둘로 갈랐다** — 공개 폼은 `Fields.tsx` 의
`REQUIRED_MARK_COLOR`(인라인 style), 포털은 `globals.css` 의 `.pv2-req`.
**공개 폼 부품을 포털에 import 하지 않으려고 가른 것**이고(원칙 57번),
🔴 **한쪽을 고치면 반대쪽도 같이 고칠 것.** 실제로 그려서 **색·크기·굵기가 같음을
확인했다**(`rgb(180,66,58)` · 15px · 700).
🔴 **`--pv2-*` 토큰을 새로 만들지 않은 것은 의도다** — 만들면 포털 전용이 되어 공개 폼과
값을 맞출 수 없다(PR #145 가 같은 판단을 했다).

🟢 **`/apply` 도 같은 정의처라 함께 바뀌었다** — 사용자가 든 것은 앞의 둘이지만
`/apply` 만 회색 글자로 남으면 공개 폼 둘이 갈린다. **merge 보고에 밝혔다.**
🔴 **동의 카드(`LandingConsentCard`)의 자체 「필수」 배지는 안 건드렸다** — 그것은
라벨 옆 표시가 아니라 카드 제목 옆 배지이고 12px `#8B8A85` 로 성격이 다르다.

⚠️ **네이티브 `required` 를 쓰지 않는 것은 그대로다**(폼에 `noValidate` 가 있다) —
브라우저 검사가 React 핸들러보다 먼저 걸리면 우리 오류 문구가 안 뜬다(PR #121).
**표시는 안내이고 막는 것은 제출 직전 검사다 — 둘이 어긋나지 않게 할 것.**

🟢 **곁다리 — 제출 검사 순서를 화면 순서와 맞췄다.** 출발지가 비었는데
「성함(업체명)과 연락처를 입력해주세요」가 뜨고 있었다. 「필수」 표시와 안내가
서로 다른 곳을 가리키면 안 된다.

### ③ B장 — 일정을 발주요청과 맞췄다

착수 전 실측에서 **`/quote` 가 `DateTimePicker` 를 아예 안 쓴다**는 것이 드러났다.
자체 부품 `DatePicker`(달력) + `Dropdown`(시간, `timeSlots()` 06:00~22:00 30분)
**두 칸**이고, 빠른 버튼은 `quickDateButtons` 의 **「오늘」·「내일」 둘뿐**이었다.
하차 하한은 `minKey` 로 **날짜만** 막고 **+30분이 없었다.**

넣은 것 넷 — 상차 **「지금」 칩** · 하차 **「당착」·「내착」 칩** · **하차 +30분 하한**
(`lib/dropoffGap.ts`) · **안내 한 줄**.

🔴 **포털 부품(`components/pv2/Pv2DateTimeField.tsx`)을 끌어오지 않았다** — `.pv2-*`
스코프가 통째로 딸려온다(원칙 57번). **같은 동작을 랜딩 생김새로 옮긴 것**이고
자리 채움 시각(`ARRIVAL_FILLER_TIME`)과 하차 하한만 정의처를 함께 쓴다.
**36차 PR 2 가 관리자에 한 것과 같은 방식이다.**

🔴 **칩이 켜지면 날짜·시간 칸을 잠근다** — 「지금」·「당착」은 **시각을 담지 않는
선택지**라 손으로 고친 값이 남아 있으면 무엇이 요청인지 갈린다. `Dropdown`·`DatePicker`
에 `disabled` 를 넣었고 🟢 **둘 다 `/quote` 한 화면만 쓴다**(전수 확인) — 그것이
다른 화면 무회귀의 근거다.

🔴 **당착·내착이면 특이사항에 하차 일시를 적지 않는다** — `23:59` 는 자리 채움이라
「23:59 도착 요청」으로 읽히면 안 된다. `arrivalNoteLine()` 한 줄을 대신 쓴다.
**견적 전환 프리필과 같은 줄**이라 중복 판정이 성립한다.
🔴 **당착·내착은 +30분 하한의 예외다**(27차·36차 D장) — 규칙을 걸면 23:40 상차 건이 막힌다.
🔴 **`public_quote_requests` 에 도착구분 컬럼을 만들지 않았다**(28차와 같은 판단).

🔴 **상차 날짜를 바꾸면 당착·내착이 따라간다** — 안 따라가면 「당착」이라 적혀 있는데
하차 날짜는 옛 상차일에 묶인 상태가 되고, **칸이 잠겨 있어 손으로 못 고친다.**
🔴 **날짜 더하기는 `Date` 로 한다** — 문자열을 자르면 월말(09-30 → 10-01)에서 어긋난다.

🟢 **같은 날이면 상차 +30분보다 이른 시각을 목록에서 아예 뺀다**(달력은 날짜만 막는다).
그래서 **제출 직전 검사가 필요한 경우는 「나중에 상차를 늦췄을 때」뿐이다** —
시험 시나리오를 그렇게 짜야 재현된다(처음엔 슬롯이 막아서 재현이 안 됐다).

### ④ C장 — 운송시간 자동선택. **관리자에 이미 있었고 틀렸다**

🔴 **착수 전 확인에서 가장 값이 컸던 발견이다.** `app/admin/quotes/page.tsx` 에
「희망 상차일시 → 운송시간 자동선택」이 **이미 있었고 결함이 둘**이었다.

```
  ① 출퇴근/혼잡(+10,000)·새벽(+20,000)을 아예 안 썼다
     `hour < 8 || hour >= 20` 을 전부 「평일 야간」으로 봐서 새벽 3시도 야간이었다
  ② `options.find(o => o.includes("평일") || o.includes("주간"))`
     `평일 주간`·`평일 야간`이 둘 다 「평일」을 포함해서 배열 순서로 먼저 오는 쪽이 잡혔다
```
🔴 **부분일치로 되돌리지 말 것.**

규칙 정의처는 **`lib/transportTimeAuto.ts` 하나**이고 **세 화면**이 쓴다
(견적문의 · 화주포털 발주요청 · 관리자 견적 등록).

```
  토·일                주말            (🔴 시간대보다 먼저다)
  00:00 ~ 05:59       새벽            +20,000
  06:00 ~ 07:59       출퇴근/혼잡      +10,000
  08:00 ~ 17:59       평일 주간        0
  18:00 ~ 19:59       출퇴근/혼잡      +10,000
  20:00 ~ 23:59       평일 야간        +10,000
```

⚠️ **그래서 18:00~19:59 상차 건의 견적이 0원 → +10,000원으로 오른다.**
🔴 **사용자 확정이다**(AskUserQuestion — 「여섯 종 전부 자동」). 06:00~07:59 는
지금도 +10,000 이라 **이름만** 바뀐다. **금액이 바뀌는 자리라 물어서 확정받았다.**

🔴 **주말이 시간대보다 먼저다** — 기존 동작을 그대로 둔 것이다. 바꾸면 주말 새벽 건이
`주말`(+10,000) → `새벽`(+20,000)으로 **또 금액이 오른다.**
⚠️ 새벽이 더 어려운 시간이라 반대가 맞다는 의견이 있을 수 있다 — 🔴 **바꾸려면 먼저 물을 것.**

🔴 **`공휴일`은 자동으로 못 고른다** — 저장소에 공휴일 달력이 없다. 목록에는 그대로 있어
담당자·화주가 직접 고른다. 🔴 **달력을 하드코딩하지 말 것**(매년 바뀐다).

🔴 **실제로 내려온 선택지 목록 안에 있을 때만 값을 준다**(`autoTransportTime` 의
`available` 인자) — 이름이 바뀌면 틀린 값을 넣는 대신 **아무것도 안 고른다.**
`option_name` 완전일치라 한 글자만 달라도 가산이 조용히 빠지는 자리다.
🔴 **`available` 을 생략 가능하게 만들지 말 것.**

🟢 **직접 바꾼 값은 남는다.** 다만 **상차일시를 다시 고치면 또 자동으로 맞춰진다** —
관리자 화면이 전부터 그렇게 동작했고 세 화면이 같아야 한다.

### ⑤ 시각 비교는 **문자열로 하면 뒤집힌다**

🔴 Postgres 는 `…+00:00`(마이크로초), `toISOString()` 은 `…Z`(밀리초)라 **형식이 다르다.**
형식이 다르면 사전순은 못 믿는다 — **실측**:

```
  "2026-09-16T12:00:00.500+00:00" > "2026-09-16T12:00:00Z"   →  false   (`.` < `Z`)
  Date.parse 로 재면                                          →  true    (실제로 500ms 뒤)
```

🔴 **`isUpdatedSince()` 를 문자열 비교로 되돌리지 말 것.**
⚠️ **밀리초 아래는 `Date.parse` 가 버린다** — 기준값과 같은 밀리초에 바뀐 건은 표시되지
않는다. 그 한 건은 **화주 본인이 방금 일으킨 것**이라 실무에서 문제가 되지 않는다.
🔴 이것을 고치겠다고 문자열 비교로 돌아가지 말 것(위 함정이 훨씬 자주 걸린다).

### 🔴 두 신고가 한 뿌리였다

`lib/generateNumber.ts` 가 번호를 **「그날 만들어진 행 수 + 1」**로 만들고 있었다.

```
  오늘 001 · 002 · 003 을 만들고  002 를 지우면
    → 건수가 2 라 다음 번호가 003
    → 003 은 이미 있으므로 유니크 위반
    → 🔴 다시 눌러도 **같은 번호**를 뽑으므로 영영 실패
```

그리고 **발주요청은 「견적이 저장되는 순간」에 `승인됨` 이 된다**
(`app/admin/quotes/page.tsx` 의 `if (fromRequestId && newQuote)` — 화면 주석이
*「실제 상태 변경은 그 견적이 저장되는 순간 자동으로 처리됩니다」*라고 적고 있다).
insert 가 실패하면 `newQuote` 가 null 이라 그 블록이 안 돌고, 요청이 `대기중` 으로 남아
**「화주요청」 배지가 안 사라진다.**

🔴 **오류 메시지 한 줄과 배지 한 개가 같은 원인이었다** — 신고를 둘로 보고 각각
고치러 갔으면 배지 쪽에서 멀쩡한 코드를 한참 봤을 것이다.

`_verify.sql` 에 **㉔** 을 신설해서 `verify` 를 돌렸다:

```

       견적번호 | 20260915 | 건수 3 | 최대번호 3 | OK
  ㉔-b 오더번호 | 다섯 날짜 전부 OK
  ㉔-c 실제 중복                                   0행(제약이 막고 있다)
  ㉔-d 제약     quotes_quote_no_key · orders_order_no_key  둘 다 UNIQUE
  ㉔-e 발주요청 | 대기중 1 · 승인됨 7             ← 저장이 막힌 그 건
```

🟢 **신고와 정확히 일치했다.** 🟢 **`orders` 에도 유니크 제약이 이미 있어서** 제약을
새로 거는 마이그레이션이 필요 없었고 그래서 **DB 변경이 0** 이다.

### 고친 것

🔴 **「그날 최대 번호 + 1」이다.** 지워진 번호는 다시 쓰지 않고 비워 둔다 —
**번호는 연속이 아니라 유일하기만 하면 된다.**

🔴 **동시 저장은 번호 계산만으로 막을 수 없다**(§7 의 「먼저 조회해서 없으면 insert」
함정). 두 사람이 같은 순간에 누르면 **둘 다 같은 최대값을 읽는다.** 그래서 **DB 유니크
제약을 방어선으로 두고 위반(`23505`)이면 번호를 다시 뽑아 재시도**한다 —
**`insertWithDailyNumber()` 한 곳**이고 상한 5회다.
🔴 **번호만 뽑아 쓰지 말고 그 함수를 쓸 것**(그래서 `generateDailyNumber` 를 export 에서
없애고 내부 함수 `nextDailyNumber` 로 바꿨다).
🔴 **호출부에서 `quote_no`·`order_no` 를 직접 넣지 말 것** — 함수가 채운다. 직접 넣으면
**재시도가 같은 번호를 다시 쓴다**(주석으로 못박았다).

🔴 **번호가 아닌 다른 유니크 위반은 재시도하지 않고 원문을 그대로 올린다** —
`error.code === "23505"` 만 보고 재시도하면 다른 유니크 컬럼(예: 사업자번호)이 겹친
경우에 몇 번을 다시 해도 같은 실패이고 **그동안 진짜 원인 메시지만 가려진다.**
`isDuplicateNumberError()` 가 **메시지·details 에 그 컬럼명이 있는지**까지 본다.

🔴 **조회 실패를 `001` 로 때우지 않는다**(원칙 55번) — 그러면 **그 자체가 중복**이 되어
화면에 **「중복」이라는 엉뚱한 원인**이 뜬다. 실패는 실패로 올리고 insert 를 아예 안 한다.

🔴 **`created_at` 이 아니라 번호 문자열로 그날을 고른다** — 번호에 박힌 날짜는 **로컬
날짜**인데 `created_at` 은 `timestamptz` 라 그 둘을 섞으면 **자정 전후에 어긋난다**
(원칙 41번과 같은 결).

🔴 **하루 1,000건을 넘어도 숫자로 비교한다** — `limit(1)` + 내림차순 정렬로 바꾸면
번호가 문자열이라 **`"1000" < "999"`** 가 되어 최대값을 잘못 집는다. 그날 것을 전부
받아(`DAILY_SCAN_LIMIT = 2000`) 코드에서 `parseInt` 로 비교한다. 형식이 깨진 옛 번호는
**건너뛴다**(`Number()` 로 바꾸면 `NaN` 이 최대값을 오염시킨다).

🟢 **`orders` 도 같은 함수를 쓰므로 함께 고쳐졌다.**
