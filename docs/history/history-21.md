### ③ 🔴 지시와 다르게 판단한 것 — 차급 역전 검사를 「완화」하되 좁게

기존 검사는 `다마스 < 라보 < 1톤 < …` **엄격 증가**였다(v12 A장 ④ · `_verify.sql` ⑥-b).
다마스 = 라보 가 되면 **그 검사가 15칸 전부를 역전으로 잡아 마이그레이션이 멈춘다.**

🔴 **`<=` 를 전부 `<` 로 바꾸지 않았다** — 그러면 나머지 11쌍의 동가까지 통과해
검사가 통째로 헐거워진다. **다마스↔라보 한 쌍만** 동가를 허용했다:

```sql
  case when oa.vt = '다마스' then b.base_fare <  a.base_fare
                            else b.base_fare <= a.base_fare end
```

🔴 **고친 곳이 둘이고 같은 커밋에 있다** — 마이그레이션 ④(5)와 **`_verify.sql` ⑥-b**.
한쪽만 고치면 다음 `verify` 가 「차급 역전 15칸」으로 빨간불을 띄우고, 그것을 본 세션이
멀쩡한 값을 되돌린다.

🟢 **완화가 정확히 좁은지 재서 확인했다** — 다마스=라보 통과(0) · **라보<다마스 는 여전히
위반(1)**. 즉 「라보가 다마스보다 싸지는 것」은 지금도 막힌다.

🔴 **막혀 있는 데이터가 있는 것이 아니었다.** 원인은 **승인부터 담당자가 배차를
등록하기까지의 시간 동안 화면이 통째로 비어 있던 것**이다 — 배차·운송 조회도 홈의
「진행 중인 운송」도 `dispatches` **만** 읽는데, 그 행은 담당자가 오더·배차를 만들어야
비로소 생긴다. **데이터를 고치는 마이그레이션이 필요한 일이 아니었고, 그래서 DB 0 이다.**

🔴 **다음에 「저장했는데 안 보인다」류 신고를 받으면 여기부터 할 것** — PR #154 가
세운 규칙(화면보다 DB 를 먼저 잰다)이 이번에도 범위를 절반으로 줄였다.

### ② 🔴 오더를 자동으로 만들어서 메우지 않았다 — 27차 확정이다

가장 쉬운 길은 승인 시점에 `orders` 를 만드는 것이지만 **27차가 못박았고 그 사유가
`app/api/customer/approve-quote/route.ts` 에 그대로 적혀 있다** — ① 같은 견적에 오더가
**두 번** 생길 수 있고 ② 담당자가 화주 조건을 확인하는 흐름을 화주가 건너뛴다.

→ **DB 에 아무것도 만들지 않고 화면에만 그리는 「가상 카드」**로 메웠다.
🔴 **「그냥 오더를 만들면 되지 않나」로 되돌리지 말 것.**

### ③ 🔴 `lib/portalPendingDispatches.ts` — 「아직 배차가 없는 건」의 유일 정의처

🔴 **배차·운송 조회와 홈이 같은 함수를 쓴다**(`lib/dispatchStage.ts`·
`lib/portalCancelledDispatches.ts` 가 세운 규칙과 같은 결). 한쪽만 고치면 「홈에는 뜨는데
조회에는 없는」 상태가 된다.

🔴 **두 갈래를 다 센다 — ①만 만들지 말 것.**

```
  ① 수주 견적인데 오더가 아직 없다   ← 화주가 승인한 직후의 자리
  ② 오더는 있는데 배차가 아직 없다   ← 담당자가 오더만 만들어 둔 자리
```

①만 만들면 **오더가 생기는 순간 카드가 사라졌다가 배차가 등록되면 다시 나타나**, 화주
눈에는 건이 없어졌다 돌아온 것으로 보인다. 둘은 겹치지 않는다(①은 오더가 없는 것만 센다).

🔴 **②의 상태 조건(`접수`·`배차중`)을 지워서 고치지 말 것** — 관리자 「+ 배차 등록」
후보와 **같은 두 단계 판정**이다(PR #167 ⑦). 상태로 좁히고 → 실제 배차가 있는 것을 뺀다.
조건을 지우면 **운송이 끝난 오더까지 「접수」 카드로 되살아난다.**

🔴 **①의 「오더가 있는가」 검사에는 상태 조건을 걸지 않는다** — 이미 운송이 끝난 오더도
「그 견적에는 오더가 있다」는 뜻이다. 좁히면 완료된 건의 견적이 다시 카드로 뜬다.

🔴 **취소된 배차가 있는 오더는 여기 안 걸린다** — 취소도 `dispatches` 행이라 ②의
「배차가 있다」에 해당하고, 그 건은 취소 카드가 이미 말한다.
🔴 **`lib/portalCancelledDispatches.ts` 와 합치지 말 것** — 저쪽은 「있는 배차를 어떻게
보여줄까」이고 이쪽은 「없는 배차를 어떻게 메울까」다.

가상 행의 모양 — 🔴 **셋 다 이유가 있다.**

```
  dispatch_status·pickup_confirmed·delivery_confirmed = null
      → getDispatchStage() 가 0(접수) 을 돌려준다. 화면에서 단계를 따로 정하지 않는다.
  order_id = null
      → getPortalCancelNotice() 가 취소 이력을 찾는 열쇠다. 채우면 「배차가 하나도
        없는 건」에 취소 배지가 붙을 길이 생긴다.
  updated_at = null
      → 이 카드가 생기는 계기는 화주 본인의 승인이다. 「업데이트」 알약을 띄울 일이
        아니다(PR #164 가 배너에서 세운 기준과 같다).
```

🔴 **접수 시각은 `approved_by_customer_at`**(승인한 때)이고 없으면 `created_at` 으로
떨어진다. `created_at`(견적을 만든 때)만 쓰면 **며칠 전에 낸 견적을 오늘 승인한 건이
목록 한참 아래에 묻힌다.**

🔴 **오더번호가 아직 없으면 「견적 20260918007」로 보여준다.** 접두어 「견적」을 빼지
말 것 — 두 번호가 같은 `YYYYMMDD+일련번호` 모양이라 접두어가 없으면 오더번호로 오해한다.
검색으로도 걸린다(`useListSearchSort` 의 `searchFields` 에 `quote_no` 를 더했다).

🔴 **합치기도 정의처가 한다**(`mergePortalPendingRows`) — 홈이 상위 5건만 자르므로 화면이
각자 정렬하면 「홈에 뜨는 5건」과 「조회 맨 위 5건」이 서로 다른 건이 된다.

⚠️ **알아 둘 구멍 하나** — 담당자가 `?from_quote=` 를 거치지 않고 오더를 직접 만들면
`orders.quote_id` 가 비어서 ①이 그 견적을 계속 「오더 없음」으로 본다. 그러면 같은 건이
가상 카드와 진짜 배차 카드로 **두 번** 보인다.
🔴 **새 판정 기준을 만들지 말 것** — 관리자 쪽이 **이미 같은 기준으로** 배지를 띄우고
(`lib/unlinkedWonQuotes.ts` · TopNav 「견적 관리」), 오더 상세의 **「견적 연결」**이 그것을
뒤늦게 잇는 길이다. 🟢 실측상 지금 어긋나 있는 건은 **0건**이다.

### ④ 곁다리 — `WON_QUOTE_STATUS` 정의처를 옮겼다(범위를 내가 넓힌 판단)

`'수주'` 상수가 `lib/unlinkedWonQuotes.ts` 에 있는데 **그 파일이 맨 위에서 관리자

### ⑥ 이메일 도메인 고르기 — `EmailField`(리뷰 1라운드)

`[아이디] @ [도메인]` + 아랫줄에 **도메인 고르기** 드롭다운. 목록은 **11종**

🔴 **아이디·도메인을 별도 state 로 들지 않는다** — **값에서 매번 갈라 읽는다**(마지막 `@`
기준 · `splitEmail`/`joinEmail`). 별도 state 를 두면 프리필·초기화 때 두 값이 조용히 어긋난다.
🔴 **도메인 칸을 잠그지 않았다** — 잠그면 `naver.com` 을 고른 뒤 회사 도메인으로 바꾸려면

🔴 **고른 값을 따로 기억하지 않는다** — 드롭다운에 보이는 것은 **지금 도메인 값**이 목록에
있으면 그것, 없으면 「직접 입력」이다. 그래서 손으로 고쳐도 표시가 항상 맞는다.
🔴 **아랫줄 배치는 실측해서 정했다** — 칸 셋을 한 줄에 놓으면 3열 격자(한 칸 약 380px)와

⚠️ **곁다리로 제출 직전 검사 하나를 넣었다**(지시에 없던 것) — 아이디만 적고 도메인을

오류 문구가 안 뜬다 — PR #121 이 같은 자리에서 겪었다). **빈 값은 그대로 통과**한다.

`display: block` 을 이겨야 한다 — 원칙 58번) · 🔴 **폭을 JS 로 재서 감추지 말 것**
(첫 그림에서 잘못된 쪽이 한 번 번쩍인다).

⚠️ 최초 커밋에서 `APPLY_CONSENT.detail` 을 한 문장으로 줄였다(「승인 여부와 무관하게

### ⑤ 🚨 곁다리 — 날짜가 9시간 어긋나고 있었다

🔴 **사용자에게 먼저 보고하고 승인받은 뒤에 고쳤다**(범위를 내가 넓힌 것이다).

운영 오더 **3건** 실재 ㉚-g). 두 문자 모두 그런 건은 **날짜만** 찍는다 —

### ⑥ C장 — 머리말 하나 · 견적 버튼 이름 · 재발송 제목 결함

**머리말은 `SMS_HEADER` 하나다**(`[위캐리운송]`). 7종이 전부 이 상수를 쓰고 **견적 LMS
제목**도 같다 — ⚠️ 그 제목에는 **띄어쓰기가 있었다**(`[위캐리 운송] 견적 안내`).
🔴 **이메일 2건의 영문 머리말은 범위 밖이다**(Resend 미가동 · diff 0).
🔴 **이미 나간 문자의 본문·제목은 고치지 않는다** — `sms_logs` 를 UPDATE 하지 말 것.
🟢 **견적 링크 문자는 상수로 바꾼 뒤에도 87byte 그대로다**(여유 3byte).

🚨 **재발송이 87byte 견적 단문에 제목을 붙여 LMS 로 올리고 있었다.** 솔라피는 제목이
있으면 단문을 장문으로 올린다. `send-sms` 와 `sms-logs/resend` **두 곳에 조건을 따로
적은 것**이 원인이고 **재발송 쪽이 길이를 안 봤다**. 에러가 아니라 **요금과 알림창 표기만**
달라져 눈치채기 어려운 자리다 — `smsSubjectFor()` **한 함수**로 모았다.
🔴 **`template_type` 만 보는 쪽으로 되돌리지 말 것** — 담당자가 확인창에서 본문을 길게
고치면 그때는 LMS 가 맞으므로 **판정 기준은 종류가 아니라 본문 길이**다.
⚠️ **운영에 시험 대상이 실재한다** — `quote_summary` 실패 **2건**(㉚-c).

견적 상세 버튼은 **「견적서 문자 발송」**이다(사용자 확정). 옆 두 버튼이 「견적서 출력
(PDF)」·「(Excel)」이라 **무엇을 어떻게 보내는지**가 한 형식으로 읽혀야 한다.
🔴 **「링크 문자 발송」으로 바꾸지 말 것** — 링크 생성이 실패하면 **옛 요약 LMS 로
내려가서**(`send-quote-sms`) 그때는 틀린 이름이 된다.

### ⑦ 리뷰 2·3라운드 — 고객센터 시간, 갈랐다가 도로 합쳤다

2라운드 — *"고객센터 문의 시간 조절이 필요하다.(화주포털내에 표시되는 부분만) 09:00~19:00
으로 바꾸자. 랜딩페이지에서는 이 시간 부분을 뺐는데 랜딩페이지는 없느채로 유지하자."*
→ 상수를 **둘로 갈라**(`COMPANY_SUPPORT_HOURS_PORTAL`) 포털만 19시로 올렸다.
3라운드 — *"공개화면도 19시로 통일하자."* → **값이 같아져 갈라 둘 이유가 없어져 다시 합쳤다.**

🔴 **지금은 `COMPANY_SUPPORT_HOURS = "평일 09:00 ~ 19:00"` 하나뿐이다. 다시 둘로 가르지 말 것** —
값이 같은 상수를 둘로 두면 언젠가 한쪽만 고쳐져 **화주가 로그인 전후로 다른 시간**을 본다
(대표번호 상수 둘이 같은 이유로 「함께 고칠 것」 경고를 달고 있다).
🔴 **`GuideBlock` 의 `only?: "public" | "portal"` 도 함께 지웠다 — 다시 만들지 말 것.**
시간이 갈렸던 그 하루만 쓰던 장치다. 화면을 가르는 일은 항목의 **`scope`** 가 한다 —
블록 단위로 가르면 두 화면이 각각 무엇을 보는지 **코드만 읽어서는 알 수 없어진다**.
사유를 그 타입 위 주석에 남겼다.

🚨 **여기서 하나 잡았다 — 로그인 화면의 시간 줄은 둘이고 뜻이 다르다.**
「접수 기준 당일 발급」 위의 것은 **고객센터 문의 시간이 아니라 발급 약속**이고, 31차가
**랜딩 FAQ(`components/landing/data.ts` 의 `account`)와 일부러 맞춰 둔 값**이었다
(*"두 화면이 다른 시간을 약속하면 지키지 못하는 쪽이 생긴다"* — 그 주석을 읽고 알았다).
2라운드에서 그것까지 19시로 올렸다가 **되돌렸고**, 3라운드에서 **랜딩 FAQ 를 같이 올리면서**
셋을 함께 19시로 맞췄다. 🔴 **이 셋(로그인 · `/apply` 접수완료 · 랜딩 FAQ)은 한쪽만 고치지 말 것.**
🔴 **랜딩 푸터의 운영시간 줄은 그대로 비어 있다**(2026-09-01 에 뺀 것을 사장님이 재확정).

⚠️ **주석을 읽지 않았으면 발급 약속을 조용히 바꿀 뻔했다** — 시간 문자열 하나를 고칠 때도
**그 줄이 무엇을 약속하는지**부터 볼 것.
