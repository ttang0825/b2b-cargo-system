다만 **현재 비밀번호를 알아야** 하는 화면이라 임시 비밀번호를 받은 직원을 가둘 수 없어서
`/admin/change-password` 를 따로 만들었다(포털과 같이 **메뉴에는 안 넣는다**).

**═══ ⑤ 🔴 저장소가 public 이다 — 이것이 이번 차수의 설계를 두 번 바꿨다 ═══**
`visibility: public` 을 API 로 확인했다. **Actions 로그는 로그인 없이 누구나 읽는다.**
1. 🔴 **아이디 값을 마이그레이션에 넣지 않았다**(지시서 2-2 와 다름). 커밋하면 **직원 실명
   4명과 로그인 아이디 4개가 git 이력에 영구 공개**되고, 로그인 화면이 공개돼 있으니
   **유효한 아이디 목록을 그대로 넘기는 셈**이다. 값 채우기는 Supabase SQL Editor 에서
   한 번 했고(사용자), `_verify.sql` ⑪ 로 확인했다.
2. 🔴 **`_verify.sql` ⑪ 의 조회를 전부 마스킹했다** — `홍**` / `eg***@d***` / `we***`.
   **이 마스킹을 풀지 말 것.** 사람이 누구인지 아는 것은 사용자이지 이 로그가 아니다.
🔴 **앞으로도 직원 실명·이메일·아이디·전화번호를 마이그레이션이나 verify 출력에 그대로
쓰지 말 것.** 이 저장소는 private 가 아니다.

**═══ ⑥ ⚠️ 아이디 넷이 전부 `we` 로 시작한다 — 화면 문구를 지시서와 다르게 적었다 ═══**
```
  전준영 admin  wejjy      김도연 admin  wekdy
  정제원 admin  wejjw      홍길동 staff  wehhh
```
지시서는 화면 도움말에 「🔴 we 로 시작하지 마십시오」를 적으라고 했는데, **실제 아이디가
전부 `we` 로 시작한다**(사용자 확정). 화면이 반대로 안내하면 다음 사람이 헷갈린다.
🔴 **그래서 이렇게 적었다** — 「영문 소문자와 숫자만 · 4~20자 · 첫 글자는 영문. 화주포털
아이디(we+숫자 8자리)와 같은 형태로는 만들지 마세요.」 `LOGIN_ID_HELP` 상수 한 곳이다.
🟢 실제 충돌 위험은 낮다 — 포털은 `we`+**숫자 8자리**, 직원은 `we`+**영문**이고 표도
로그인 화면도 완전히 별개다.
🟢 **아이디는 언제든 바꿀 수 있다**(사용자 질문에 답한 내용) — Auth 이메일과 무관한 평범한
컬럼이라 바꿔도 비밀번호는 그대로다. 화면에도 그렇게 적어 뒀다. **포털 아이디는 반대로
바꾸기 어렵다**(아이디가 곧 Auth 이메일이다).

**═══ ⑦ 🔴 실패 응답을 한 종류로 뭉갠 것은 의도다 ═══**
「없는 아이디」·「비밀번호 틀림」·「퇴사 처리됨」이 **문구·상태코드·응답시간 모두 같다.**
갈라 보여주면 아이디를 넣어보는 것만으로 **누가 재직 중인지가 새어 나간다.**
🔴 **「사용자에게 친절하게」를 이유로 나누지 말 것.** 형식 위반(`we_jjy` 등)도 DB 조회조차
하지 않고 같은 실패로 떨어진다 — 알려주면 규칙을 모르는 공격자에게 규칙을 가르쳐 준다.
🔴 **없는 아이디일 때도 비밀번호 확인을 한 번 태운다**(`no-such-staff@wecarry-admin.invalid`).
안 태우면 「빨리 실패했다」는 것만으로 그 아이디가 없다는 게 드러난다. `.invalid` 는 표준이
예약한 TLD 라 누구도 그 주소로 계정을 만들 수 없다.
🟢 **잠금 문구만 다르다** — 판정 근거가 「방금 그 사람이 입력한 문자열」이라 계정 존재를
말해주지 않는다(없는 아이디로 10번 틀려도 똑같이 잠긴다. 시험으로 확인함).

**═══ ⑧ 🔴 실패 횟수 제한에 표를 만들지 않았다 — 한계를 알고 쓸 것 ═══**
같은 아이디로 **10분에 10번 실패 → 5분 잠금**, 값은 **프로세스 메모리**(`LoginAttemptTracker`).
```
  🔴 IP 를 저장하지 않는다   IP 는 개인정보라 저장하면 처리방침 제2조를 고쳐야 한다(범위 밖)
  🔴 표를 안 만든 둘째 이유   완료조건 1이 _migrations 26행이라, 표를 만들면 27행이 된다
  ⚠️ 한계                   Vercel 은 인스턴스가 여럿이라 완벽히 못 막는다 —
                            한 연결로 반복해 두드리는 경우를 막는 과속방지턱이지 벽이 아니다
  ⚠️ 대가                   아이디를 아는 사람이 남의 계정을 5분간 잠글 수 있다
                            (관리자 계정이 3개라 감당 가능하다고 봤다)
```
🔴 **제대로 된 지속 저장이 필요해지면 표와 함께 별도 차수다.** 그때도 **IP 를 넣으려면
처리방침을 같이 고쳐야 한다**는 것을 잊지 말 것.

**═══ ⑨ 🔴 로그인은 목으로 흉내내기 어렵다 — 어떻게 쟀는가 ═══**
판정만 **순수 함수**(`lib/staffLogin.ts` 의 `resolveStaffLogin`)로 떼어내고 라우트는 결과를
응답으로 옮기기만 하게 했다. 그래서 다섯 갈래를 주입으로 전수 시험할 수 있다.

**═══ ⑩ 🔴 되돌리면 안 되는 구현 지점 ═══**
- 🔴 **재설정 API 는 서버에서 `role === 'admin'` 을 다시 확인한다**(원칙 25번). 화면에서
  버튼을 숨기는 것만으로는 콘솔에서 직접 부르는 것을 못 막는다. **대상이 실제 직원
  계정인지도 확인한다** — 안 하면 화주포털 계정 비밀번호까지 바꿀 수 있다.
- 🔴 **재설정은 비밀번호와 `must_change_password` 를 `updateUserById` **한 호출로** 함께
  바꾼다.** 따로 돌다 한쪽만 성공하면 「임시 비밀번호인데 아무 화면이나 들어가지는」
  상태가 생긴다. ⚠️ `updateUserById` 는 `user_metadata` 를 **병합이 아니라 교체**하므로
  `role`·`status` 미러링을 되살리는 보정이 뒤따른다 — 그 블록을 지우지 말 것.
- 🔴 **middleware 의 강제변경 검사는 재직 확인 *뒤*에 있다.** 앞에 두면 퇴사자가 차단
  대신 변경 화면으로 간다. 판정은 `user_metadata.must_change_password === true` 이고
  값이 없으면 막지 않는다(켜는 곳이 재설정 API 한 곳뿐이라 그게 맞다).
- 🔴 **`/admin/change-password` 라우트를 지우지 말 것** — middleware 가 여기로 보내는데
  화면이 없으면 404 에 갇힌다. **`PUBLIC_PATHS` 에 넣지도 말 것**(로그인이 필요한 화면).
  `PUBLIC_PATHS` 3개는 그대로다.
- 🔴 **해제는 클라이언트가 직접 안 한다** — `/api/admin/confirm-password-change` 가 토큰을
  **서버에서 직접 검증**한 뒤 끈다(원칙 30번. 화주쪽과 같은 구조, **표는 다르다**).
  DB 와 `user_metadata` 를 **둘 다** 끈다 — 한쪽만 끄면 계속 되돌아온다.
- 🔴 **판별자를 `kind: "ok"|"failed"|"locked"` 문자열로 뒀다** — 이 저장소는 `strict: false`
  라 `if (!result.ok)` 로는 타입이 **안 좁혀진다**(실제로 컴파일 에러가 났다). boolean
  판별자로 되돌리지 말 것.
- ⚠️ **`.ilike("login_id", id)` 를 쓴다** — supabase-js 에 `lower(col) = ?` 를 거는 방법이
  없다. `_`·`%` 가 와일드카드가 되지만 `LOGIN_ID_PATTERN` 이 그 앞에서 이미 걸러낸다.
  **패턴 검사를 빼면 이 자리가 구멍이 된다.**
- 🔴 **성공 경로에서 `setLoading(false)` 를 부르지 않는다**(PR #129 와 같은 이유).
  로그인 화면의 `LEGACY_SAVED_EMAIL_KEY` 제거도 지우지 말 것 — 옛 키에는 **이메일**이
  들어 있어서 그대로 읽으면 아이디 칸에 이메일이 채워진다.
